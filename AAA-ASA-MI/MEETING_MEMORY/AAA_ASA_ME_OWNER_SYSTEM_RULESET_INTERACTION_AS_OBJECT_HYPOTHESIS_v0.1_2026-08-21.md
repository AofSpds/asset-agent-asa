## OWNER_EXPLICIT

- The Owner sees a system/regime as a set of rules.
- A person can also be viewed as a system.
- The Owner has considered whether interaction itself should be represented as an object.
- The Owner currently prefers the direction in which objects may be understood as relatively stable local systems/rulesets/capability boundaries, while interaction remains highly flexible.
- Relation flexibility and interaction flexibility remain primary requirements.

## OPEN HIGH-INTEREST HYPOTHESIS

Possible current framing:

`OBJECT ~= LOCAL SYSTEM / RULESET / CAPABILITY BOUNDARY`

`PERSON ~= SYSTEM`

`INTERACTION ~= SITUATED SYSTEM-TO-SYSTEM COUPLING`, potentially itself reified/materialized as an object when useful.

`RELATION ~= EMERGENT / PERSISTENT STRUCTURE OR HISTORY ARISING FROM INTERACTION`

`PROTOCOL = OPEN; potentially higher-order rules/coordination grammar governing or interpreting interactions, but not yet fixed.`

The key idea is not that every interaction must permanently be an object. Rather, the architecture should allow interaction to be treated as a first-class object/system when that representation is useful, without forcing the ontology prematurely.

## IMPORTANT DISTINCTION

Do NOT collapse without evidence:

- object-as-ruleset;
- interaction-as-object;
- protocol-as-ruleset;
- relation-as-interaction-history;
- person-as-system.

These are related but distinct hypotheses.

## RESEARCH IMPLICATION

High-priority prior-art families now include:

- coalgebraic views of state-based systems by observable interaction behavior;
- behavioral/interface/session/protocol types;
- game semantics and interaction semantics;
- open systems / compositional systems / wiring-diagram formalisms;
- affordance and capability models;
- actor/object semantics;
- cybernetics and dynamical systems;
- category-theoretic open systems / structured cospans / decorated cospans / operadic composition;
- higher-order process calculi where processes/interactions can themselves become manipulable entities.

## FAILURE MODE

Reject architectures where reifying interaction as an object merely freezes it into a rigid predefined class hierarchy. The purpose of reification, if used, is to make interaction first-class, inspectable, composable, historized, and potentially mutable—not to reduce interaction diversity.
