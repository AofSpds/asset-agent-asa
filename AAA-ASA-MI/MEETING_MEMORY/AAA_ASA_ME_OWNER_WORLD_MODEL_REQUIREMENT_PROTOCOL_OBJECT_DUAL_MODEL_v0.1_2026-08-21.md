## 1. Owner-explicit requirement clarification

OWNER_EXPLICIT:

- The Owner had considered protocol important before the current candidate interrogation exposed the issue clearly.
- Relation and/or Event responsiveness is a core requirement.
- The missing concept is that Protocol can define how the model responds to a Relation and/or Event.
- The desired world model requires BOTH a Protocol Model and an Object Model.
- The Protocol Model should be variable and flexible.
- The Object Model should respond flexibly, case-by-case, to the active protocol.
- Where scientifically and architecturally appropriate, the Object Model may be capable of MUTATE-like adaptation in response to protocol interaction.
- Protocol itself may be modeled as a Relation/Event model, or as a mechanism operating over relations/events; this is not yet fixed.
- The deeper reason for valuing variability and relationality is to support many heterogeneous protocol sets rather than one fixed adjudication regime.
- The Owner also believes such adaptability may better correspond to the internal implementation of reality.

## 3. Object Model requirement

The Object Model is not assumed to be a fixed immutable object ontology.

Required candidate capabilities include:

- represent mutable/contextual entities, relations, events, states, or their equivalents;
- avoid collapsing every perspective into one permanent identity assignment;
- expose enough structure for heterogeneous protocols to query or act on it;
- preserve uncertainty, conflict, plurality, and supersession where appropriate;
- permit view/materialization differences by context/purpose/protocol;
- where justified, adapt or mutate without silently rewriting Frozen semantic history.

`MUTATE` here is an Owner research hypothesis/requirement direction, NOT an implementation command and NOT authorization to overwrite a Frozen exact target.

Any semantic mutation of a Frozen model requires successor target + new exact identity + new validation.

## 4. Protocol Model requirement

The Protocol Model is a first-class modeled object, not merely hard-coded evaluation logic.

A Protocol may potentially define or govern:

- which Relation/Event is relevant;
- what perspective/purpose is active;
- what facts/attributes/relations are queried;
- what transformation or materialization is requested;
- how judgment/action/interpretation is produced;
- what uncertainty/conflict state is allowed;
- what update or mutation request is issued to the Object Model;
- what invariants or boundaries must be preserved.

The Protocol Model itself should support variability, composition, contextual activation, and heterogeneous protocol families.

## 5. Interaction requirement

The key research target is not a one-way pipeline only.

Candidate architecture hypothesis:

`PROTOCOL MODEL <-> OBJECT MODEL`

The protocol may query, activate, constrain, interpret, transform, or request mutation of the object/world representation.

The object/world representation may respond with:

- a local judgment/materialized view;
- multiple valid views;
- UNKNOWN;
- CONFLICT;
- NOT_PROVEN;
- OUT_OF_SCOPE;
- a request for more evidence/context;
- a bounded mutation/adaptation result;
- refusal where the requested protocol cannot be supported without semantic distortion.

This interaction is more important than whether a single candidate protocol is itself philosophically correct.

## 6. Corrected candidate question

LOW-DISCRIMINATION:

- "Is this protocol/model correct?"
- "Is this the world model?"
- "Which single adjudication protocol should win?"

HIGHER-DISCRIMINATION:

- "Can your underlying model support this protocol without semantic distortion?"
- "What internal structure does the protocol act on?"
- "How does the model behave under this protocol?"
- "Can the same model support a materially different protocol?"
- "What happens when protocols request incompatible views/actions?"
- "Which aspects are allowed to mutate and which must remain invariant?"
- "When must the model return UNKNOWN/CONFLICT instead of adapting?"

## 9. Open questions

Still explicitly open:

- Is Relation or Event the more fundamental foreground object?
- Is Protocol itself primarily an Event/Relation construct, a distinct modeled object, or both?
- Does protocol selection require a separate meta-protocol/router, or can the interaction emerge from the model itself?
- What may mutate at runtime versus only through successor-model evolution?
- Which invariants must survive protocol changes?
- How should conflicting protocols coexist or interact?

These are research questions, not gaps to fill by inference.
