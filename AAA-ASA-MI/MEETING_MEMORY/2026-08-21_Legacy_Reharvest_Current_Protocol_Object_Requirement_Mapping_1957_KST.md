## 1. Purpose

Map the current Owner requirement around diversity/flexibility, Relation/Event responsiveness, Protocol-as-interaction modeling, explicit capability limits, and possible successor mutation against pre-existing PCS-SHAI / prior ASA-MI legacy without retroactive rewriting.

## 2. Strong direct legacy ancestors

The PCS-SHAI v0.2 revision proposal already contains strong adjacent directions:

- Protocol standardizes definability, not the substantive definition.
- Global Protocol is closer to shared grammar/infrastructure than a universal worldview.
- Person/Community local rulesets govern their own rule/status/authority/lifecycle semantics.
- `UNKNOWN`, `UNDEFINED`, `DISPUTED`, new relation/status semantics are valid states rather than automatic errors.
- `NEW RELATION TYPE != PROTOCOL FAILURE` and future extensibility should not require rewriting the entire Core.
- Boundary may be a governed relational status rather than a fixed metaphysical boundary.
- Persona Evolution is explicitly allowed and may involve memory, relationship, status, integration, role and capability changes.
- History may remain immutable while current meaning/status evolves.
- Diversity and connectivity are both valued; `CONNECTIVITY != HOMOGENIZATION`, `DIVERSITY != DISCONNECTION`.
- Replaceability, reconfiguration, recoverability, optionality and adaptability are important survivability axes.
- Protocol capture / monoculture is a first-class counter-hypothesis.

These are legacy ancestors, not proof that the current model requirement already existed in exact form.

## 3. Current requirement that is materially newer/deeper

The current Owner requirement adds a stronger structural proposition not explicitly established in the legacy Whitepaper:

- Protocol may itself be modeled as interaction / Relation / Event / Process semantics.
- World-model performance should prioritize heterogeneous Protocol / interaction support rather than one protocol correctness.
- Object/world representation and Protocol/interaction semantics may mutually affect one another.
- A model should expose explicit capability boundaries rather than claim universal support.
- Unsupported interaction may yield UNKNOWN / OUT_OF_SCOPE / CONFLICT / REQUIRES_SUCCESSOR_MUTATION.
- If a model cannot support a materially new interaction without semantic distortion, successor mutation/evolution may be preferable to pretending compatibility.

Do NOT retroactively claim that PCS-SHAI v0.1/v0.2 already specified `OBJECT MODEL <-> PROTOCOL MODEL` or `Protocol = interaction/event/relation model` as a settled architecture.

## 4. Important bridge from later ASA-MI reharvest

Later ASA-MI research already deepened the legacy using:

- Relation as constitutive axis;
- Event as transition/change aspect;
- Process as temporally extended change;
- Instance as bounded materialization;
- perspective/scale/purpose-dependent Event/Relation classification;
- interaction/relation altering future Standpoint/constitution;
- Persona succession/materialization rather than silent eternal-object mutation.

This makes the current Protocol-as-interaction hypothesis historically continuous with the research trajectory, but it remains a current hypothesis rather than a legacy canonical requirement.

## 5. Interpretation

Best current mapping:

LEGACY PCS-SHAI:
`extensible grammar + local semantic freedom + relation/status/rules/lifecycle + unknown-friendly architecture + evolvability + anti-monoculture`

LATER ASA-MI:
`Relation/Event/Process/Materialization + interaction can alter constitution + succession`

CURRENT OWNER REQUIREMENT:
`diversity/flexibility first + Protocol as interaction/Relation/Event modeling candidate + explicit support boundary + optional successor mutation when support requires deeper change`

This is better described as a deepening/recombination of legacy ancestors than as either a wholly new invention or a legacy requirement already present verbatim.
