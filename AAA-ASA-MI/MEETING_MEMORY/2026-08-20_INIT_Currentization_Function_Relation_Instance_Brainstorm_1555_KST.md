# 1. ASA-MI Research Goal — Current Working Form

Owner clarified the larger objective of ASA-MI.

The project aims to:

1. collect already-developed abstraction hypotheses that humans have used to model reality across philosophy, thought, religion, mathematics, science, computer science, and other disciplines;
2. preserve those abstractions as reusable research legacy rather than re-inventing them unnecessarily;
3. develop new abstraction hypotheses when the existing legacy is insufficient;
4. maintain a current assessment of those hypotheses;
5. select/tag hypotheses as needed for a target modeling task;
6. compose a concrete instance from the hypotheses judged useful for that instance;
7. keep revising the hypothesis set, composition method, and instance representation as new evidence, criticism, implementation experience, and research accumulate.

Important Owner clarification:

The intent is not to display philosophical knowledge or cite philosophy for prestige.

The intent is closer to:

> There is already a long abstraction legacy. Reuse it where useful instead of pretending ASA-MI invented the abstraction from zero.

This implies that a hypothesis may have a conceptual ancestor without being identical to that ancestor.

# 3. Liveness and Immutability

Owner expressed a lifecycle intuition:

> Immutability is close to a dead state.

Current ASA interpretation:

For a living modeled entity/research system:

- change does not have to occur at every moment;
- but the possibility of successor change must remain open;
- a state that is permanently prohibited from successor revision is lifecycle-wise close to DEAD / TERMINATED / NO-LONGER-EVOLVING.

Important distinction:

`MUTABLE LIVING STATE != MUTABLE HISTORY`

A past record may and often should remain immutable while the living present evolves.

Therefore:

`IMMUTABLE CURRENT MEANING ~= DEADNESS` (working analogy, not formal ontology)

while

`IMMUTABLE HISTORICAL RECORD = MEMORY / LINEAGE INTEGRITY CANDIDATE`

Also:

`FREEZE(instance/state@t) != FREEZE(the living lineage/research system)`

A frozen snapshot may be a photograph of a living system, not the freezing of the system itself.

# 7. Terminology Cleanup — Remove Ambiguous Bare `STATUS`

During brainstorming, the word `STATUS` became overloaded.

Two different concepts had been conflated:

1. what value a modeled instance/member has under current conditions;
2. how ASA-MI currently judges a hypothesis.

Working terminology proposal accepted positively by Owner:

## HYPOTHESIS
An abstraction hypothesis being researched.

## CURRENT_JUDGMENT
How ASA-MI currently evaluates that hypothesis.

Examples may include CANDIDATE / SUPPORTED / CHALLENGED / TECHNICAL_REVIEW_REQUIRED, but the vocabulary itself is not final.

## CURRENT_VALUE
A current value produced/indicated for a member under particular conditions, if such a concept remains useful under the adopted representation.

## RELATION
A relationship between instances/concepts/hypotheses/etc.; identified as a major research axis requiring special attention.

## MEMBER_ROLE
The role that a selected hypothesis/member plays in a particular model/instance composition.

Lifecycle terminology such as `EPISTEMIC_POSTURE` and `LIFECYCLE_PHASE` was intentionally rejected as unnecessarily obscure at this stage.

Bare `STATUS` should be avoided as a canonical ASA-MI term when it causes ambiguity.

# 9. Function Representation Hypothesis — Current Strong Candidate

Owner currently considers function representation a strong modeling candidate, subject to technical review and replacement if a better representation is found.

This is NOT P0 itself.

This is NOT an instruction.

It remains a technical/modeling hypothesis.

Weak form:

> A mutable member/current value may be more appropriately represented as a mapping result over time/environment/context/etc. than as a fixed scalar or immutable constant.

Stronger current form:

> The concrete instance object itself may be represented/materialized as a mapping result under specific time/environment/context/relation/history/etc.

Loose conceptual sketch:

`INSTANCE = F(time, environment, context, relation, history, ...)`

This does NOT mean:

`REALITY IS A FUNCTION`

It means function/mapping is a candidate representation for modeling a concrete instance.

Owner emphasizes that if a better representation exists, it should replace the function approach.

# 10. Function Member Representation Hypothesis

A stronger sub-hypothesis emerged:

> When an instance is instantiated, its members may be normalized to a common function/mapping representation interface rather than stored as bare fixed values.

This may allow:

- time/context/environment dependence;
- member-level replacement;
- explicit current evaluation;
- consistency of representation across heterogeneous member semantics.

However this remains an implementation/representation research candidate.

It must be attacked for over-abstraction, replay difficulty, serialization, caching, equality, circular dependencies, side effects, versioning, stochasticity, performance, and implementation complexity.

# 11. Primitive Values Are Not Necessarily Eliminated

Owner noted that the function representation hypothesis probably cannot eliminate primitive values.

ASA interpretation:

`EVERY MEMBER FUNCTIONALLY REPRESENTED`

may be researched without asserting:

`EVERYTHING IS A FUNCTION`

Functions still require some form of domain/codomain values.

Primitive candidates could include numbers, symbols, booleans, references, timestamps, identifiers, or other atomic representations.

One possible technical idea:

A primitive/fixed value could still be exposed through a constant function/mapping interface.

Example conceptually:

`M(x) = 3`

This would distinguish:

- a currently constant result;
- from an ontological claim that the member can never change.

This is only a technical candidate, not an adopted rule.

# 13. Instance Discreteness and Succession — Replace Continuity

Owner corrected the earlier use of “continuity.”

In a digital world, strict continuity is not the preferred primitive concept.

Working direction:

`INSTANCE_1 != INSTANCE_2`

but

`SUCCESSION_RELATION(INSTANCE_1, INSTANCE_2)`

may hold.

Preferred terminology:

- PREDECESSOR
- SUCCESSOR
- SUCCESSION_RELATION
- LINEAGE

Avoid using `INHERITANCE` as the primary English term because of strong OOP-class-inheritance semantics.

Important implications:

`SUCCESSION != IDENTITY`

`SUCCESSION != EQUALITY`

`SUCCESSION != COMPLETE COPY`

A successor may differ materially from its predecessor while still participating in a lineage.

Branching is naturally possible:

one predecessor may have multiple successors without requiring one to be the metaphysically “true” continuation.

What exactly constitutes valid succession remains a separate RELATION research question.

# 18. Relation / Instance Circularity — Important Technical Problem

A major technical research question appeared.

If instance construction depends on relations:

`INSTANCE = F(... RELATIONS ...)`

but relation construction depends on instances:

`RELATION = G(INSTANCE_A, INSTANCE_B, ...)`

then a simple one-way function may be insufficient.

Potential alternatives to examine include:

- simultaneous equations;
- constraints;
- fixed-point systems;
- graphs;
- dynamical systems;
- transition systems;
- relational algebra;
- hybrid approaches.

This is an important falsification/technical challenge for the function representation hypothesis.
