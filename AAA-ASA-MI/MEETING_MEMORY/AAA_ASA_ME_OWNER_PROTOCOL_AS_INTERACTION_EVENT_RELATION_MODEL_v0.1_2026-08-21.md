## 1. Owner-explicit clarification

OWNER_EXPLICIT:

- Protocol may be better understood as modeling interaction.
- Protocol may also be modeled in terms of Event and/or Relation.
- The Protocol concept should not be reduced to a static ruleset or checklist.
- The Owner's intended world-model direction is compatible with treating Protocol as a model of how Objects / Relations / Events interact, respond, transform, or condition one another.

## 2. Current research interpretation

MODEL_INFERRED / HIGH-WEIGHT CANDIDATE, NOT OWNER-ACCEPTED CANON:

`PROTOCOL ~= INTERACTION SEMANTICS OVER RELATION / EVENT STRUCTURE`

A Protocol may therefore describe, depending on the successor architecture:

- which interaction is occurring;
- which Relation becomes active, modified, created, suspended, or removed;
- which Event is recognized or emitted;
- which responses/transitions are permitted, required, optional, or invalid;
- which perspective/materialization becomes relevant;
- how participating Object Models may change state;
- whether adaptation/mutation is requested or prohibited;
- what evidence is required to establish the interaction;
- what uncertainty/conflict state must be preserved.

## 3. Consequence for Object Model / Protocol Model split

The distinction should not be prematurely interpreted as two unrelated software modules.

Candidate possibilities remain open:

A. `OBJECT/RELATION/EVENT SUBSTRATE + PROTOCOL AS INTERACTION SEMANTICS`

B. `RELATION-EVENT SUBSTRATE WHERE PROTOCOL ITSELF IS A FIRST-CLASS RELATION/EVENT`

C. `PROCESS-FIRST MODEL WHERE OBJECT AND PROTOCOL ARE DIFFERENT VIEWS OF INTERACTION DYNAMICS`

D. other successor representations.

The research target is to discover which formulation best preserves flexibility, plurality, protocol generality, and scientific tractability.

## 4. Corrected model-generation question

Do not ask candidates to implement a predetermined protocol set.

Higher-value questions are:

- How does your model represent interaction itself?
- Can Protocol be expressed natively as Relation/Event/process structure rather than external hard-coded logic?
- Can new interaction protocols be introduced without redesigning the entire Object Model?
- Does a Protocol merely read the world, or can it participate in events/relations that change the represented world?
- What distinguishes ordinary interaction/state transition from semantic model mutation?
- Can different protocol families coexist without forcing one ontology or one personality?

## 5. Open state

Still OPEN:

- Relation-first vs Event-first vs Relation-Event hybrid;
- Protocol as separate modeled object vs Protocol as Relation/Event itself;
- whether interaction requires a meta-protocol/router;
- whether protocol activation is represented as an Event, a Relation, a state transition, or some successor construct.

These are research questions and must not be resolved by silent inference.
