# N07 — Typed Protocol Interpreter over a Stable Evidence Kernel

## 1. Candidate identity and governing thesis

N07 treats a Protocol as a first-class, typed, inspectable model that is executed by a small interpreter/VM. Objects are not passive records attached to one fixed workflow, and Protocols are not untyped scripts hidden in application code. An Object supplies identity and evidence; a Protocol supplies a declared interpretation, transition system, view family, status vocabulary, persona policy, and effect budget.

The stable center is deliberately small:

- opaque identities and revisions;
- immutable evidence records;
- reified Relations and Events;
- provenance, time, context keys, and lineage edges;
- typed effect requests and deterministic execution receipts.

Domain meaning is outside that center. It is contributed by admitted Protocol revisions. Accordingly, N07 does not claim a universal semantics, a universal ontology, or that every external procedure can be represented faithfully. It claims only that a bounded class of Protocols can be admitted, interpreted, isolated, observed, and refused against the declared kernel.

The required bidirectionality is explicit:

- Object to Protocol: evidence, Relations, Events, context, and Persona feed selection and transitions.
- Protocol to Object: admitted effects materialize contextual views, update isolated runtime state, or propose a semantic successor with lineage.

Neither direction grants an interpreter the right to rewrite prior evidence or silently alter an existing semantic target.

## 2. Scope, non-claims, and trust boundary

N07 covers execution of finite, resource-bounded Protocol packages over locally addressable evidence snapshots. It is intended for Protocol heterogeneity: two admitted Protocols may assign different views or statuses to the same Object without either becoming globally canonical.

In scope:

- explicit Protocol definitions and revisions;
- structural admission before execution;
- typed reads, view materialization, runtime transitions, and semantic successor creation;
- Object, Relation, and Event responsiveness;
- contextual and Persona-relative results;
- deterministic replay when a Protocol declares deterministic behavior;
- audit receipts, refusal reasons, and lineage verification.

Out of scope unless supplied by an admitted, separately trusted adapter:

- discovering the true meaning of arbitrary source data;
- reconciling all ontologies;
- proving a Protocol is morally, legally, or scientifically correct;
- executing unrestricted native code;
- inferring consent, authority, identity, or causal truth from syntax alone;
- guaranteeing distributed exactly-once delivery;
- collapsing plural statuses into one global status;
- mutating an existing target in place when its semantics change.

The trust boundary contains the kernel, verifier, interpreter, append-only stores, and cryptographic/content digests. Protocol packages, adapters, Persona definitions, evidence producers, and external services are untrusted by default. Admission establishes only machine-level eligibility under a named host policy; it is not endorsement of a Protocol's conclusions.

## 3. Stable evidence kernel

The kernel uses the following closed family of host types. Protocols may define domain types above them but may not redefine their host meaning.

- Id: opaque, globally unique identifier.
- Digest: content digest for immutable payloads and definitions.
- RevisionRef: pair of target Id and revision Digest.
- Instant and Interval: ordered host time values plus an explicit clock identifier.
- ContextKey: canonical digest of declared context dimensions.
- PersonaRef and ProtocolRef: revision-pinned references.
- EvidenceRef: reference to an immutable evidence envelope.
- LineageRef: reference to a typed derivation or succession edge.
- Capability: named host permission with a statically checkable scope.

An EvidenceEnvelope has:

- evidence_id;
- kind, one of Observation, AttributeAssertion, RelationAssertion, EventOccurrence, RetractionNotice, DerivationReceipt, or ExternalAttestation;
- subject references;
- typed payload with schema digest;
- producer and ingestion provenance;
- observed time, asserted time, and ingestion sequence;
- optional validity interval;
- confidence or uncertainty only when the producer declares its scale;
- supersedes or challenges references, without erasing them;
- integrity digest and access label.

The evidence log is append-only. A RetractionNotice changes what a Protocol may conclude at a later cutoff; it does not remove the earlier envelope. Ordering is by a host-assigned ingestion sequence within a partition. Event time remains data and is not silently equated with ingestion order.

The kernel makes no claim that an AttributeAssertion is true, that a RelationAssertion corresponds to a real-world relation, or that one Event caused another. It preserves who asserted what, about which identifiers, under which schema, when, and with which lineage. Domain truth conditions belong to Protocols.

## 4. Explicit Object Model

An Object is an addressable continuity anchor with revisioned semantic targets, not a mutable bag of fields.

ObjectRecord:

- object_id: stable identity anchor;
- object_kind_hint: optional non-authoritative routing hint;
- evidence_heads: indexed references into the evidence log;
- semantic_heads: zero or more current RevisionRefs, because branches may coexist;
- relation_index: inbound and outbound Relation ids;
- event_cursor_map: consumed-log cursors by admitted Protocol instance;
- policy_ref: access and mutation policy;
- created_receipt: immutable creation provenance.

ObjectRevision:

- target: a fresh RevisionRef;
- predecessor: zero or one direct semantic predecessor for a linear step;
- merge_predecessors: optional set for an explicit merge;
- semantic_payload: typed value with schema digest;
- grounds: EvidenceRefs and prior RevisionRefs;
- lineage_edge: typed as CreatedFrom, SuccessorOf, DerivedFrom, ForkedFrom, or MergedFrom;
- authoring ProtocolRef, PersonaRef if applicable, and execution receipt;
- context envelope describing the conditions under which the revision was produced.

RelationRecord is reified rather than stored as an anonymous edge:

- relation_id, relation_type_ref, endpoint roles, endpoint RevisionRefs or Object ids;
- evidence and provenance;
- validity interval and lifecycle state;
- context qualification;
- change Events, including asserted, activated, suspended, superseded, and retracted.

EventRecord is also reified:

- event_id, event_type_ref, actors, subjects, payload, source;
- event time, ingestion sequence, correlation and causation claims;
- evidence and provenance;
- delivery partition and idempotency key.

Identity continuity does not imply semantic sameness. A new ObjectRevision can remain under the same object_id, while its distinct target and lineage make the semantic change visible. Concurrent branches remain plural until an explicit merge Protocol emits a new successor target.

## 5. First-class variable Protocol Model

A Protocol is itself stored as an Object with immutable ProtocolRevision targets. It can be read, related to other Objects, viewed in context, assigned statuses by other Protocols, and superseded. A Protocol cannot interpretively overwrite its own admitted definition while running.

ProtocolRevision contains:

- protocol_id and revision_digest;
- kernel_compatibility range;
- declaration schema version;
- domain type table and schema digests;
- selector: total, side-effect-free predicate over routable kernel metadata;
- input ports for Objects, Relations, Events, contexts, and Persona references;
- output ports and their domain schemas;
- state schema, initial state constructor, and migration declarations;
- transition table or verified typed bytecode;
- Relation and Event subscriptions;
- view declarations with dependency signatures;
- status namespaces and emission rules;
- Persona policy: invariant, partitioned, shared-read-only, or prohibited;
- required capabilities, allowed effects, quotas, and determinism declaration;
- admission probes and declared unsupported input classes;
- successor and compatibility lineage;
- human documentation, issuer provenance, and package signature.

ProtocolInstance is separate from ProtocolRevision:

- instance_id;
- pinned ProtocolRef;
- bound Object ids or query scope;
- Persona partition;
- ContextKey;
- runtime state revision;
- input cursors;
- lease and quota counters;
- health and refusal state.

Variability is controlled by revision pinning. Different Object instances can bind different Protocol revisions; one Object can participate in several heterogeneous Protocols simultaneously; and a session can switch Protocol stacks. Every result identifies the exact ordered stack and revision digests. There is no ambient latest Protocol lookup during an execution transaction.

Because Protocol is an Object, meta-Protocols may lint, compare, document, test, status, or propose successors to Protocol definitions. They do not receive privileged access merely by being meta-Protocols; the same admission and effect rules apply.

## 6. Interpreter/VM execution model

The VM executes a compact typed intermediate representation rather than arbitrary host-language code. The instruction families are:

- pure values: construct, project, match, compare, and bounded collection operations;
- kernel queries: snapshot reads over declared indexes;
- transition logic: finite state-machine or bounded dataflow operations;
- effect construction: build one of the four typed effect requests;
- control: bounded branch, bounded iteration over a materialized finite input, emit, refuse, and halt.

An activation is:

Activation = (ProtocolRef, InstanceId, PersonaRef, ContextKey, EvidenceCutoff, InputEnvelope, RuntimeRevision, CapabilitySet, Budget).

Execution has six phases:

1. Resolve all revision-pinned references and verify digests.
2. Freeze an evidence cutoff and load the exact runtime revision.
3. Type-check the input envelope against the admitted input port.
4. Run pure instructions and construct an ordered effect journal.
5. Validate the whole journal against capabilities, quotas, target revisions, and effect-specific invariants.
6. Commit atomically where a shared transaction domain exists; otherwise write a prepare receipt and use idempotent, compensatable adapters.

The result is one of Committed, NoOp, Refused, BudgetExceeded, TypeFault, Conflict, AdapterPending, or HostFault. Each result carries an execution receipt containing input digests, cutoff, instruction digest, state before and after, requested and committed effects, dependency set, resource use, and refusal or failure codes.

An undeclared source of nondeterminism is a verifier error. Time, randomness, external responses, and model inference are permitted only through typed input ports whose realized values are captured in the receipt. Replay means replay against those captured inputs, not recreation of an external world.

## 7. Bidirectional Object↔Protocol interaction

Object to Protocol flow:

- Object routing metadata is evaluated by the Protocol's pure selector.
- The VM supplies a snapshot of authorized evidence and the pinned ObjectRevision.
- matching Relation or Event envelopes trigger transitions;
- the ContextKey and PersonaRef select the correct view and state partition;
- lineage and prior receipts allow a Protocol to reason about explicit revision history.

Protocol to Object flow:

- READ effects acquire no mutation right and return dependency-tagged values.
- VIEW_MATERIALIZATION effects create replaceable derived artifacts keyed by full context.
- RUNTIME_STATE_MUTATION effects advance only the ProtocolInstance state partition.
- MODEL_SEMANTIC_MUTATION effects may create a new ObjectRevision or ProtocolRevision target, provided a lineage edge to the prior target is included and policy permits it.

A Protocol may never smuggle one flow into another. For example, a view cache entry is not evidence, runtime state is not an Object attribute, and a derived label is not a semantic revision unless emitted through MODEL_SEMANTIC_MUTATION. Conversely, creating a semantic successor does not silently reset runtime state; a separately declared transition or migration is required.

Feedback loops are legal only when declared. A Protocol-generated Event carries producer ProtocolRef, origin activation id, causal depth, and idempotency key. Subscription admission sets a maximum causal depth or proves a decreasing measure. The scheduler refuses an activation that would exceed the declared loop bound.

## 8. Relation and Event responsiveness

Subscriptions are typed declarations, not broad callbacks. Each contains:

- Relation or Event type/schema digest;
- endpoint or subject role filters;
- transition entry point;
- delivery partition key;
- ordering need: ingestion order, per-Object order, or no order;
- late-arrival policy;
- duplicate policy and idempotency key expression;
- maximum fan-out and processing budget;
- view invalidation and status recomputation dependencies.

All Relation lifecycle changes are normalized into Events. A new Relation assertion can therefore both update the Relation index and trigger Protocol instances. Event responsiveness follows these rules:

- ingestion sequence determines scheduler order inside a partition;
- duplicates may be delivered, so committed transitions must be idempotent by activation key;
- gaps pause an instance that requires order;
- out-of-order event time is retained and handled by the declared late-arrival policy;
- a retraction or supersession triggers dependency invalidation rather than erasure;
- fan-out is bounded, with overflow recorded as refusal or deferred work;
- one failing subscriber cannot block unrelated subscribers.

For deterministic Protocols, the tuple of pinned definitions, frozen cutoff, ordered envelopes, and prior runtime revision must yield the same effect journal. A replay comparator checks this property.

Relation responsiveness includes endpoint revision change. A subscription may choose stable Object identity, exact RevisionRef, or follow-successor behavior. Follow-successor is never implicit, because it can alter interpretation when an endpoint changes semantics.

## 9. Admission, sandboxing, and refusal for heterogeneous or unseen Protocols

Unseen Protocols are evaluated by form and declared capability, not by a registry of familiar domain names. Admission is a staged decision:

1. Package integrity: digest, signature policy, complete manifest, immutable dependencies.
2. Kernel compatibility: supported host types, opcodes, and schema declaration version.
3. Static typing: input/output/state/effect types and total selector.
4. Capability closure: every possible effect is declared and allowed by host policy.
5. Resource analysis: bounded loops, collection sizes, fan-out, state size, and activation budget.
6. Isolation analysis: runtime keys, Persona partitions, context keys, and external adapter boundaries.
7. Semantic-mutation shape: fresh successor target plus valid lineage construction on every path.
8. Determinism check: claimed determinism has no uncaptured nondeterministic inputs.
9. Fixture probes: host-supplied malformed, duplicate, late, unauthorized, and rollback cases.
10. Policy decision: ADMIT, ADMIT_SANDBOXED, or REFUSE with machine-readable reasons.

ADMIT_SANDBOXED can remove MODEL_SEMANTIC_MUTATION, restrict evidence fields, lower quotas, and route views to a temporary namespace. It is still admission under an explicit reduced capability set, not silent partial execution.

Mandatory refusal reasons include:

- unknown or dynamically generated opcode;
- missing or cyclic schema dependency;
- unrestricted native, network, filesystem, reflection, or code-loading request;
- unbounded iteration, recursion, fan-out, or state;
- selector with effects or non-total behavior;
- effect kind ambiguity;
- in-place semantic overwrite;
- absent successor lineage;
- undeclared context or Persona dependence;
- inability to isolate Persona state;
- requirement for a stronger delivery guarantee than the host provides;
- unverifiable adapter authority;
- kernel version or type incompatibility.

Refusal is an ordinary result. It records the stage, code, evidence, and retry condition. The host does not guess missing semantics or downgrade a prohibited semantic mutation into a view.

## 10. Contextual views and materialization

A View is a contextual projection, never the Object itself. View identity is keyed by:

ViewKey = digest(ObjectRevision, ProtocolStack, PersonaRef, ContextKey, EvidenceCutoffPolicy, ViewName, ViewSchema, LocalePolicy).

Context dimensions are named and typed. The minimum context envelope includes:

- observation or evidence cutoff;
- Protocol stack and exact revisions;
- Persona;
- jurisdiction or policy domain when used;
- temporal frame;
- audience/access scope;
- locale and presentation preferences;
- experiment or scenario identifier;
- caller-supplied domain dimensions.

VIEW_MATERIALIZATION writes:

- the derived payload;
- complete ViewKey;
- input dependency EvidenceRefs and RevisionRefs;
- producing activation receipt;
- creation time and expiry policy;
- completeness marker;
- access label.

Materializations are disposable and recomputable. They can be invalidated by dependency arrival, retraction, Relation lifecycle Event, successor creation, context change, Protocol successor, or access-policy change. Invalidation marks stale; it does not rewrite history.

Two views of one target may conflict. The kernel preserves both if their keys differ. A comparison or aggregation requires an explicit Protocol whose output carries its own provenance. The VM has no privileged default context beyond host administration metadata.

## 11. Status plurality

Status is modeled as a typed, contextual assertion emitted by a named Protocol revision, not as one mutable field on ObjectRecord.

StatusAssertion:

- status_id;
- subject RevisionRef;
- namespace and status type schema;
- value;
- issuer ProtocolRef;
- PersonaRef or Persona-invariant marker;
- ContextKey;
- grounds and producing receipt;
- validity interval and evidence cutoff;
- precedence rule only within the declaring namespace;
- supersedes or challenges links.

Multiple statuses can coexist:

- operationally_ready under one Protocol;
- review_required under another;
- eligible for Persona A and hidden for Persona B;
- historical at one cutoff and current at another;
- conflicting values in the same namespace on separate branches.

The host does not collapse those assertions. If a consumer requires one answer, it must name an aggregation Protocol and conflict policy. Aggregation outputs another StatusAssertion rather than altering its sources. A status used as a transition guard must be pinned by status id or by an explicit resolution query recorded in the activation receipt.

Status lifecycle changes are Events, so subscribers can respond without polling. Expiry produces an expiry Event but does not delete the assertion.

## 12. Multi-Persona model

Persona is a first-class, revisioned policy-and-perspective object, not an informal prompt string.

PersonaRevision declares:

- Persona identity and revision;
- allowed evidence scopes and redaction rules;
- vocabulary and presentation preferences;
- goals or task lens;
- permitted Protocols and effects;
- runtime sharing mode;
- status namespaces visible or writable;
- delegation and authority attestations;
- switching entry and exit hooks;
- invariants that must survive switching.

One Object can be engaged through several Personas concurrently. Each activation names exactly one active Persona. Cross-Persona aggregation requires a specifically admitted bridge Protocol and capability; it is never an incidental read.

Protocol Persona modes:

- invariant: behavior and runtime are independent of Persona, verified by declaration and tests;
- partitioned: runtime and materializations are keyed by PersonaRef;
- shared-read-only: common runtime may be read but Persona-local overlays hold all writes;
- prohibited: Protocol cannot execute in Persona sessions.

Persona affects authorization, context, state partition, status interpretation, and view output. It does not alter prior evidence. A Persona claim of authority is treated as evidence until a trusted policy adapter validates it.

## 13. Switching fidelity

A switch is an explicit SwitchEvent from (Persona A, ProtocolStack A, Context A) to (Persona B, ProtocolStack B, Context B), with a switch transaction and receipt. Fidelity means preserving declared continuity while preventing undeclared carryover.

Switch procedure:

1. Stop admitting new activations to the source session epoch.
2. Drain or cancel in-flight work according to each Protocol's declared boundary.
3. Freeze evidence cutoff, input cursors, pinned revisions, source ContextKey, and runtime revisions.
4. Execute declared exit hooks using only their admitted effects.
5. Snapshot invariant state and seal Persona-partitioned state under the source key.
6. Resolve and admit the destination stack and Persona revision.
7. Construct destination partitions; migrate only fields named in a typed migration declaration.
8. Execute entry hooks and materialize destination views.
9. Increment session epoch and emit a SwitchReceipt.

The receipt records preserved, reset, redacted, migrated, and refused fields. No field is inherited merely because it has the same name.

Required fidelity properties:

- isolation: destination reads cannot access source-local state without a bridge capability;
- pin fidelity: returning to an unchanged source uses the same Protocol and Persona revisions unless a successor is explicitly selected;
- cursor fidelity: no Event is silently skipped; duplicates remain possible and are idempotently handled;
- context fidelity: every materialization uses the destination ViewKey;
- round-trip fidelity: A to B to A with no intervening admitted inputs restores the sealed A state byte-for-byte, excluding monotonic receipt counters;
- branch fidelity: if A changes while inactive through subscribed Events, return performs declared catch-up and records it rather than pretending exact restoration;
- failure atomicity: a failed destination admission leaves the source sealed and resumable.

Switching fidelity is tested with trace comparison, state-partition diffing, dependency-key checks, and adversarial redaction probes. A Protocol that cannot declare its switch boundary or state sharing mode is refused in switchable sessions.

## 14. Typed effect system

Every effect journal entry has an EffectKind, input type, output type, capability, scope, target, expected revision, and idempotency key. The four effect kinds are disjoint.

READ

- Purpose: snapshot query of authorized kernel data or an admitted adapter.
- May change: no persistent model, materialization, or runtime state.
- Required fields: query type, scope, EvidenceCutoff, access capability, dependency capture.
- Result: typed value plus exact dependency references or external attestation.
- Reject when: query is unbounded, scope is ambient, adapter response is untyped, or a read hides a write.

VIEW_MATERIALIZATION

- Purpose: write or invalidate a derived contextual artifact.
- May change: only the view/materialization store under a complete ViewKey.
- Required fields: output schema, ViewKey, dependencies, completeness, expiry, producing receipt.
- Result: MaterializationRef.
- Reject when: key omits Protocol, Persona, context, target revision, or cutoff policy; payload claims canonical object state.

RUNTIME_STATE_MUTATION

- Purpose: advance a ProtocolInstance's operational state.
- May change: only the expected runtime revision inside the declared instance, Persona, context, and session partition.
- Required fields: old revision, typed patch or replacement, new state digest, transition id, activation id.
- Result: RuntimeRevision.
- Reject when: state schema changes without migration, target partition differs, compare-and-swap fails, or state encodes an undeclared semantic Object change.

MODEL_SEMANTIC_MUTATION

- Purpose: change the semantic model of an Object or Protocol.
- May change: only by creating a fresh successor target and appending lineage; the predecessor is immutable.
- Required fields: predecessor RevisionRef, fresh successor target, semantic payload/schema, typed delta, grounds, SuccessorOf or explicit branch/merge lineage, authoring receipt, policy capability.
- Result: new RevisionRef and lineage receipt.
- Reject when: target id/revision is reused, lineage is absent or inconsistent, expected predecessor changed, grounds are inaccessible, or mutation attempts an in-place overwrite.

The verifier computes the maximum effect set reachable from bytecode. Runtime checks then validate concrete targets and revisions. A lower-privilege effect cannot be promoted dynamically. A journal mixing effects commits in the declared order only after whole-journal validation; a semantic successor cannot depend on an uncommitted materialization masquerading as evidence.

## 15. Semantic succession, lineage, branching, and merge

The sole legal form of semantic change is successor target plus lineage. This applies to ordinary Objects, Protocol objects, Persona objects, and other semantic targets.

For a simple step:

- old target remains immutable;
- new target has a fresh revision digest and, where policy requires, a fresh target nonce;
- one SuccessorOf edge names the exact predecessor;
- semantic delta and full resulting payload are both digest-bound;
- grounds and authoring activation are recorded;
- current-head selection is a policy view, not deletion of the old head.

For concurrent change, each writer creates a separate successor branch from the revision it read. Compare-and-swap prevents accidental serialization over a newer head. A merge is a new target with MergedFrom edges to every input head and an explicit merge Protocol. Conflicts that the merge Protocol cannot resolve remain encoded in the merge result or cause refusal.

Protocol semantic change follows the same rule. A ProtocolRevision cannot patch its bytecode, effect declarations, schemas, or selectors in place. Its successor must state compatibility and, if it owns runtime state, a typed migration. Existing instances remain pinned until a separate rebind operation succeeds.

Lineage validation checks:

- all referenced predecessors exist and are immutable;
- successor digest binds payload, schema, grounds, and lineage;
- graph edges do not create ancestry cycles;
- claimed delta reproduces the successor from the predecessor under the named delta schema;
- authoring effect had authority over that target;
- merge inputs match the declared branch set.

Lineage proves an accountable transformation path, not correctness of the new semantics.

## 16. Concrete implementation blueprint

Reference implementation components:

- Registry: content-addressed Protocol, schema, Persona, and adapter packages.
- Admission service: parser, signature checker, type checker, control-flow/effect analyzer, quota analyzer, fixture runner, and policy engine.
- Compiler: lowers the declarative package to canonical typed IR and produces a verification certificate tied to its digest.
- VM workers: deterministic interpreters with no ambient filesystem, network, clock, randomness, or dynamic loading.
- Evidence store: append-only log plus subject, Relation endpoint, Event type, time, provenance, and access indexes.
- Revision store: immutable ObjectRevision payloads and a lineage graph.
- Runtime store: compare-and-swap rows keyed by instance, Persona, ContextKey, session epoch, and ProtocolRef.
- View store: content-addressed payloads indexed by full ViewKey and dependency reverse indexes.
- Scheduler: partitioned Event dispatch, gap detection, retries, idempotency, fan-out limits, and causal-depth enforcement.
- Audit store: admission, execution, switch, refusal, adapter, and commit receipts.

Suggested implementation boundary is a memory-safe host such as Rust, with Protocol IR encoded canonically in a schema language that has deterministic serialization. PostgreSQL can provide the first transactional implementation for evidence metadata, revision heads, runtime compare-and-swap, materialization metadata, and an outbox; payload blobs may be content-addressed. A production event log can later replace the outbox without changing VM semantics.

Core host interfaces:

- admit(package, host_policy) -> AdmissionDecision;
- activate(instance, input, persona, context, cutoff) -> ExecutionResult;
- switch(session, destination_spec) -> SwitchResult;
- replay(execution_receipt) -> ReplayComparison;
- explain(receipt_or_ref) -> dependency and lineage graph;
- invalidate(evidence_or_revision_ref) -> bounded invalidation plan.

Commit strategy:

- lock or compare-and-swap the expected runtime and semantic heads;
- validate the complete effect journal;
- append evidence-derived receipts and new revisions;
- advance runtime state;
- write view entries and invalidation markers;
- append scheduler outbox Events;
- commit once;
- deliver asynchronously with activation-id idempotency.

External adapters cannot participate in this atomic commit. Their calls use prepare, signed request digest, idempotency key, bounded timeout, response attestation, and explicit AdapterPending or compensation state. A Protocol requiring irreversible external atomicity is unsupported unless a trusted adapter provides that contract.

Minimum conformance suite:

- type and effect negative corpus;
- deterministic replay corpus;
- Relation/Event duplicate, gap, late, retraction, and fan-out tests;
- multi-Protocol conflict and status-plurality tests;
- Persona isolation and A-to-B-to-A switch tests;
- successor/branch/merge lineage property tests;
- crash points before and after every commit boundary;
- hostile unseen packages targeting every refusal rule.

## 17. Invariants, failure semantics, falsification, and unsupported Protocols

Normative invariants of this candidate proposal:

- K1 — Evidence immutability: committed evidence is never overwritten or deleted by a Protocol.
- K2 — Revision immutability: semantic payload at a RevisionRef never changes.
- K3 — Semantic succession: every semantic change creates a fresh successor target and lineage.
- K4 — Effect separation: view and runtime writes cannot become semantic changes by convention.
- K5 — Revision pinning: every activation and output identifies exact Protocol, Persona, and target revisions.
- K6 — Context completeness: contextual results carry a complete ContextKey and evidence-cutoff policy.
- K7 — Status plurality: the host stores conflicting statuses without implicit collapse.
- K8 — Persona isolation: Persona-local state and views are partitioned, with explicit bridge authority required.
- K9 — Receipt completeness: every committed or refused activation is auditable from digest-bound inputs and decisions.
- K10 — Admission closure: executed instructions and effects are a subset of the admitted certificate.
- K11 — Bounded response: subscriptions have finite fan-out, work, state, and causal-depth limits.
- K12 — No universal-semantics claim: kernel records and Protocol outputs remain attributed assertions, not host-declared truth.

Failure semantics:

- malformed input is Refused before transition;
- a type or capability fault commits no journal entry except a failure receipt;
- compare-and-swap conflict retries from a new snapshot only if the Protocol declares retry safety;
- budget exhaustion aborts the activation and preserves the prior runtime revision;
- adapter uncertainty becomes AdapterPending, never assumed success;
- partial distributed side effects are represented by explicit compensation state;
- poison Events are quarantined per subscriber, not removed from the log;
- materialization failure cannot corrupt semantic targets;
- invalid lineage rejects the entire semantic mutation.

Falsification criteria: N07 is falsified as specified if a conforming implementation demonstrates any of the following under its stated host assumptions:

- an admitted Protocol changes the semantic content reachable at an existing RevisionRef;
- two executions with identical deterministic activation tuples yield different journals;
- switching allows an unauthorized destination Persona to read source-local state;
- a view or runtime effect changes Object semantics without a successor lineage receipt;
- an activation executes an effect outside its admission certificate;
- retraction dependency invalidation cannot identify every materialization whose declared dependencies include the retracted evidence;
- an unknown package bypasses refusal with an unbounded loop or ambient capability;
- a failed atomic local transaction advances only a subset of runtime, revision, view, and outbox state;
- status conflict is silently collapsed without a named aggregation Protocol;
- an A-to-B-to-A switch with no intervening inputs fails the stated round-trip property outside documented monotonic metadata.

Protocols explicitly unsupported by N07:

- unrestricted native-code, self-modifying, reflective, or dynamically code-generating Protocols;
- Protocols whose input/output/effect types cannot be declared;
- unbounded recursion, iteration, fan-out, state, or causal feedback;
- Protocols requiring global instantaneous knowledge or universal closed-world truth;
- Protocols requiring distributed exactly-once or irreversible cross-system atomicity absent a trusted adapter;
- Protocols that require in-place semantic mutation or lineage erasure;
- Protocols with undeclared dependence on wall clock, randomness, external model output, or ambient context;
- Protocols that cannot isolate or explicitly prohibit multi-Persona execution;
- Protocols whose semantics require the host to infer domain truth from opaque payloads;
- Protocols that demand automatic reconciliation of incompatible status namespaces or ontologies;
- Protocols whose legal, ethical, or physical validity cannot be reduced to the machine admission checks claimed here.

## 18. Global OPEN questions preserved

These questions remain OPEN; this candidate does not resolve them by definition:

- OPEN-01: What is the smallest evidence kernel that remains useful without smuggling in a privileged domain ontology?
- OPEN-02: Which host authority defines admissible schemas, capabilities, and trust roots, and how is that authority contested or replaced?
- OPEN-03: When should an Object retain one stable object_id across radical semantic succession, and when should a new Object identity be created?
- OPEN-04: Can compatibility between heterogeneous Protocols be established compositionally, or must it remain an empirical property of each stack?
