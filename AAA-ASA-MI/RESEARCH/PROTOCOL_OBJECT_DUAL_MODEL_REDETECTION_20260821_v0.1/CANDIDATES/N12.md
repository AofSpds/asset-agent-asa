# 1. Status, Scope, and Claim Boundary

N12 is a finite reference design for an Object Model and a first-class, variable
Protocol Model joined by contextual, bidirectional interaction. It is a frozen
proposal, not a standard, proof, implementation report, ranking, or claim of
universal protocol coverage. `NOT_VALIDATED` means that the examples below are
executable specifications to build and test; no conformance result is asserted.

The candidate fixes one bounded kernel:

```
materialize : ObjectSnapshot × ProtocolValue × Context × Persona -> ViewOutcome
planWrite   : ObjectSnapshot × ProtocolValue × Context × Persona × ViewDelta
              -> WriteOutcome<TypedPatchBundle>
apply       : ObjectSnapshot × CommittedPatchBatch -> SuccessorOutcome
```

Interaction is bidirectional only when an admitted optic supplies a write
direction. A read-only projection is not mislabeled as a lens. Partiality,
loss, ambiguity, refusal, and lack of proof remain visible values.

Out of scope for this proposal are universal schema inference, arbitrary remote
code execution, and an assertion that every heterogeneous protocol can be made
compatible. Section 18 records unsupported cases and unresolved questions.

# 2. Design Commitments and Non-Goals

N12 makes the following bounded commitments:

1. An object snapshot and a protocol are separate versioned values. A protocol
   may be selected, replaced, or refused without rewriting object identity.
2. Materialization is a function of an explicit immutable context snapshot and
   persona; neither is ambient process state.
3. A permitted write is planned as a typed patch, recorded in a plural ledger,
   checked, and only then applied.
4. Optic laws are conditional obligations with machine-readable reports. A
   lossy or partial optic carries a loss certificate rather than borrowing the
   laws of a total lens.
5. Relation changes and events invalidate declared dependencies and can trigger
   re-materialization. They do not silently authorize semantic writes.
6. Multiple valid views and multiple valid write plans remain plural until an
   explicit selector chooses one.
7. Persona switching preserves exact source identity and reports every declared
   stable field as preserved, transformed, hidden, or failed.

N12 does not make protocol families mandatory. `familyHint` is optional
metadata and never an admission shortcut. N12 does not use last-write-wins as a
general conflict policy, does not equate omission with deletion, and does not
turn `UNKNOWN`, `CONFLICT`, `NOT_PROVEN`, or `OUT_OF_SCOPE` into false.

# 3. Core Vocabulary and Finite Types

The reference kernel uses the following closed wire vocabulary. Implementations
may extend it only through the admission path in Section 11.

```ts
type EntityId = string;       // stable semantic entity key
type SnapshotId = string;     // content-addressed exact snapshot key
type LineageId = string;
type ProtocolId = string;
type ProtocolVersion = string;
type ContextId = string;
type PersonaId = string;
type PatchId = string;
type BatchId = string;
type EventId = string;
type RelationId = string;
type Digest = `sha256:${string}`;

type ExactObjectIdentity = {
  entityId: EntityId;
  snapshotId: SnapshotId;
};

type Knowledge<T> =
  | { tag: "KNOWN"; value: T; evidence: EvidenceRef[] }
  | { tag: "UNKNOWN"; reason: string; sought: string[] }
  | { tag: "CONFLICT"; candidates: T[]; evidence: EvidenceRef[][] }
  | { tag: "NOT_PROVEN"; proposition: string; attemptedChecks: string[] }
  | { tag: "OUT_OF_SCOPE"; boundary: string };

type Plural<T> =
  | { tag: "ONE"; value: T }
  | { tag: "MULTIPLE_VALID"; values: NonEmpty<T>; discriminator?: string }
  | Knowledge<never>;
```

`MULTIPLE_VALID` means that at least two candidates pass the currently declared
constraints. `CONFLICT` means evidence supports incompatible claims. The two
states are not interchangeable. `NOT_PROVEN` concerns a proposition or law;
`UNKNOWN` concerns missing value knowledge; `OUT_OF_SCOPE` names a declared
boundary.

Every externally meaningful value carries a provenance reference. A provenance
reference names a source digest, observation time, producer, and applicable
context. Absence of a reference yields `UNKNOWN`, not an invented default.

# 4. Object Model

An object is addressed through immutable snapshots:

```ts
type Cell<T> = {
  schema: string;
  value: Knowledge<T>;
  cellDigest: Digest;
  provenance: EvidenceRef[];
};

type RelationEdge = {
  relationId: RelationId;
  kind: string;
  from: ExactObjectIdentity;
  to: Knowledge<ExactObjectIdentity>;
  attributes: Record<string, Cell<unknown>>;
  validDuring?: { from: string; until?: string };
  edgeDigest: Digest;
};

type ObjectEvent = {
  eventId: EventId;
  kind: string;
  subject: ExactObjectIdentity;
  sequence: number;
  observedAt: string;
  payload: Knowledge<unknown>;
  causation?: EventId;
  eventDigest: Digest;
};

type ObjectSnapshot = {
  exact: ExactObjectIdentity;
  lineageId: LineageId;
  revision: number;
  parents: ExactObjectIdentity[]; // zero for a root; two or more for a merge
  facets: Record<string, Cell<unknown>>;
  relations: Record<RelationId, RelationEdge>;
  eventCursor: number;
  schemaSet: string[];
  semanticDigest: Digest;
};
```

`entityId` denotes continuity chosen by the object authority. `snapshotId`
denotes one exact immutable state. The pair is exact identity; neither member
may be dropped from a contact, relation endpoint, cache key, or patch
precondition. Relations are objects with identity and provenance rather than
untyped embedded labels. Events are ordered per declared source cursor; N12
does not infer a global order across sources.

A facet can be unknown or conflicted independently of the containing snapshot.
Materialization preserves that state unless the selected protocol explicitly
renders an epistemic marker. A missing path and a known null are distinct cells.

# 5. First-Class Variable Protocol Model

A protocol is data with exact version and digest, not a compile-time enum or an
object-owned method table:

```ts
type ProtocolKey = {
  protocolId: ProtocolId;
  version: ProtocolVersion;
  manifestDigest: Digest;
};

type ProtocolValue = {
  key: ProtocolKey;
  wireVersion: "n12-wire/1";
  familyHint?: string;
  inputSchemas: string[];
  contextSchema: string;
  personas: PersonaContract[];
  viewSchema: string;
  optics: OpticDeclaration[];
  relationSubscriptions: DependencyDeclaration[];
  eventSubscriptions: DependencyDeclaration[];
  effects: ("READ" | "VIEW" | "RUNTIME_MUTATION" | "SEMANTIC_MUTATION")[];
  admissionRequirements: CapabilityRequirement[];
  normalizers: NormalizerDeclaration[];
  lawClaims: LawClaim[];
  signature: Knowledge<SignatureRecord>;
};

type ProtocolSlot = {
  requested: Knowledge<ProtocolKey>;
  resolved: Knowledge<ProtocolValue>;
  admission?: AdmissionCertificate | Refusal;
};
```

The active protocol is supplied to each contact through `ProtocolSlot`. A
session may hold several admitted slots and switch between exact keys. Caches
are keyed by `(ExactObjectIdentity, ProtocolKey, ContextId, PersonaId,
operationMode)`; a protocol switch cannot reuse a view under a different key.

Protocol equivalence is not inferred from matching names. An adapter is itself
versioned data with a digest, input/output protocol keys, declared losses, and
law reports. An absent exact protocol version yields `UNKNOWN` or refusal; it
does not fall forward to "latest."

# 6. Context Model

Context is immutable, hash-addressed input:

```ts
type Context = {
  contextId: ContextId;
  contextDigest: Digest;
  capturedAt: string;
  actor: string;
  personaId: PersonaId;
  purpose: string;
  locale: string;
  permissions: string[];
  relationWindow: { asOf: string; kinds: string[] };
  eventWindow: { afterCursor: number; throughCursor: number };
  runtimeNamespace: string;
  uncertaintyPolicy: "PRESERVE" | "REQUIRE_KNOWN";
  deterministicSeed?: string;
  variables: Record<string, Knowledge<unknown>>;
};
```

Materialization records the `contextDigest` in its receipt. Write planning must
use that same digest or explicitly rebase through a new read. If permissions,
persona, relation/event windows, or relevant variables changed, the planner
returns `CONTEXT_DRIFT`; it does not assume that the old view still denotes the
same source paths.

Contextual values are not copied into semantic facets unless a semantic optic
declares such a write and the persona is authorized. Time, locale, and purpose
are therefore dependencies, not secret mutable globals. A missing dependency
produces `UNKNOWN_CONTEXT_VALUE` or `OUT_OF_SCOPE_CONTEXT`, according to the
protocol declaration.

# 7. Typed Patch Algebra and Plural Patch Ledger

The algebra is finite and type-directed:

```ts
type TypedPath<A> = { objectSchema: string; path: string; valueSchema: string };

type Patch<A> = {
  patchId: PatchId;
  mode: "RUNTIME_MUTATION" | "SEMANTIC_MUTATION";
  target: ExactObjectIdentity;
  op:
    | { tag: "SET"; path: TypedPath<A>; before: Digest; value: A }
    | { tag: "DELETE"; path: TypedPath<A>; before: Digest }
    | { tag: "INSERT"; path: TypedPath<A[]>; index: number; value: A; before: Digest }
    | { tag: "REMOVE"; path: TypedPath<A[]>; index: number; itemDigest: Digest; before: Digest }
    | { tag: "RELATE"; edge: RelationEdge; absentBefore: true }
    | { tag: "UNRELATE"; relationId: RelationId; edgeDigest: Digest }
    | { tag: "EMIT"; event: ObjectEvent };
  protocol: ProtocolKey;
  opticId: string;
  contextDigest: Digest;
  personaId: PersonaId;
  parents: PatchId[];
  evidence: EvidenceRef[];
  inverse?: Patch<unknown>;
};

type TypedPatchBundle =
  | { tag: "SINGLE_PLAN"; patches: NonEmpty<Patch<unknown>> }
  | {
      tag: "ALTERNATIVE_PLANS";
      alternativeGroup: string;
      plans: NonEmpty<NonEmpty<Patch<unknown>>>;
      discriminator: Knowledge<string>;
    };

type LedgerEntry = {
  entryId: string;
  state: "PROPOSED" | "SELECTED" | "COMMITTED" | "REJECTED" | "SUPERSEDED";
  bundle: TypedPatchBundle;
  selectedPlan?: number;
  batchId?: BatchId;
  receiptDigest: Digest;
};
```

There are two append-only partitions: `runtimeLedger` and `semanticLedger`.
Alternative plans occupy one plural entry; selecting one appends a selection
receipt and does not erase the unselected plans. A committed batch contains
patches from exactly one mode and one target base snapshot. Cross-object work is
a transaction proposal whose atomicity must be supplied by a named coordinator;
without one it is `OUT_OF_SCOPE`.

Let `0_S` be the empty patch on schema `S`, and `p ; q` mean checked sequential
composition. The reference checker enforces these conditional laws:

1. **Identity:** `0_S ; p = p = p ; 0_S`.
2. **Typed associativity:** `(p ; q) ; r = p ; (q ; r)` only when each path
   type matches and every recorded `before` digest equals the preceding result.
3. **Type preservation:** applying `Patch<A>` to its declared path either
   produces that path's declared schema or fails atomically.
4. **Locality:** disjoint patches commute only when neither protocol declares a
   shared invariant or dependency between their paths.
5. **Conflict visibility:** overlapping writes with unequal expected digests
   yield `PATCH_PRECONDITION_CONFLICT`; no implicit ordering resolves them.
6. **Conditional inverse:** `p ; inverse(p) = 0_S` only when the before-image is
   retained and neither external event nor normalizer changed the affected cell.

Failed composition is a typed result, not an algebraic element smuggled in as a
no-op. Ledger order is evidence of processing order, not proof of semantic
commutativity.

# 8. Contextual Optics, Round Trips, and Loss Laws

N12 distinguishes total `Lens`, partial `Optional`, variant `Prism`, plural
`Traversal`, and read-only `Getter`. Each declaration names its source/view
schemas and multiplicity.

```ts
type OpticDeclaration = {
  opticId: string;
  kind: "LENS" | "OPTIONAL" | "PRISM" | "TRAVERSAL" | "GETTER";
  sourcePath: string;
  viewPath: string;
  readDependencies: string[];
  writeMode?: "RUNTIME_MUTATION" | "SEMANTIC_MUTATION";
  putPolicy?: "EXACT" | "NORMALIZING" | "ALTERNATIVE";
  loss?: LossDeclaration[];
};

type LossDeclaration = {
  code: "PROJECTION" | "NORMALIZATION" | "MANY_TO_ONE" |
        "IRREVERSIBLE" | "AUTHORITY_FILTER" | "CONTEXT_DEPENDENT";
  affectedPaths: string[];
  witness: string;
};

type LawResult =
  | { tag: "HOLDS_FOR_CASE"; testId: string; receipt: Digest }
  | { tag: "FAILS"; counterexample: string }
  | { tag: "NOT_PROVEN"; attemptedChecks: string[] }
  | { tag: "OUT_OF_SCOPE"; boundary: string };
```

For an admitted optic, define `get_P,C,R(S)` and
`put_P,C,R(S, desiredView)` returning a patch plan. Its obligations are:

- **Get-Put:** if `get(S)=V` is single and known, context is unchanged, and the
  optic claims `EXACT`, then `put(S,V)` must be an empty semantic plan.
- **Put-Get:** if a plan for desired `V'` commits to successor `S'`, then
  `get(S') = normalize(V')`. If normalization is not identity, its exact loss
  declaration must appear in the contact receipt.
- **Put-Put:** two accepted writes may collapse to the latter only for a path
  declared overwriting, with the same context and no intervening dependency
  change. Otherwise the proposal makes no Put-Put claim.
- **Persona round trip:** switching `A -> B -> A` must preserve the
  observational values declared stable for `A`; hidden values are retained in
  the source, not emitted as delete patches.
- **Plural traversal:** a traversal write preserves cardinality and stable item
  keys unless it declares insertion/removal effects. Ambiguous target matching
  returns `MULTIPLE_VALID` plans or `CONFLICT`.

A `Getter` has no `put`; an `Optional` may refuse absent-source creation; a
`Prism` may refuse a mismatched variant. Such behavior is honest partiality,
not a broken total-lens law. Each executed round trip emits a `LawResult`; a
protocol's unexecuted law claim stays `NOT_PROVEN`.

# 9. Bidirectional Interaction and Executable Contact

One contact follows a finite state machine:

```
RECEIVED -> RESOLVED -> ADMITTED -> SNAPSHOTTED -> MATERIALIZED
         -> WRITE_PLANNED? -> VALIDATED? -> LEDGERED? -> APPLIED?
         -> REMATERIALIZED? -> REPORTED
```

Any state can terminate in `REFUSED` or an epistemic outcome. The contact API is:

```ts
type ContactRequest = {
  requestId: string;
  object: ExactObjectIdentity;
  protocol: ProtocolSlot;
  context: Context;
  persona: PersonaId;
  mode: "READ" | "VIEW" | "RUNTIME_MUTATION" | "SEMANTIC_MUTATION";
  viewDelta?: unknown;
  selectedAlternative?: number;
};

type ContactReceipt = {
  requestId: string;
  resolvedObject: Knowledge<ObjectSnapshot>;
  protocolDecision: AdmissionCertificate | Refusal | Knowledge<never>;
  view: Plural<unknown>;
  patchBundle?: Plural<TypedPatchBundle>;
  ledgerEntry?: string;
  successor?: Knowledge<ObjectSnapshot>;
  roundTrips: Record<string, LawResult>;
  losses: LossDeclaration[];
  failures: Failure[];
  receiptDigest: Digest;
};
```

`contact(request)` is executable when object, protocol registry, capability
registry, ledger, and deterministic normalizers are supplied. The executor
must expose the complete receipt. It may not return only a rendered view after
a refusal, conflict, or lossy write.

READ and VIEW stop before a source patch. Mutation modes require explicit
planning, validation, ledger append, application, and re-materialization. A
receipt that lacks one of those stages cannot claim a successful mutation.

# 10. Relation and Event Responsiveness

Protocols declare dependencies as exact selectors:

```ts
type DependencyDeclaration = {
  dependencyId: string;
  source: "RELATION" | "EVENT";
  kinds: string[];
  selector: string;
  affectsViewPaths: string[];
  response: "INVALIDATE" | "REMATERIALIZE" | "PROPOSE_PATCH";
  maxFanout: number;
};
```

When a relation edge changes or an event arrives, the runtime:

1. verifies its exact subject/endpoint identity and digest;
2. deduplicates events by `(source, eventId, eventDigest)`;
3. finds admitted dependency declarations with matching kind and selector;
4. invalidates only their declared cached view paths;
5. creates a new context with the advanced relation/event window;
6. re-materializes and emits a view diff; and
7. if `PROPOSE_PATCH` is declared, creates a proposal that still requires the
   requested mode, persona authority, preconditions, and ledger commitment.

An event never acquires semantic-write authority merely by matching a
subscription. Unknown event kinds are retained as `UNKNOWN` payload evidence
when the manifest permits opaque events; otherwise admission or processing is
refused with `UNSUPPORTED_EVENT_KIND`. A relation with an unresolved endpoint
can render an unknown target, but cannot be dereferenced or written as though
the endpoint were known.

To prevent unbounded reactions, each declaration fixes `maxFanout`. Exceeding
it yields `REACTION_BUDGET_EXCEEDED`, records the remaining count as unknown,
and emits no partial semantic batch.

# 11. Heterogeneous and Unseen Protocol Admission or Refusal

Admission is structural and explicit; `familyHint` has no authority. The finite
decision procedure is:

1. Parse a manifest under a supported `wireVersion`.
2. verify the exact manifest digest and record signature knowledge;
3. match input/context/view schemas or locate a named versioned adapter;
4. negotiate requested operation mode against declared effects and runtime
   capabilities;
5. validate optic kinds, typed paths, deterministic normalizers, dependencies,
   fanout bounds, and persona contracts;
6. reject undeclared network, storage, clock, randomness, or code effects;
7. emit one signed admission certificate or one typed refusal.

```ts
type AdmissionCertificate = {
  tag: "ADMITTED_EXACT" | "ADMITTED_ADAPTER" | "ADMITTED_SANDBOX";
  protocol: ProtocolKey;
  adapter?: { key: string; digest: Digest; losses: LossDeclaration[] };
  grantedModes: ("READ" | "VIEW" | "RUNTIME_MUTATION" | "SEMANTIC_MUTATION")[];
  capabilityDigest: Digest;
  checkedAt: string;
};

type Refusal = {
  tag: "REFUSED";
  code:
    | "MALFORMED_MANIFEST" | "UNSUPPORTED_WIRE_VERSION"
    | "DIGEST_MISMATCH" | "SIGNATURE_REQUIRED"
    | "UNSUPPORTED_SCHEMA" | "MISSING_ADAPTER"
    | "UNSUPPORTED_OPTIC" | "UNDECLARED_EFFECT"
    | "MODE_NOT_GRANTED" | "PERSONA_NOT_GRANTED"
    | "NONDETERMINISTIC_NORMALIZER" | "UNBOUNDED_REACTION"
    | "UNSUPPORTED_EVENT_KIND" | "UNSUPPORTED_RELATION_KIND";
  protocol: Knowledge<ProtocolKey>;
  detail: string;
  retryWith?: string[];
};
```

An unseen protocol can receive `ADMITTED_SANDBOX` if its manifest uses only the
closed wire vocabulary, its schema/optic/effect checks pass, and sandbox limits
are finite. "Unseen" does not imply trusted, compatible, or refused. A protocol
requiring an unsupported optic or effect is refused even if its family label is
familiar. Adapter admission surfaces adapter losses in every receipt.

# 12. Epistemic Honesty and Multiple-Valid Views

The renderer preserves epistemic state at the smallest affected view path.
When a whole view cannot be formed, `ViewOutcome` itself carries the state:

```ts
type ViewOutcome =
  | { tag: "SINGLE"; view: unknown; receipt: Digest }
  | { tag: "MULTIPLE_VALID"; views: NonEmpty<unknown>; reason: string }
  | { tag: "UNKNOWN"; missing: string[]; partialView?: unknown }
  | { tag: "CONFLICT"; claims: unknown[]; partialView?: unknown }
  | { tag: "NOT_PROVEN"; proposition: string; candidateView?: unknown }
  | { tag: "OUT_OF_SCOPE"; boundary: string };
```

The protocol may label or arrange these states but may not coerce them to a
known scalar. A policy that requires known values converts an unknown result to
a typed refusal, not to a default. Defaults are permitted only as visibly
synthetic view values with provenance `protocol-default`; they are never source
facts and cannot be written back without a fresh, authorized edit.

If locale, persona, or a prism produces several equally valid renderings, the
receipt returns `MULTIPLE_VALID` plus a discriminator if one exists. If the
discriminator is unknown, no choice is applied. Corresponding write plans remain
in an `ALTERNATIVE_PLANS` ledger entry. A later selection references the exact
entry and index; it does not retroactively claim the alternatives were false.

Evidence updates can turn `UNKNOWN` into `KNOWN`, `KNOWN` into `CONFLICT`, or a
plural set into one selected presentation. Each transition creates a new
context or object snapshot as appropriate and keeps the earlier receipt.

# 13. Multi-Persona Operation and Switching Fidelity

A persona is a protocol-scoped contract, not a replacement identity:

```ts
type PersonaContract = {
  personaId: PersonaId;
  readableViewPaths: string[];
  writableViewPaths: string[];
  stableAcrossSwitch: string[];
  allowedModes: ("READ" | "VIEW" | "RUNTIME_MUTATION" | "SEMANTIC_MUTATION")[];
  redactions: { path: string; marker: "HIDDEN" | "OUT_OF_SCOPE" }[];
};

type SwitchFieldResult =
  | { tag: "PRESERVED"; beforeDigest: Digest; afterDigest: Digest }
  | { tag: "TRANSFORMED"; rule: string; loss?: LossDeclaration }
  | { tag: "HIDDEN"; retainedSourceDigest: Digest }
  | { tag: "MULTIPLE_VALID"; candidateDigests: Digest[] }
  | { tag: "UNKNOWN"; reason: string }
  | { tag: "CONFLICT"; reason: string }
  | { tag: "NOT_PROVEN"; missingTest: string }
  | { tag: "OUT_OF_SCOPE"; boundary: string };
```

Switching persona creates a new context and materialization receipt while
retaining exact object and protocol keys. A switch report covers each
`stableAcrossSwitch` path. The `A -> B -> A` check compares observational
digests under A. Values hidden from B stay in the source and caches protected
for A; B's omission does not generate deletion.

If B semantically writes an authorized shared source path, returning to A shows
the successor's value rather than pretending fidelity to the obsolete snapshot.
The report labels this `TRANSFORMED` and references the committed batch. If two
personas propose concurrent edits from the same base, both ledger entries are
retained; overlap yields conflict during selection or rebase.

Persona switching never upgrades permissions. A protocol switch performed at
the same time is reported as two operations with two exact protocol keys so
that persona fidelity is not falsely attributed across incompatible views.

# 14. READ, VIEW, RUNTIME_MUTATION, and SEMANTIC_MUTATION

The four modes have disjoint effect ceilings:

| Mode | Permitted result | Ledger | Creates semantic successor |
|---|---|---|---|
| `READ` | resolve object cells, relations, events, and epistemic state | contact receipt only | no |
| `VIEW` | contextual materialization and cache entries | view receipt only | no |
| `RUNTIME_MUTATION` | session/cache/cursor state inside `runtimeNamespace` | runtime ledger | no |
| `SEMANTIC_MUTATION` | authorized facet/relation/event semantic patch | semantic ledger | yes |

The request mode is an upper bound. A protocol, persona, or capability can
reduce it, never increase it. READ does not execute a protocol normalizer with
effects. VIEW may compute deterministic derived values but may not change source
or runtime state. RUNTIME_MUTATION targets a typed runtime schema, has a stated
expiry or retention policy, and cannot be replayed as semantic history.

A semantic batch cannot contain runtime patches. A contact needing both first
commits (or refuses) a runtime batch, then uses its resulting runtime receipt as
explicit context for a separate semantic proposal. This prevents transient
state from leaking into lineage without provenance.

Dry-run semantic planning returns proposed patches and law checks but no
`COMMITTED` entry and no successor. A UI label such as "preview" cannot alter
this mode boundary.

# 15. Successor Exact Identity and Lineage

Applying a semantic batch to base `(entityId=E, snapshotId=S0)` creates exactly
one immutable successor record for that application:

```ts
type LineageReceipt = {
  lineageId: LineageId;
  entityId: EntityId;
  predecessor: ExactObjectIdentity;
  successor: ExactObjectIdentity;
  batchId: BatchId;
  patchIds: NonEmpty<PatchId>;
  protocol: ProtocolKey;
  contextDigest: Digest;
  personaId: PersonaId;
  semanticDigestBefore: Digest;
  semanticDigestAfter: Digest;
  createdAt: string;
  receiptDigest: Digest;
};
```

For an in-line semantic update, `entityId` and `lineageId` remain equal to the
base values, `revision` advances by one, `parents=[base.exact]`, and
`snapshotId=hash(canonical successor content)`. Reusing S0 for changed content
is `IDENTITY_COLLISION`. The successor is not "the same exact object" as its
predecessor; continuity is stated through entity and lineage fields.

Concurrent committed branches from S0 have distinct snapshot IDs and the same
predecessor. A merge has a fresh snapshot ID and lists each exact parent; it
does not fabricate a linear predecessor. A change that reifies a different
semantic entity receives a new `entityId` and lineage receipt with an explicit
`DERIVED_FROM` relation; N12 does not silently carry identity across it.

Runtime mutation, view change, protocol switch, persona switch, and context
refresh create receipts but no semantic successor. Replay verifies base exact
identity, patch order, result digest, and lineage receipt. Any mismatch stops
with a failure rather than approximating the intended successor.

# 16. Invariants and Typed Failure Semantics

The candidate exposes these checkable invariants:

- **I01 Exact targeting:** every patch target equals the base exact identity.
- **I02 Immutable snapshots:** a known snapshot ID maps to one semantic digest.
- **I03 Typed paths:** patch value schema equals the path schema.
- **I04 Preconditions:** each before-image digest matches at application time.
- **I05 Mode separation:** a batch contains one mode and uses its matching ledger.
- **I06 Admission:** every executing optic belongs to the admitted manifest digest.
- **I07 Context binding:** write context equals or explicitly rebases the view context.
- **I08 Persona authority:** written view paths and mode are granted to the persona.
- **I09 Loss disclosure:** observed or declared non-identity conversion has a receipt loss.
- **I10 Epistemic preservation:** non-known states are neither coerced nor silently selected.
- **I11 Plural retention:** unselected valid plans remain addressable in ledger history.
- **I12 Event idempotence:** a deduplication key affects a reaction at most once per runtime namespace.
- **I13 Lineage linkage:** each semantic successor references exact parents and committed batch.
- **I14 Switch reporting:** every declared persona-stable path has one switch result.

```ts
type Failure = {
  code:
    | "OBJECT_NOT_FOUND" | "IDENTITY_COLLISION" | "STALE_SNAPSHOT"
    | "TYPE_MISMATCH" | "PATCH_PRECONDITION_CONFLICT"
    | "CONTEXT_DRIFT" | "UNKNOWN_CONTEXT_VALUE"
    | "ADMISSION_REFUSED" | "MODE_VIOLATION" | "PERSONA_VIOLATION"
    | "LOSS_UNDECLARED" | "AMBIGUOUS_TARGET" | "SELECTION_REQUIRED"
    | "LAW_COUNTEREXAMPLE" | "REACTION_BUDGET_EXCEEDED"
    | "LEDGER_MISMATCH" | "LINEAGE_MISMATCH" | "UNSUPPORTED";
  stage: string;
  invariant?: string;
  detail: string;
  retryable: boolean;
  evidence: EvidenceRef[];
};
```

Validation is atomic at batch scope. On failure, no patch in the batch changes
the snapshot, the failure receipt is appended, and proposals remain inspectable.
A validator crash yields `UNKNOWN` application state until ledger and snapshot
digests are reconciled; it is not reported as success or rollback without
evidence.

# 17. Finite Executable Example, Tests, and Falsification

This fixture is deliberately small:

```json
{
  "object": {
    "exact": {"entityId":"person:17","snapshotId":"sha256:S0"},
    "lineageId":"lineage:17","revision":4,"parents":[],
    "facets": {
      "name": {"schema":"string","value":{"tag":"KNOWN","value":"Mira","evidence":["ev:name:1"]},"cellDigest":"sha256:N0","provenance":["ev:name:1"]},
      "preferredName": {"schema":"string?","value":{"tag":"UNKNOWN","reason":"not supplied","sought":["profile"]},"cellDigest":"sha256:P0","provenance":[]}
    },
    "relations": {}, "eventCursor":7,
    "schemaSet":["Person/v1"], "semanticDigest":"sha256:SEM0"
  },
  "protocol": {
    "key":{"protocolId":"compact-card","version":"2.0.0","manifestDigest":"sha256:PC2"},
    "wireVersion":"n12-wire/1","inputSchemas":["Person/v1"],
    "contextSchema":"CardContext/v1","personas":["operator","reviewer"],
    "viewSchema":"Card/v2",
    "optics":[
      {"opticId":"display-name","kind":"LENS","sourcePath":"/facets/name","viewPath":"/displayName","readDependencies":["/facets/name"],"writeMode":"SEMANTIC_MUTATION","putPolicy":"EXACT","loss":[]}
    ],
    "effects":["READ","VIEW","SEMANTIC_MUTATION"]
  }
}
```

Under context `C0` and persona `operator`, VIEW returns
`{"displayName":"Mira"}` plus the exact object/protocol/context receipt. Editing
to `{"displayName":"Mira K."}` plans:

```json
{"tag":"SET","path":{"objectSchema":"Person/v1","path":"/facets/name","valueSchema":"string"},"before":"sha256:N0","value":"Mira K."}
```

After validation and semantic commit `B1`, the successor is
`(person:17, sha256:S1)`, revision 5, parent `(person:17, sha256:S0)`, with the
same lineage ID and a lineage receipt naming B1. Re-materialization must return
`{"displayName":"Mira K."}`. A preferred-name editor may instead validly map a
new alias to `/facets/preferredName` or a declared locale-alias relation; if the
protocol cannot discriminate, it returns two `ALTERNATIVE_PLANS` and commits
neither until selection.

The minimum conformance harness contains these finite cases:

| Test | Stimulus | Required observable result |
|---|---|---|
| T01 | get then put unchanged display name | empty semantic plan; Get-Put `HOLDS_FOR_CASE` |
| T02 | put `Mira K.` then get successor | exact desired view; Put-Get `HOLDS_FOR_CASE` |
| T03 | change name cell digest before apply | `PATCH_PRECONDITION_CONFLICT`; no successor |
| T04 | change locale/context digest before plan | `CONTEXT_DRIFT` or explicit rebase |
| T05 | submit two valid preferred-name mappings | plural ledger entry; `SELECTION_REQUIRED` |
| T06 | switch operator -> reviewer -> operator with no write | stable paths preserved or a field-level failure |
| T07 | hide name from reviewer | source cell retained; no delete patch |
| T08 | matching relation event | bounded invalidation and re-materialization receipt |
| T09 | duplicate same event digest | no second reaction in the runtime namespace |
| T10 | structurally valid unseen read-only manifest | sandbox admission or a typed capability refusal |
| T11 | unseen manifest requests undeclared network effect | `UNDECLARED_EFFECT` refusal |
| T12 | runtime patch presented to semantic ledger | `MODE_VIOLATION` |
| T13 | replay B1 against S1 rather than S0 | `STALE_SNAPSHOT` |
| T14 | claimed exact optic performs normalization | `LOSS_UNDECLARED` and `LAW_COUNTEREXAMPLE` |

N12 is falsified for this kernel if an implementation claiming conformance:

1. commits either alternative in T05 without a recorded selector;
2. reports a successor while a batch precondition failed;
3. reuses a snapshot ID for different canonical semantic content;
4. deletes a source value merely because a persona cannot view it;
5. renders `UNKNOWN` or `CONFLICT` as a known fact without provenance;
6. accepts an unsupported effect because a family name is recognized;
7. reports a total-lens law as proven from an unexecuted declaration; or
8. performs a semantic change with no committed plural-ledger and lineage receipt.

# 18. Unsupported Cases, Falsification Boundary, and Global OPEN Questions

The frozen proposal marks the following as unsupported rather than guessing:

- protocols whose manifests require unbounded or non-sandboxed code execution;
- nondeterministic normalizers without an explicit seed and replay record;
- globally ordered events across independent sources without an ordering service;
- cross-object atomic semantic writes without a named transaction coordinator;
- irreversible external side effects without a declared compensation protocol;
- automatic semantic identity equivalence across forks, imports, or reification;
- proof of lens laws over infinite domains from the finite harness;
- confidential-field noninterference proofs and cryptographic signature validity;
- automatic synthesis of adapters for unseen schemas; and
- write-back through an aggregation when ownership of the source cell is plural
  or unknown.

The following global questions are preserved as **OPEN**. N12 intentionally does
not close them:

1. **OPEN-G1 — Identity authority:** Which authority may declare entity
   continuity or reification across administrative domains, and how is a dispute
   represented without collapsing exact identities?
2. **OPEN-G2 — Protocol trust:** What trust and revocation model should govern
   signed manifests, adapters, capability certificates, and already-issued
   contact receipts?
3. **OPEN-G3 — Law strength:** Which combination of exhaustive checking,
   property testing, proof objects, and runtime monitoring is sufficient to
   upgrade `NOT_PROVEN` for a claimed optic law?
4. **OPEN-G4 — Plural selection:** Who or what may select among multiple-valid
   views or patch plans, and when may that selection be reused in a new context?
5. **OPEN-G5 — Persona equivalence:** What observational equivalence should be
   required when personas use different schemas, redactions, or normalizers?
6. **OPEN-G6 — Distributed mutation:** How should partial commit, compensation,
   and lineage be represented for cross-object or cross-ledger operations?
7. **OPEN-G7 — Event time:** How should late, retracted, or causally incomparable
   events revise materializations without claiming a nonexistent global order?
8. **OPEN-G8 — Context retention:** Which context and evidence fields must be
   retained for replay, and which must be minimized or erased for privacy?
9. **OPEN-G9 — Adapter composition:** Under what checked conditions may adapter
   loss certificates and round-trip claims compose across several protocols?
10. **OPEN-G10 — Conflict governance:** Which domain-specific merge authorities
    may resolve conflicted facts while preserving rejected evidence and branches?

These OPEN items are requirements for later investigation, not defects hidden by
defaults. Until resolved, relevant contacts return `NOT_PROVEN`, `UNKNOWN`,
`CONFLICT`, `OUT_OF_SCOPE`, or a typed refusal as appropriate.
