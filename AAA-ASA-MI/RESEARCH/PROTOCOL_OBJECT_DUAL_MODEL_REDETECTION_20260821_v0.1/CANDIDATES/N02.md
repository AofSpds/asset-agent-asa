N02 is a bounded design candidate, not a universal ontology. It treats addressable relations as the primary operational substrate while leaving relation-versus-event primacy, Protocol ontological status, router separateness, cross-Protocol invariants, the exact mutation boundary, and conflict algebra explicitly open.

## 1. Object Model

An `Object` is an immutable semantic identity plus versioned facets, not a single mutable record:

```text
ObjectID := opaque, stable identifier
ObjectRevision := (ObjectID, RevisionID, ParentRevisionIDs, Facets, Claims, Status)
Facet := (FacetType, Value, Provenance, ValidityInterval, VisibilityLabel)
Claim := (SubjectID, PredicateType, ValueOrObjectID, EvidenceRefs, ClaimStatus)
ClaimStatus := KNOWN | UNKNOWN | CONFLICT | NOT_PROVEN | OUT_OF_SCOPE
```

An object revision may have no materialized body. It may be known only through incident relations, capabilities, or negative knowledge. Identity equality is never inferred from matching names, payloads, or relation neighborhoods. Merging revisions requires a Protocol-authorized rule; otherwise they coexist.

The Object Model fixes only structural obligations: stable identity, provenance, typed facets, explicit epistemic status, and revision lineage. Domain schemas, identity criteria, and lifecycle meanings remain supplied by active Protocols.

## 2. Protocol Model

`Protocol` is a first-class, versioned variable consumed by every operation that interprets or changes the fabric:

```text
ProtocolRef := (ProtocolID, ExactVersion, DefinitionDigest)
Protocol := {
  ref,
  accepted_object_types,
  relation_schemas,
  event_schemas,
  capability_requirements,
  guards,
  routing_rules,
  materializers,
  conflict_policy,
  merge_algebra?,
  status_rules,
  invariants,
  mutation_permissions,
  compatibility_claims,
  unsupported_cases
}
```

No operation may silently use “the current Protocol.” It must carry an exact `ProtocolRef`, or return `UNKNOWN_PROTOCOL`. Protocol definitions are immutable once admitted. Protocol parameters may vary only where the definition declares them as runtime inputs.

Protocol ontological status is deliberately unresolved: a Protocol may be implemented as an object revision, an external signed module, or a distinct metalevel entity. N02 requires only stable addressing, exact versioning, digest binding, inspectable rules, and enforceable authority boundaries. This interface constraint does not settle ontology.

Unseen Protocols are admitted through a quarantine path. A loader can parse a declared interface, verify signatures and capabilities, statically check rule termination where possible, and execute conformance probes. Admission does not imply semantic compatibility. Failure to prove compatibility yields `NOT_PROVEN`, not rejection masquerading as contradiction.

## 3. Object↔Protocol Interaction Contract

The interaction is bidirectional and explicit:

```text
interpret(protocol_ref, object_revision, context) -> ViewResult
authorize(protocol_ref, capability_set, operation, targets, context) -> Decision
apply(protocol_ref, authorized_operation, fabric_snapshot) -> TransitionResult
observe(object_or_relation_change, protocol_ref) -> ActivationCandidates
propose_successor(source_model_ref, exact_target, patch, evidence) -> Proposal
```

Protocols constrain admissible object facets, relations, events, views, and transitions. Objects and relations, in turn, may activate Protocols, supply Protocol parameters, expose counterexamples, or trigger successor proposals. Object data never edits an admitted Protocol in place.

Every result carries:

```text
(protocol_ref, input_snapshot_ids, operation_kind, status,
 provenance, authorizing_capability_ids, output, unresolved_items)
```

The four operation kinds are disjoint:

| Kind | May create a derived view? | May change live state? | May change model semantics? |
|---|---:|---:|---:|
| `READ` | No | No | No |
| `VIEW_MATERIALIZATION` | Yes, as a provenance-bound cache/artifact | No | No |
| `RUNTIME_STATE_MUTATION` | Indirectly, after commit | Yes | No |
| `MODEL_SEMANTIC_MUTATION` | Only through a successor proposal | No in the source model | Creates a new exact target only |

An endpoint must reject operations whose declared kind disagrees with their effects.

## 4. Relation/Event Treatment

The fabric is relation-first operationally:

```text
RelationInstance := {
  RelationID, RelationType, EndpointRoles[Role -> ObjectID],
  Attributes, ProtocolRef, Provenance, CausalContext, Status
}

EventInstance := {
  EventID, EventType, Participants[Role -> ObjectID],
  ObservedAt, EffectiveInterval, Payload, ProtocolRef,
  Provenance, CausalContext, Status
}
```

Relations are addressable, typed, versioned entities. They may be n-ary, temporally qualified, and themselves endpoints of other relations. An event is not automatically reduced to a relation update: it may be an observation, command, attempted transition, completed transition, or counterevidence. Event handlers emit proposed operations; authorization and validation occur before commit.

Responsiveness is subscription-based. A change to an object facet, relation, event log, capability, or context produces activation candidates indexed by affected IDs and types. Handlers must be idempotent under duplicate delivery and must receive causal context. N02 does not decide whether events or relations are metaphysically prior; it only chooses relations as the routing index in this candidate.

## 5. Activation and Routing

Activation proceeds in five bounded stages:

1. Normalize an input envelope without interpreting domain meaning.
2. Match declared selectors against relation types, endpoint roles, event types, object facets, and context labels.
3. Filter matches by exact Protocol availability and capability possession.
4. Evaluate Protocol guards against a named snapshot.
5. return zero, one, or many activation candidates with reasons and status.

Multiple matches are retained. Routing does not choose a winner merely because priorities differ; priority may order evaluation but cannot erase alternatives. A selector that cannot evaluate because a required fact is absent returns an `UNKNOWN` branch.

Whether routing is a separate trusted component or merely a Protocol function is open. The minimum trusted surface is: exact-version resolution, capability verification, snapshot binding, deterministic dispatch for deterministic rules, and an audit log of considered candidates. A router may not translate payload semantics unless the active Protocol explicitly authorizes a named adapter.

## 6. Coexistence

Each admitted Protocol writes to a logical namespace identified by `ProtocolRef`. Shared object identities do not imply shared meanings. Coexistence is supported by an append-only operation log and CRDT-style replicated state where a Protocol supplies a valid merge algebra.

The default substrate offers only conservative primitives:

- grow-only sets for observations and evidence references;
- observed-remove sets for explicitly retractable memberships;
- multi-value registers for concurrent, non-equivalent values;
- causal maps keyed by stable IDs;
- tombstones that preserve lineage and do not assert semantic nonexistence.

A Protocol may use these primitives only after declaring algebraic obligations: closure, associativity, commutativity, idempotence, and deterministic canonical encoding. If those obligations are not established, replicas retain operation branches and report `NOT_PROVEN` for convergence. “Last writer wins” is unavailable as a default because wall-clock order is not semantic authority.

Cross-Protocol coexistence keeps results side by side. Bridges are explicit, versioned Protocols with their own capabilities, loss annotations, and provenance. Switching Protocols means reinterpreting the same named snapshot or selecting a bridge; it never silently rewrites source claims.

## 7. Conflict

Conflict is typed rather than Boolean:

```text
ConflictRecord := {
  ConflictID,
  contenders: NonEmptySet<ClaimOrOperationRef>,
  conflict_kind: VALUE | IDENTITY | ORDER | AUTHORITY | SCHEMA |
                 INVARIANT | TEMPORAL | INTERPRETATION,
  protocol_refs,
  causal_context,
  status: CONFLICT,
  permitted_resolvers,
  resolution_history
}
```

Detection and resolution are separate. Detection preserves all contenders. Resolution may create a new claim, select a view-local preference, retract a claim when authorized, or leave the conflict live. It may not erase losing provenance.

There is no global conflict algebra. Within a Protocol, a declared join may settle structural concurrency; semantic conflict still requires a Protocol rule or an authorized human/process decision. Across Protocols, different answers can be jointly valid views. A cross-Protocol contradiction is asserted only by a bridge that defines comparable terms and supplies evidence; otherwise the relation between outputs is `NOT_PROVEN`.

## 8. Contextual Materialization

Materialization is a pure, snapshot-bound operation:

```text
materialize(
  protocol_ref,
  snapshot_ref,
  context: {persona_ref?, purpose, jurisdiction?, time_basis,
            locale?, disclosure_capabilities, query_parameters},
  view_spec
) -> MaterializedView
```

The view contains source revision IDs, relation IDs, Protocol digest, context digest, derivation trace, epistemic statuses, alternative branches, and expiry conditions. Caches are keyed by all of those dependencies. A changed capability, source revision, Protocol version, or context invalidates reuse.

Context may select, redact, rank, aggregate, or transform only where declared rules permit. Redaction produces an explicit placeholder such as `OUT_OF_SCOPE(reason=CAPABILITY_WITHHELD)`; it must not convert withheld material into `UNKNOWN`. Materialization does not commit runtime facts. If a materializer discovers a candidate fact, it may emit a separately authorized mutation request.

## 9. Runtime State Change

`RUNTIME_STATE_MUTATION` changes instances under frozen semantics. The transaction envelope is:

```text
RuntimeMutation := {
  OperationID, ProtocolRef, BaseSnapshotRef, Intent,
  Preconditions, RelationAndObjectDeltas, CapabilityProofs,
  CausalContext, IdempotencyKey
}
```

Processing order is authenticate → resolve exact Protocol → authorize capabilities → validate schemas → check preconditions and invariants → append operation → compute local state → publish event. Authorization is least-privilege and target-scoped. Possession of a read capability grants no mutation power; materialization capability grants no write power.

Concurrent valid mutations merge only through the declared algebra. A failed precondition returns a structured non-commit result. Partial commits are forbidden unless the Protocol declares independent subtransactions and their compensation semantics. External side effects require an outbox record and a deduplication key; fabric commit does not falsely certify completion of the external effect.

The exact boundary between runtime and semantic mutation remains open at the margins—for example, adding a previously unseen relation type instance can be runtime change only if that exact type already exists in the Protocol. Any request that changes type meaning, validation, authorization, routing, merge, status, or materialization rules is semantic.

## 10. Semantic Mutation and Successor Models

The N02 proposal is frozen. `MODEL_SEMANTIC_MUTATION` against it must be rejected with `FROZEN_MODEL`. Semantic change is expressible only as:

```text
SUCCESSOR_MODEL_PROPOSAL := {
  ProposalID,
  SourceModelRef: (N02, exact_version, digest),
  NewExactTarget: (new_model_id, exact_version, proposed_digest),
  SemanticPatch,
  ChangedObligations,
  MigrationOrBridgePlan,
  CounterexamplesAndEvidence,
  CompatibilityClaimsWithProofStatus,
  AuthorCapability,
  Lineage: [ancestor_model_refs]
}
```

`NewExactTarget` must not alias N02 or reuse its exact version. Acceptance creates a distinct model node and preserves the source. Existing logs remain interpreted under their original Protocol and model digests unless an explicit, auditable migration creates new derived records. “Upgrade in place” is invalid.

A successor proposal can be `NOT_PROVEN`, `CONFLICT`, or rejected without changing N02. Model lineage is a DAG; competing successors may coexist. Descendant status does not confer correctness or authority.

## 11. Status and Plural Semantics

Statuses are payload-bearing:

| Status | Required meaning |
|---|---|
| `KNOWN` | Supported under named Protocol, snapshot, context, and evidence. |
| `UNKNOWN` | A required value is absent or indeterminate within the query boundary. |
| `CONFLICT` | Two or more typed contenders cannot jointly satisfy a named rule. |
| `NOT_PROVEN` | A claim, compatibility relation, invariant, or convergence property lacks sufficient proof. |
| `OUT_OF_SCOPE` | The active Protocol, capability, purpose, or declared domain excludes adjudication. |

These statuses are not ordered by truth or confidence. `UNKNOWN` cannot be collapsed into false; `NOT_PROVEN` cannot be promoted to conflict; `OUT_OF_SCOPE` cannot be used to conceal a known conflict. Every non-`KNOWN` result includes a reason code and, when safe, missing prerequisites.

A query may return `MultipleValidViews`, a nonempty collection keyed by exact Protocol, Persona, context, and derivation. The collection has no mandatory canonical member. Aggregation must state whether it is union, intersection, voting, preference ordering, or another Protocol-defined operation; absence of such a rule preserves plurality.

## 12. Personas and Worldviews

`Persona` is a versioned policy-bearing context reference, never an omnipotent subject:

```text
PersonaRef := (PersonaID, ExactVersion, Digest)
Persona := {
  permitted_protocol_refs,
  capability_bindings,
  salience_rules,
  disclosure_policy,
  preference_rules,
  declared_assumptions,
  jurisdiction_and_purpose_constraints
}
```

Personas can yield different materializations from the same snapshot. Their outputs remain provenance-bound and may coexist without forced convergence. A Persona cannot override Protocol invariants or mint capabilities. Persona preference resolves presentation only unless a Protocol explicitly grants it adjudication authority.

A worldview is modeled as a named set of Protocols, bridges, assumptions, and Persona policies. Worldviews may overlap, disagree, or be mutually non-comparable. Switching worldview or Protocol constructs a new view request; the response must disclose losses, unresolved mappings, changed status rules, and source preservation. If faithful switching cannot be established, return `NOT_PROVEN` or `OUT_OF_SCOPE` rather than a cosmetically unified result.

## 13. Invariants

The candidate requires the following local invariants:

1. **Exact binding:** every interpreted result names exact model and Protocol digests.
2. **Capability confinement:** each read, materialization, runtime mutation, and successor proposal is authorized for its operation kind and exact targets.
3. **No semantic in-place change:** frozen definitions and admitted Protocol versions are immutable.
4. **Lineage retention:** revisions, retractions, resolutions, bridges, and successors retain parent/source references.
5. **Plurality preservation:** no generic layer discards concurrent values, Protocol branches, Persona views, or live conflicts.
6. **Status honesty:** the five epistemic statuses remain distinguishable and reason-bearing.
7. **Materialization purity:** view generation alone cannot alter runtime state.
8. **Deterministic replay where claimed:** same exact inputs and deterministic modules yield the same canonical output; nondeterminism must be logged as input.
9. **CRDT conditionality:** convergence is claimed only for state whose declared algebra meets the stated laws.
10. **Source preservation under switching:** adapters and bridges never overwrite source claims.

Cross-Protocol invariants are intentionally limited to these envelope properties. Whether stronger invariants—identity continuity, temporal coherence, non-contradiction, or common authorization semantics—can hold across heterogeneous Protocols is open and must be stated per bridge.

## 14. Failure Boundaries

N02 fails closed on authority and model binding, but remains plural on meaning:

- missing/invalid capability → `DENIED`, with no protected existence leak;
- unavailable exact Protocol or digest mismatch → `UNKNOWN_PROTOCOL`, no fallback;
- schema/guard evaluation lacking facts → `UNKNOWN`, no mutation;
- invariant violation → rejected transaction plus evidence record;
- incompatible concurrent updates → retained branches plus `CONFLICT`;
- unproved merge or adapter safety → `NOT_PROVEN`, no fabricated convergence;
- unsupported domain or operation → `OUT_OF_SCOPE`;
- materializer crash/timeout → incomplete view marked with failed dependency, never a complete result;
- replica partition → locally qualified snapshot and causal frontier, never global-completeness language;
- external side-effect uncertainty → `NOT_PROVEN_COMPLETION` with outbox state.

The trusted computing base includes capability verification, digest resolution, append integrity, snapshot construction, and isolation between Protocol modules. Compromise there invalidates the relevant guarantees. A malicious but correctly signed Protocol may still encode harmful semantics; admission checks establish interface compliance, not goodness.

## 15. Executable Implementation Contact

One minimal implementation can use an append-only log, a content-addressed Protocol registry, a relation index, and a sandboxed evaluator. The following pseudocode is intended to be implementable rather than decorative:

```rust
enum OpKind { Read, ViewMaterialization, RuntimeStateMutation,
              ModelSemanticMutation }

enum Epistemic<T> {
    Known(T),
    Unknown(Reason),
    Conflict(Vec<Contender>, Reason),
    NotProven(Obligation),
    OutOfScope(Boundary),
}

fn execute(env: Envelope, store: &mut Store) -> Result<Receipt, ExecError> {
    let p = store.protocols.resolve_exact(&env.protocol_ref)?;
    verify_digest(&p, &env.protocol_ref.definition_digest)?;
    verify_capabilities(&env.capability_proofs, env.kind, &env.targets)?;
    let snap = store.snapshots.resolve(&env.snapshot_ref)?;

    match env.kind {
        OpKind::Read => p.read(&snap, &env.payload).map(Receipt::read),
        OpKind::ViewMaterialization =>
            p.materialize(&snap, &env.context, &env.payload)
             .map(|v| Receipt::view(v.with_dependencies())),
        OpKind::RuntimeStateMutation => {
            let delta = p.validate_runtime_delta(&snap, &env.payload)?;
            p.check_invariants(&snap, &delta)?;
            let op_ref = store.log.append_if_absent(env.idempotency_key, delta)?;
            Ok(Receipt::commit(op_ref, p.ref_exact()))
        }
        OpKind::ModelSemanticMutation => Err(ExecError::FrozenModel {
            required: "SUCCESSOR_MODEL_PROPOSAL with new exact target"
        }),
    }
}
```

Minimum persistence tables/collections are `object_revisions`, `relation_instances`, `events`, `protocol_blobs`, `capability_grants`, `operations`, `conflicts`, `view_manifests`, and `successor_proposals`. Each row carries tenant/security labels and provenance. Protocol evaluators run with resource limits and no ambient authority. Conformance tests must exercise duplicate events, reordered delivery, partitions, concurrent conflicts, revoked capabilities, digest mismatch, and context-cache separation.

## 16. Falsification

N02 is falsified, within its claimed envelope, by any reproducible case where:

1. a `READ` or `VIEW_MATERIALIZATION` changes runtime state;
2. a runtime operation changes schema, routing, authorization, merge, status, or interpretation semantics without a successor model;
3. replay under identical exact inputs produces different output without logged nondeterministic input;
4. an unauthorized principal learns protected existence or causes a target mutation;
5. switching Protocols overwrites or silently re-labels the source claim;
6. concurrent values disappear without a declared, authorized resolution;
7. a claimed CRDT merge violates closure, associativity, commutativity, or idempotence;
8. `UNKNOWN`, `CONFLICT`, `NOT_PROVEN`, or `OUT_OF_SCOPE` is silently coerced to `KNOWN` or false;
9. a Persona alters an invariant without explicit Protocol-granted authority;
10. an accepted semantic change reuses the frozen source exact target or loses lineage;
11. cache reuse crosses a Protocol, snapshot, context, capability, or Persona digest boundary;
12. an unseen Protocol is treated as compatible merely because it parses.

Validation requires executable property tests, trace replay, authorization-negative tests, partition simulations, and adversarial Protocol fixtures. Passing these tests supports only the tested implementation and Protocol classes; it does not validate all possible Protocols.

## 17. Strongest Self-Critique

Relation-first routing may privilege stable addressability and underfit processes whose identity is fundamentally event- or flow-dependent. Turning relations into entities adds indirection, storage, and stale-index risks. Capability checks on every interpretation can be expensive and can fragment otherwise useful views. CRDT primitives solve only carefully bounded convergence problems; they do not solve semantic disagreement, and the proposed conflict records may simply make disagreement durable.

The Protocol abstraction pushes difficult choices into Protocol authorship. A sufficiently expressive Protocol language makes termination, safety, compatibility, and information-flow properties undecidable; a restricted language excludes important domains. Sandboxing limits damage but cannot determine whether signed semantics are fair, correct, or legitimate. Exact digests improve reproducibility while increasing operational friction and version proliferation.

The distinction between runtime and semantic mutation has genuine gray zones: adding a new code value, changing a capability grant, revising identity evidence, or updating a learned parameter can change effective meaning without editing a schema. N02 supplies an audit boundary, not a complete theory for classifying every such case. Likewise, no global answer is given for relation/event primacy, Protocol ontology, router independence, cross-Protocol invariants, or conflict algebra. These are retained as decision points because prematurely fixing them would overstate the candidate.

## 18. Unsupported Protocols

N02 does not currently support, and must return `OUT_OF_SCOPE` or `NOT_PROVEN` for, Protocol classes that require any of the following without an admitted bounded adapter:

- unbounded or non-terminating rule evaluation with hard real-time guarantees;
- hidden semantics that cannot be versioned, digested, inspected, or replayed;
- ambient authority, unverifiable identity, or mutation without target-scoped capabilities;
- destructive history erasure or deniable lineage as normal operation;
- global total ordering across partitions without an external consensus assumption;
- automatic semantic convergence for arbitrary natural-language or normative disputes;
- exact cross-Protocol translation where the mapping is lossy, partial, or undecidable;
- nondeterministic external oracles whose inputs and attestations cannot be recorded;
- retroactive in-place reinterpretation of frozen records without derived lineage;
- quantum state protocols requiring no-cloning/no-observation semantics not captured by this classical log;
- safety-critical physical control where the evaluator, timing model, and actuators lack separately certified bounds;
- privacy regimes requiring deletion that cannot be reconciled with the append-only provenance design;
- adversarial Protocol code for which isolation, resource bounds, or information-flow confinement cannot be established.

An unsupported Protocol may motivate a `SUCCESSOR_MODEL_PROPOSAL`, but the proposal must name a new exact target, preserve lineage, state which invariant changes, and include evidence. Until accepted and independently validated, it remains non-normative and does not expand N02's claims.
