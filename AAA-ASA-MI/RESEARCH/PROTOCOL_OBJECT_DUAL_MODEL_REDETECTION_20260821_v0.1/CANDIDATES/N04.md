## 1. Object

An **Object** is an addressable actor boundary, not a passive record. Its minimum model is:

`Object = (object_id, object_type_ref, behavior_target, local_state, mailbox, capability_manifest)`.

- `object_id` is stable within a declared namespace.
- `behavior_target` is an exact, immutable model target, including version and digest.
- `local_state` is private to the actor. Only that Object's accepted behavior may mutate it.
- `mailbox` receives immutable message envelopes; delivery does not imply acceptance.
- `capability_manifest` declares message families, schema targets, and operational limits the Object is prepared to consider.

The Object exposes `receive(envelope)`, `emit(envelope)`, `read(snapshot_request)`, and `propose_successor(proposal)`. It does not expose arbitrary state writes. A local transition records its triggering message IDs, prior state revision, resulting revision, behavior target, and emitted event IDs. Object identity, type, state, and behavior are separate: changing state does not change the model; changing behavior requires a successor model.

This is a bounded actor abstraction. It does not assert that every social, physical, or computational entity is an Object. **OPEN:** the global ontology of entities, identity, type, composition, and whether Relations are also Objects.

## 2. Protocol

A **Protocol Model** is a first-class, variable, addressable definition rather than logic compiled into Object classes:

`ProtocolDefinition = (protocol_id, exact_target, roles, alphabet, schemas, admission, transition_evaluator, causal_rules, projections, termination, declared_extensions)`.

A **Protocol Instance** is runtime state:

`ProtocolInstance = (instance_id, protocol_target, role_bindings, state_revision, event_frontier, timers, status)`.

The definition declares role constraints; accepted message and event types; payload schema references; admission and transition contracts; causal prerequisites; permitted projections; and termination conditions. The instance binds Objects to roles and advances only under the frozen definition at `protocol_target`. Definition and instance are never conflated.

Heterogeneous or previously unseen Protocols can be stored and inspected through the generic envelope and metadata layer. They are executable only when their schemas and transition evaluator are available through a declared adapter with a supported execution profile. Otherwise they remain honestly `UNKNOWN`, `NOT_PROVEN`, or `OUT_OF_SCOPE`; mere registration is not a claim of semantic understanding. No universal protocol expressivity is claimed.

## 3. Object↔Protocol interaction

Interaction is bidirectional and message-mediated.

1. **Object → Protocol:** an Object emits a proposal, observation, commitment, withdrawal, or result envelope to a Protocol Instance. The runtime checks exact targets, role binding, schema, authorization, and causal prerequisites before the Protocol transition evaluator may append a transition.
2. **Protocol → Object:** a Protocol emits an offer, request, grant, timeout, obligation notice, or completion envelope to a bound Object. The Object may accept, reject, defer, or return an epistemic status according to its own frozen behavior and capabilities.

Neither direction grants hidden write access. A Protocol cannot directly mutate Object local state, and an Object cannot directly mutate Protocol Instance state. Each side changes only its own runtime state after receiving a causally linked message and records any outgoing consequence. A coordinated exchange is therefore a chain of explicit transitions, not an assumed cross-boundary transaction.

Every envelope carries at least `message_id`, `source`, `destination_or_role`, `protocol_target`, `instance_id`, `message_type`, `payload_schema_target`, `parent_ids`, `idempotency_key`, and `evidence_refs`. Missing mandatory correlation yields a recorded rejection or dead-letter result, not guessed context.

## 4. Relation/Event responsiveness

An **Event** is an immutable occurrence claim with provenance:

`Event = (event_id, kind, participants, protocol_target, instance_id, parents, logical_time, payload, evidence_refs, status)`.

Message send, receipt, acceptance, rejection, timeout, and actor transition are distinct event kinds. Causality is a partial order: actor-local accepted transition order, send-before-receive, and explicit parent links induce `happens_before`. Events without such evidence remain concurrent; wall-clock timestamps do not manufacture causality.

A **Relation** is represented locally as a provenance-bearing claim or projection over events, such as `authorized_by(A,B)` or `depends_on(X,Y)`. When a relevant event arrives, the View Engine invalidates or incrementally updates only projections whose dependency declarations match it. A Relation can therefore change status without rewriting its source events. N-ary, temporal, and context-indexed Relation claims are allowed by the local representation.

Relation claims retain the event frontier and exact model target from which they were derived. A late or contradictory event may produce a new view or `CONFLICT`; it may not erase the prior result. **OPEN:** a global Relation ontology, universal event taxonomy, identity equivalence, and cross-domain meaning alignment.

## 5. Routing

Routing is an explicit, inspectable decision, never an ambient assumption. For a single Protocol Instance, the bounded interface is:

`route(envelope, role_bindings, capability_manifests, context) -> RouteDecision`.

`RouteDecision` contains candidate destinations, exclusions, decision basis, resolver target, evidence frontier, and status. A frozen Protocol may select a named resolver or require an explicit destination. If several destinations remain admissible, the result is a set with `MULTIPLE_VALID_VIEWS` or a Protocol-defined choice event; if none can be justified, the result is `UNKNOWN` or `OUT_OF_SCOPE`. Delivery retries preserve `message_id` and idempotency key.

No resolver may silently infer a unique identity, role, or authority. **OPEN:** global routing priorities, discovery, trust, federation, naming, tie-breaking, and the existence of any default resolver.

## 6. Coexistence

Objects may participate concurrently in many Protocol Instances and occupy different roles in each. Isolation is by `(object_id, instance_id, protocol_target)`, while causal links between instances require explicit bridge events. Message types and roles are scoped to an exact Protocol target, avoiding accidental equivalence between similarly named concepts.

Different Protocol Models may coexist over the same source events. Each consumes only events admitted by its declared adapter and emits projections labelled with its own target. One model cannot overwrite another model's projection. A bridge can map events or roles between two exact targets, but the bridge itself is a versioned model with provenance and stated lossiness.

Coexistence includes incompatible interpretations. There is no forced canonical view, and shared Object IDs do not imply shared meaning beyond the identity scope explicitly declared.

## 7. Conflict

Conflict is data, not an exception to hide. A `ConflictSet` records competing claim IDs, evidence frontiers, involved exact targets, conflict kind, and unresolved status. At least four conflict kinds are distinguished: contradictory payload claims, incompatible role bindings, causal-order disagreement, and incompatible model interpretations.

A particular frozen Protocol may name a local resolver and its admissible evidence. That resolver returns a new, provenance-bearing decision or leaves the set unresolved; it never deletes the alternatives. If two outcomes are each valid under different contexts or worldviews, they are reported as `MULTIPLE_VALID_VIEWS`, not collapsed into `CONFLICT`. If no proof obligation has been discharged, the status is `NOT_PROVEN` rather than false.

**OPEN:** global conflict precedence, authority, reconciliation, trust weighting, appeal, and whether any cross-Protocol resolution is legitimate.

## 8. Materialization

Every operation declares exactly one effect class before execution:

| Effect class | Permitted effect | Forbidden effect |
|---|---|---|
| `READ` | Return existing events, states, definitions, or projections at a named revision/frontier | Any durable write or transition |
| `VIEW_MATERIALIZATION` | Create or refresh a derived, disposable projection keyed by exact target, context, Persona/worldview, and event frontier | Changing source events, runtime state, or model semantics |
| `RUNTIME_STATE_MUTATION` | Advance Object or Protocol Instance state under its already-frozen transition semantics | Changing definitions, schemas, role meaning, or causal rules |
| `MODEL_SEMANTIC_MUTATION` | No in-place execution is permitted | Any alteration of a frozen exact target; it must cross the successor boundary in section 10 |

Materialized views carry dependency sets and may be discarded and recomputed. A cache hit is valid only for the same exact targets, event frontier, context, and Persona/worldview target. If an operation cannot be classified unambiguously, it is rejected before side effects with `UNKNOWN` classification evidence.

## 9. Runtime change

A runtime mutation is a compare-and-append transition against a specific actor or Protocol Instance revision. The request supplies the expected revision, exact behavior/protocol target, causal parents, and idempotency key. The runtime validates them, evaluates the frozen transition, atomically appends its events with the new local revision, and only then releases outgoing messages.

Concurrent proposals to the same actor revision do not receive a fabricated order. One may commit; the others are retried, rejected, or reconsidered under the Protocol's declared concurrency rule. Cross-actor atomicity is not assumed. Sagas, reservations, or compensation must be explicit Protocol behavior, with each step causally recorded.

Timers and external inputs enter as messages with provenance. Replay suppresses duplicate external effects through the idempotency ledger. Runtime state can evolve freely within admitted transitions, but its evaluator, schemas, role meanings, and causal rules remain byte-identical to the exact target.

## 10. Successor boundary

Frozen model semantics change only through `SUCCESSOR_MODEL_PROPOSAL`. Such a proposal contains:

- a new proposed exact target and complete model content or deterministic patch;
- predecessor exact target(s) and lineage relation;
- rationale, changed semantic surfaces, and affected Protocol/Object types;
- compatibility claims explicitly marked `NOT_PROVEN` until validated;
- proposed event/view migration and known losses;
- author, evidence, and proposal digest.

Submitting a proposal does not activate it and does not mutate its predecessor. If separately accepted by an authority outside this candidate, it becomes a new exact target with immutable lineage. Existing instances remain pinned unless a frozen migration Protocol explicitly produces a new instance or binding. Historical events remain under their original targets; successor reinterpretations are additional views.

Direct schema edits, evaluator replacement, role redefinition, causal-rule changes, and meaning-changing configuration edits are `MODEL_SEMANTIC_MUTATION` and are forbidden in place. **OPEN:** global mutation governance, proposal authority, validation threshold, adoption policy, migration authority, and lineage reconciliation.

## 11. Status and plural semantics

Statuses are typed values attached at claim, field, route, transition, proof, and view level:

- `UNKNOWN`: required information or a capable evaluator is absent.
- `CONFLICT`: incompatible claims share a comparison context and have not been resolved.
- `NOT_PROVEN`: a stated proof obligation exists but has not been discharged.
- `OUT_OF_SCOPE`: the active exact target explicitly does not model or decide the question.
- `MULTIPLE_VALID_VIEWS`: two or more contextual results are individually valid and need not be reconciled.

These statuses are not interchangeable and are not coerced to `false`, empty, zero, or error. Aggregation propagates them according to a frozen projection's declared status algebra; if that algebra is missing, aggregation returns `UNKNOWN`. A result may carry multiple scoped statuses—for example, an observed event can be known while a claimed obligation derived from it is `NOT_PROVEN`.

Plural semantics are represented as labelled claim sets `(claim, exact_target, context, worldview, frontier, evidence, status)`. The system preserves alternatives and reports which question each answers. It does not designate a globally true worldview.

## 12. Personas and switching fidelity

A **Persona** is a versioned projection contract defining vocabulary, salience, redaction, aggregation, and interaction affordances for a declared audience or worldview. It can change presentation and choose among permitted contextual projections; it cannot change events, causal edges, permissions, runtime state, or frozen model meanings.

Several Personas and worldviews may coexist over the same Object and Protocol histories. Persona output carries `persona_target`, `worldview_target`, source exact targets, context, event frontier, evidence references, and epistemic statuses. A viewer may request parallel outputs rather than switching.

Switching fidelity requires preservation of Object/Protocol/instance identifiers, exact targets, causal frontier, evidence links, unresolved alternatives, and statuses. Before a switch, the engine emits a `SwitchManifest` listing preserved, renamed, hidden, aggregated, and non-representable claims. Lossy projection is allowed only when disclosed; it never authorizes deletion. A round trip is faithful when all claims declared preservable by both Personas retain identity, evidence, status, and causal frontier. If that cannot be demonstrated, the switch result is `NOT_PROVEN` or `OUT_OF_SCOPE`, not "equivalent."

## 13. Invariants

This candidate requires the following local invariants:

1. **Exact-target pinning:** every evaluated transition and derived claim names immutable model targets.
2. **Event immutability:** accepted events are append-only; correction is another linked event.
3. **Causal honesty:** only declared local order, send/receive links, and explicit parents induce `happens_before`.
4. **Actor ownership:** only an Object's frozen behavior changes its local state; only a Protocol runtime using the frozen evaluator changes its instance state.
5. **Effect separation:** `READ`, `VIEW_MATERIALIZATION`, `RUNTIME_STATE_MUTATION`, and `MODEL_SEMANTIC_MUTATION` are enforced as distinct capabilities and storage paths.
6. **Provenance completeness:** runtime transitions and views retain triggers, evidence frontier, evaluator target, and status.
7. **Plural preservation:** conflicts and multiple valid views cannot be silently collapsed.
8. **Persona non-interference:** Persona choice cannot mutate source or runtime state.
9. **Idempotent intake:** repeated delivery of the same accepted message ID cannot repeat a local transition or external effect.
10. **Successor-only semantics:** a frozen target's meaning never changes in place.

These are candidate-local obligations, not a global invariant theory. **OPEN:** the global invariant set, priority among invariants, proof system, enforcement authority, and cross-Protocol compositionality.

## 14. Failures

Bounded failure handling is explicit:

- Missing model, adapter, schema, or evaluator: quarantine the envelope; report `UNKNOWN` capability.
- Unsupported evaluator profile or question beyond the model: report `OUT_OF_SCOPE`.
- Schema mismatch or unauthorized role: reject without transition and retain diagnostic provenance.
- Missing causal parent: hold pending within a declared limit, then expose a causal-gap status; do not invent the parent.
- Causal cycle: reject the proposed edge and preserve the evidence for diagnosis.
- Duplicate message: return the prior outcome through the idempotency ledger.
- Revision race: emit no state change for the loser; retry only if frozen policy permits.
- Evaluator crash or nondeterministic replay: stop the instance at its last valid revision and mark subsequent claims `NOT_PROVEN`.
- Contradictory evidence: create or extend a `ConflictSet`.
- View or Persona switch loses material: disclose it in the `SwitchManifest`; refuse claims of equivalence.
- External side effect succeeds but acknowledgement is lost: retain an indeterminate outcome and reconcile by an explicit message; never assume rollback.

Quarantine, retry ceilings, timeouts, and compensation are bounded by the active Protocol. When absent, the runtime stops safely rather than adopting a global default.

## 15. Implementation contact

A minimal implementation has eight replaceable components: `ObjectHost`, `ProtocolRegistry`, `ProtocolRuntime`, append-only `EventStore`, `Router`, `ViewEngine`, `StatusAlgebra`, and `SuccessorRepository`. Definitions are content-addressed. Object and instance snapshots are accelerators; the authoritative runtime record is the validated transition/event sequence plus exact targets.

The core transition boundary is:

```text
handle(envelope, expected_revision):
  require envelope.protocol_target == instance.protocol_target
  classify_effect(RUNTIME_STATE_MUTATION)
  validate_schema_role_capability_and_parents(envelope)
  result = evaluator_at_exact_target(instance, envelope)
  compare_and_append(expected_revision, result.events, result.new_revision)
  publish(result.outgoing_envelopes_after_commit)
```

Suggested storage keys are `(namespace, object_id, revision)`, `(protocol_target, instance_id, revision)`, `(instance_id, event_id)`, and `(model_targets, context, persona_target, worldview_target, frontier)` for view caches. Evaluators run in a sandbox with declared deterministic inputs; network, clock, random, and human responses arrive as separately recorded messages. A generic adapter may preserve opaque payload bytes and envelope metadata even when no evaluator exists.

Operational telemetry includes rejection reason, queue age, causal-gap count, evaluator target, replay hash, view frontier, and switch-loss count. These contacts make the proposal testable but do not prescribe a programming language, database, global registry, or deployment topology.

## 16. Falsification

The candidate is falsified, or at minimum requires a new successor proposal, if controlled tests show any of the following:

1. a runtime operation changes the digest or meaning of its pinned Object or Protocol Model;
2. replay of identical admitted inputs under one exact target produces different local transitions without recorded nondeterministic input;
3. duplicate delivery repeats an accepted transition or external effect;
4. the system asserts a causal order between concurrent events without declared evidence;
5. a Relation-responsive view fails to advance or invalidate when a declared dependency event is appended;
6. a Persona switch drops conflict, evidence, exact-target, or epistemic-status information without disclosure;
7. an unseen Protocol cannot even be preserved as an opaque, provenance-bearing definition and envelope stream without modifying core storage;
8. an unavailable evaluator is represented as a successful or false semantic answer rather than `UNKNOWN`, `NOT_PROVEN`, or `OUT_OF_SCOPE`;
9. one Protocol or worldview overwrites another's source events or projection;
10. any frozen semantic edit bypasses `SUCCESSOR_MODEL_PROPOSAL`, a new exact target, and lineage.

Passing these tests only supports the bounded mechanisms stated here. It does not validate universal expressivity, global ontology, social legitimacy, security, liveness, or cross-Protocol compositionality.

## 17. Strongest critique

The strongest critique is that this design can make ignorance and causality legible without solving meaning. A generic envelope plus external evaluator gives useful containment for heterogeneous Protocols, but representation of an unseen Protocol may be little more than lossless storage until an adapter, shared ontology, and trusted semantics exist. First-class versioning can also multiply models, bridges, views, and lineage faster than humans can govern them.

Actor ownership avoids hidden writes but makes multi-Object atomic commitments expensive and sometimes impossible; compensation may be inadequate for irreversible real-world effects. Event retention and provenance impose storage, privacy, and latency costs. Deterministic replay does not guarantee that an external observation was truthful. Persona plurality can preserve disagreement yet still conceal power in who authors schemas, evaluators, routing resolvers, and admissible evidence.

Accordingly, this is a concrete execution and accountability boundary, not a solution to the open global questions or a proof that actor/process-calculus semantics fit every domain.

## 18. Unsupported Protocols

The proposal does not currently execute or guarantee:

- in-place self-modifying Protocols whose grammar, role meaning, or transition rules change without a successor exact target;
- Protocols that require deletion or undetectable rewriting of accepted causal history;
- hard real-time, continuous-time, analog, or physical-control guarantees that cannot tolerate message, storage, or evaluator latency;
- globally serializable atomic transactions across arbitrary, uncooperative actors or external systems;
- Protocols whose only semantics live in an unavailable proprietary engine, undocumented human convention, or inaccessible oracle—these can be retained opaquely but not interpreted;
- arbitrary semantic equivalence, refinement, or compatibility proofs between independently authored Protocol languages;
- proof-carrying or cryptographic claims when the required proof system, keys, or verification evidence are absent;
- covert or off-ledger interactions for which no causal or provenance-bearing boundary event can be observed;
- unbounded higher-order mobility or resource behavior beyond the configured evaluator sandbox and quotas;
- Protocols that demand a single global ontology, router, invariant hierarchy, mutation authority, or conflict sovereign, because those choices remain **OPEN**.

An unsupported class is reported with the narrowest applicable status and preserved evidence. It is not silently approximated into a supported class. Future support would require a `SUCCESSOR_MODEL_PROPOSAL` or a new adapter/model exact target with explicit lineage and falsification tests.
