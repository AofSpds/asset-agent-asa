This candidate treats relations and transitions as mutually constraining, but only through finite, typed records that an implementation can validate. Its categorical vocabulary names concrete data structures and composition checks; it does not assert universal coverage.

## 1. Object Model

An **Object** is a revision-pinned semantic identity plus a separately revisioned runtime instance. Definitions are immutable; instance state advances only through recorded events.

```text
SemanticRef      = {namespace, kind_id, semantic_rev, digest}
ObjectRef        = {object_id, kind_ref: SemanticRef}
ObjectSnapshot   = {
  object_ref, state_rev, fields, relation_endpoints,
  effective_time, observed_time, provenance_refs
}
ContextRef       = {
  context_id, context_rev, tenant, locale, jurisdiction,
  time_basis, purpose, permission_scope, protocol_ref?, persona_ref?, policy_refs[]
}
```

`kind_ref` fixes field types, identity rules, admissible relations, transition guards, and view contracts. `state_rev` fixes runtime values. Every evaluation consumes an exact `ObjectSnapshot` and `ContextRef`; neither “current” nor ambient context is a valid stored reference.

Objects expose four bounded surfaces:

1. typed fields that may be read under a context;
2. typed relation endpoints;
3. guarded runtime commands;
4. successor proposals against an exact semantic revision.

A contextual view is not a field on the object and is never presumed canonical. It is a derived claim bundle whose lineage names its object snapshot, context, Protocol, Persona, policies, and evidence.

## 2. Protocol Model

A **Protocol** is a first-class, immutable, versioned program description rather than a hidden procedure.

```text
ProtocolDefinition = {
  protocol_id, protocol_rev, digest, protocol_class,
  input_ports[], output_ports[], accepted_kind_refs[],
  effect_classes[], observation_rules[], transition_rules[],
  materializers[], status_rules[], conflict_policy_refs[],
  capability_manifest, resource_bounds, determinism_contract,
  adapter_abi, provenance_refs
}

ProtocolInvocation = {
  invocation_id, protocol_ref, exact_target_refs[], parameters,
  context_ref, persona_refs[], requested_effect_class,
  expected_state_revs{}, idempotency_key, parent_invocation_ref?,
  deadline, resource_budget
}
```

Supported `protocol_class` values initially include query, workflow, interpreter, simulator, transaction, migration, and external-observer. They share an invocation envelope but retain class-specific rules and outputs; heterogeneity is not erased into one generic callback.

An unseen Protocol is admitted only if it supplies a signed or locally attested descriptor matching the adapter ABI. The admission path schema-checks its ports, effects, opcodes, determinism declaration, and bounds, then compiles it to the finite Protocol IR in section 15. A novel identifier or natural-language description does not establish semantics. A descriptor that cannot compile is returned as `OUT_OF_SCOPE`, not guessed into the closest known Protocol.

## 3. Bidirectional Object–Protocol Interaction

Binding is an explicit negotiation:

```text
bind(ObjectSnapshot, ProtocolDefinition, ContextRef, PersonaRef*)
  -> Engagement | OUT_OF_SCOPE | CONFLICT
```

The Object acts on the Protocol by supplying typed affordances and constraints: visible fields, admissible relation types, permitted commands, transition guards, semantic pin, and contextual policies. These may select a Protocol branch, restrict its inputs, reduce its capabilities, or reject the binding.

The Protocol acts on the Object only by producing one of four typed effects: observations, view artifacts, runtime event proposals, or semantic successor proposals. It cannot write through an untyped object handle. Accepted observations may change which relation claims are evidenced; accepted events may change object state; accepted successor proposals may create a new semantic revision. Each accepted effect therefore changes the admissible inputs of later Protocol invocations.

An `Engagement` records both directions:

```text
Engagement = {
  object_snapshot_refs[], protocol_ref, context_ref, persona_refs[],
  granted_capabilities[], denied_capabilities[], selected_rules[],
  input_projection_digest, effect_ceiling, negotiation_evidence[]
}
```

No side is ontologically prior in an execution: the Protocol’s behavior is specialized by the Object, while the Object’s evidenced relations or future state are specialized by Protocol effects. The immutable pre-execution snapshots remain addressable.

## 4. Relation/Event Co-Constitution

The executable core is a bounded double-incidence structure.

- A **0-cell** is a pinned configuration `X = (ObjectSnapshot+, ContextRef, policy_refs)`.
- A **horizontal arrow** `h: X -> Y` is a typed relation assertion with a predicate, evidence, scope, and status. It relates configurations without itself advancing runtime state.
- A **vertical arrow** `u: X => X'` is an immutable transition event with exact before/after revisions.
- A **square** relates a pre-transition relation, two endpoint transitions, and a post-transition relation.

```text
SquareWitness = {
  square_id,
  top_relation_ref: h(X,Y),
  left_event_ref: u(X,X'),
  right_event_ref: v(Y,Y'),
  bottom_relation_ref: k(X',Y'),
  witness_policy_ref,
  witness_kind: STRICT | LAX | OPLAX | COUNTEREXAMPLE,
  derivation_steps[], evidence_refs[], verifier_digest,
  result_status
}
```

Operationally, `h` is a typed predicate over the before snapshots. The two events must transform exactly those snapshots. The witness verifier then evaluates `k` over the exact after snapshots and checks the policy-specific preservation obligation. `STRICT` requires the declared relation-preservation equation; `LAX` and `OPLAX` require a recorded directed comparison accepted by the pinned witness policy. `COUNTEREXAMPLE` records a demonstrated failure and yields `CONFLICT` for a claimed preservation. If evidence is insufficient, the square is `NOT_PROVEN`; a missing endpoint or unsupported predicate is `OUT_OF_SCOPE`.

Identity relations and identity events are real typed records, allowing a one-sided transition without inventing a hidden counterpart. Horizontal composition is a bounded relational join; vertical composition is a revision-contiguous event sequence. Squares compose only when shared boundary references, policy versions, and digests match exactly. The implementation checks associativity and the interchange law for admitted composites; it does not assume them for opaque or partial operations.

## 5. Routing and Admission

Routing is by exact keys, never by label similarity:

```text
RouteKey = {
  protocol_id, protocol_rev, adapter_abi,
  target_kind_refs[], requested_effect_class,
  context_ref, persona_refs[]
}
```

The router performs, in order: descriptor verification; Protocol IR compilation; object-kind matching; context/permission evaluation; effect-ceiling negotiation; resource-bound reservation; and adapter selection. Its receipt records every rejected and accepted capability.

For an unseen Protocol, the registry may install only its immutable descriptor and compiled IR, scoped to the current trust domain. Unknown opcodes, undeclared network access, ambiguous effects, missing revision pins, or non-enforceable bounds return `OUT_OF_SCOPE`. Multiple eligible routes are retained as labeled alternatives when their policies do not establish a unique choice. A Persona may rank alternatives but may not rewrite capability or correctness results.

Every invocation is classified before execution as exactly one of:

- `READ`;
- `VIEW_MATERIALIZATION`;
- `RUNTIME_STATE_MUTATION`;
- `MODEL_SEMANTIC_MUTATION`.

Mixed requests are split into a dependency-linked invocation plan so that each step retains one effect class and its own authorization boundary.

## 6. Coexisting Context Views

`ViewClaim` is the unit of contextual plurality:

```text
ViewClaim<T> = {
  proposition_id, value: T?, status, object_snapshot_refs[],
  context_ref, protocol_ref, persona_ref?, policy_refs[],
  evidence_refs[], valid_interval?, produced_at, claim_digest
}
ViewSet<T> = {claims[], compatibility_matrix, coverage_receipt}
```

Views from different Contexts, Protocols, time bases, jurisdictions, or Personas may coexist. They are not merged merely because their proposition labels match. Compatibility is evaluated only after an explicit projection maps them to the same proposition, context dimensions, units, and effective interval.

Several incompatible-looking values can therefore be simultaneously valid when their scopes differ. Such a result is `PLURAL_VALID`, with every scope retained. A caller may request a context projection, but the projection creates another lineage-bearing claim rather than deleting its sources. No default “global view” is defined.

## 7. Conflict Handling

A Conflict is evidence-bearing data, not an exception or a forced winner.

```text
ConflictRecord = {
  conflict_id, normalized_proposition_ref, normalized_context_ref,
  candidate_claim_refs[], incompatibility_witnesses[],
  authority_policy_ref?, resolution_state,
  resolution_claim_ref?, created_at, supersedes_conflict_ref?
}
```

Conflict detection requires claims to be comparable: same normalized proposition, compatible context, overlapping time, and mutually exclusive values. Differently scoped valid claims remain `PLURAL_VALID`. Same-scope incompatible claims become `CONFLICT`, even if a presentation policy ranks one higher.

Resolution is another Protocol invocation. It may add evidence, narrow scopes, apply a pinned authority rule, or create a successor claim. It never erases candidates. Last-write-wins is not a semantic resolution. Until a resolution is evidenced, downstream operations must propagate the Conflict or explicitly declare a branch choice with lineage.

Relation preservation can itself conflict: if an asserted bottom relation and a verified counterexample share the same square boundary, both are attached to one `ConflictRecord`. A policy change does not retroactively rewrite the earlier outcome.

## 8. Materialization and Effect Separation

The four effect classes have disjoint write surfaces:

| Effect class | Reads pinned state | May write derived artifact | May advance runtime `state_rev` | May create semantic revision |
|---|---:|---:|---:|---:|
| `READ` | Yes | No | No | No |
| `VIEW_MATERIALIZATION` | Yes | Yes | No | No |
| `RUNTIME_STATE_MUTATION` | Yes | Optional receipt only | Yes, by event | No |
| `MODEL_SEMANTIC_MUTATION` | Yes | Proposal/receipt only | No | Yes, as successor |

A materialized view has this identity:

```text
ViewArtifactKey = hash(
  object_snapshot_refs, context_ref, protocol_ref, persona_ref,
  policy_refs, evidence_digests, materializer_rev
)
```

The artifact stores its `ViewSet`, dependency graph, creation receipt, and invalidation status. It is a cache or presentation surface, never authoritative object state. A dependency change marks it stale; consumers may still inspect the stale artifact only with a visible stale status and its original pins. Cache writes are physically separated from event and model registries.

`READ` returns an evaluation envelope without persisting a view. `VIEW_MATERIALIZATION` may persist that same envelope. Neither can invoke a runtime command or successor writer through a helper function; execution roles and database permissions enforce the distinction.

## 9. Runtime Mutation

Runtime change begins with a command proposal and completes with one or more immutable events:

```text
RuntimeCommand = {
  command_id, protocol_invocation_ref, exact_target_ref,
  expected_state_rev, command_type, typed_payload,
  guard_refs[], idempotency_key, authorization_receipt
}
RuntimeEvent = {
  event_id, command_ref, exact_target_ref,
  before_state_rev, after_state_rev, delta,
  effective_time, recorded_time, cause_refs[], receipt_digest
}
```

The event store uses compare-and-swap on `expected_state_rev`. A mismatch yields `CONFLICT`; it does not silently rebase. Repeated idempotency keys return the original receipt. Multi-object mutation requires an atomic event bundle or a declared saga whose compensations are new events. Compensation does not delete history.

After commit, relation obligations named by the command are checked as witnessed squares. A required square that is `NOT_PROVEN` may either block commit or quarantine the resulting state according to the predeclared guard policy; this choice must be fixed before execution. Post-commit checking is permitted only for policies that explicitly accept quarantine risk.

Runtime events cannot alter field definitions, relation semantics, validators, Protocol rules, Persona definitions, or policies. Those are semantic targets and require section 10.

## 10. Semantic Successors and Exact Lineage

Semantic mutation is append-only successor creation. Its target must be an exact `SemanticRef`; wildcards, ranges, aliases, and “latest” are invalid targets.

```text
SuccessorProposal = {
  proposal_id,
  exact_predecessor_refs: SemanticRef[1..n],
  reserved_successor_ref: {namespace, kind_id, semantic_rev},
  semantic_delta, semantic_delta_digest,
  migration_protocol_ref?, compatibility_claims[],
  proposer_ref, context_ref, evidence_refs[], approval_policy_ref
}
SuccessorRecord = {
  successor_ref: SemanticRef,
  predecessor_refs[], proposal_ref, migration_protocol_ref?,
  compatibility_results[], lineage_witness_refs[], created_at
}
```

Creation verifies every predecessor digest, reserves a unique successor revision, rejects lineage cycles, validates the semantic delta, and records the new digest. Branches and multi-parent successors are allowed and explicit; there is no singular implicit successor. An older definition is never overwritten.

Runtime instances remain pinned to their prior semantic revision until an exact-target migration Protocol emits runtime events. Each migration is linked to squares showing how relevant relations change across the semantic boundary. A rollback is a new successor branch or runtime compensating event, not history mutation. Consumers asking for a successor without a branch-selection policy receive `PLURAL_VALID` when several branches satisfy the request.

## 11. Statuses and Plurality

Every read, claim, square, route, and effect returns a typed result envelope:

```text
Result<T> =
  | VALUE           {value: T, evidence_refs[]}
  | PLURAL_VALID    {values: Scoped<T>[2..n], compatibility_witnesses[]}
  | UNKNOWN         {missing_inputs[], attempted_sources[], retry_hint?}
  | CONFLICT        {conflict_ref, candidate_refs[]}
  | NOT_PROVEN      {claim_ref, unmet_obligations[], available_evidence[]}
  | OUT_OF_SCOPE    {unsupported_capabilities[], boundary_receipt}
```

- `UNKNOWN`: the question is in scope, but a required value or observation is absent or unavailable.
- `NOT_PROVEN`: the claim and proof obligation are understood, but the available witness does not establish it. This is not falsehood.
- `CONFLICT`: comparable, evidence-backed candidates cannot jointly hold under the pinned policy and context.
- `OUT_OF_SCOPE`: the engine, adapter, permissions, or declared resource bounds do not admit the operation. This is not lack of data.
- `PLURAL_VALID`: two or more labeled answers are valid in distinct or explicitly non-exclusive scopes. This is not Conflict.

There is no total precedence that collapses these states. A composite result may contain successful subresults plus a coverage receipt listing unknown, unproved, conflicting, or unsupported branches. Boolean projection is allowed only through an explicit policy and must retain the source envelope.

## 12. Personas and Switching Fidelity

A Persona is a versioned interaction and prioritization policy, not a user identity and not an authority source.

```text
PersonaDefinition = {
  persona_id, persona_rev, goals[], visibility_profile_ref,
  allowed_context_transforms[], ranking_policy_ref,
  presentation_contract, switch_policy_ref
}
```

One invocation may request multiple Personas. Each Persona produces separately labeled claims inside the same `ViewSet`; agreement does not merge provenance, and disagreement is tested using section 7. Persona ranking can order already-admissible alternatives but cannot turn `OUT_OF_SCOPE`, `CONFLICT`, or `NOT_PROVEN` into a value.

A switch is an explicit transition:

```text
PersonaSwitch = {
  switch_id, from_persona_ref, to_persona_ref,
  source_context_ref, target_context_ref,
  carried_claim_refs[], transformed_claim_refs[], dropped_claim_refs[],
  transform_protocol_ref, authorization_receipt
}
FidelityReport = {
  object_identity, semantic_pin, state_pin, context_dimensions,
  permissions, units_locale, protocol_position, unresolved_statuses,
  lineage, overall: EXACT | LOSSLESS_NORMALIZED | LOSSY_DECLARED | BLOCKED
}
```

Exact object and revision pins, unresolved statuses, and source lineage are carried by default. A unit or locale normalization may be `LOSSLESS_NORMALIZED` when reversible and witnessed. Any dropped claim, narrowed context, changed proposition, or non-reversible transformation is `LOSSY_DECLARED` and requires caller acknowledgement. Privilege elevation, semantic-pin substitution, Conflict suppression, or missing mandatory lineage is `BLOCKED`. The pre-switch view remains independently addressable.

## 13. Invariants

The validator enforces these invariants at write time and rechecks them during replay:

1. **Typed boundaries:** every relation, event, and square endpoint conforms to exact semantic revisions.
2. **Pinned inputs:** executions contain no unresolved “current” references.
3. **Effect separation:** one invocation step has one effect class and one permitted write surface.
4. **Event continuity:** `before_state_rev` equals the committed target revision; `after_state_rev` is unique.
5. **Witness completeness:** an accepted square names all four boundaries, a policy revision, and verifier digest.
6. **Compositional closure:** admitted composite squares pass endpoint, associativity, and interchange checks within declared bounds.
7. **Lineage immutability:** evidence, events, definitions, and successor edges are append-only.
8. **Exact succession:** every successor names digest-verified predecessors and cannot form a cycle.
9. **Context visibility:** every claim exposes its ContextRef or an authorized opaque reference to it.
10. **Status non-collapse:** `UNKNOWN`, `CONFLICT`, `NOT_PROVEN`, `OUT_OF_SCOPE`, and `PLURAL_VALID` remain distinguishable.
11. **Plural preservation:** context-distinct valid claims survive aggregation unless an explicit projection supersedes them.
12. **Conflict preservation:** resolution adds a lineage-bearing result without deleting candidates.
13. **Materialization non-authority:** no view artifact is accepted as object state or semantic definition.
14. **Persona non-elevation:** Persona switching cannot increase permissions or effect ceiling.
15. **Replay accountability:** fixed pins and deterministic Protocols reproduce digests; nondeterministic Protocols record seeds, external observation receipts, or an explicit non-replayable boundary.
16. **Bounded execution:** steps, fan-out, evidence bytes, wall time, and external calls remain within the invocation receipt.

An invariant failure aborts the affected pre-commit write. If detected after an allowed external or post-commit boundary, it quarantines the result and emits an immutable failure record.

## 14. Failure Modes

| Failure | Detection | Required behavior |
|---|---|---|
| Unknown Protocol opcode | IR compiler | `OUT_OF_SCOPE`; execute nothing |
| Descriptor/adapter drift | digest or ABI mismatch | Reject route; retain both receipts |
| Stale runtime target | compare-and-swap mismatch | `CONFLICT`; require explicit retry/rebase Protocol |
| Missing square evidence | unmet witness obligation | `NOT_PROVEN`; block or quarantine per pinned policy |
| Demonstrated non-commutation | counterexample verifier | `CONFLICT`; retain counterexample |
| Context mismatch | projection preflight | keep scoped claims separate or `OUT_OF_SCOPE` |
| Same-context incompatible claims | conflict detector | create `ConflictRecord`; do not rank away |
| Stale materialization | dependency digest mismatch | label stale; never promote to authority |
| Persona switch loses mandatory state | fidelity validator | `BLOCKED` |
| Partial multi-object write | transaction/saga monitor | roll back atomically or emit compensations and quarantine |
| Semantic predecessor changed | digest mismatch | reject successor proposal |
| Lineage cycle | DAG constraint | reject successor edge |
| Bound exhaustion | metering | `OUT_OF_SCOPE` with consumed-budget receipt |
| External nondeterminism unreceipted | replay audit | quarantine output as `NOT_PROVEN` for reproducibility claims |
| Policy version unavailable | registry lookup | `OUT_OF_SCOPE`; no fallback to a newer policy |

Failure records include exact inputs and the last completed step. Retries are new invocations linked to the failed one; they do not edit its history.

## 15. Implementation Sketch

The minimum implementation has separate stores and writers:

- `semantic_versions` and `semantic_successor_edges` (append-only model registry);
- `object_instances`, `runtime_events`, and `event_bundles` (event store plus snapshots);
- `relation_assertions` and `square_witnesses` (incidence ledger);
- `protocol_versions`, `compiled_protocols`, `invocations`, and `route_receipts`;
- `view_claims`, `view_artifacts`, and `artifact_dependencies` (derived store);
- `conflicts`, `resolution_claims`, `persona_versions`, `persona_switches`, and `fidelity_reports`;
- a content-addressed evidence store.

Database roles allow the read executor no writes, the materializer only derived-store writes, the runtime executor only command/event writes, and the semantic executor only proposal/successor writes. An orchestrator may split a mixed user request but holds none of those write privileges itself.

The finite Protocol IR initially contains:

```text
LOAD_PINNED, SELECT_FIELD, PROJECT_CONTEXT, NORMALIZE,
ASSERT_RELATION, REQUIRE_RELATION, PROPOSE_VIEW,
PROPOSE_EVENT, REQUIRE_SQUARE, PROPOSE_SUCCESSOR,
BRANCH_STATUS, COMPOSE_BOUNDED, EMIT_RESULT
```

Each opcode declares input/output types, permitted effect class, maximum fan-out, and evidence obligations. Arbitrary native calls are not IR opcodes. External adapters expose typed observations through a metered boundary.

Execution is a state machine:

1. resolve and digest-check all exact references;
2. compile/admit the Protocol and issue a route receipt;
3. bind Object, Context, and Personas; freeze the effect ceiling;
4. read one consistent snapshot set;
5. execute metered IR and accumulate claims/evidence;
6. validate statuses, context projections, and required squares;
7. for a materialization, write only the content-addressed artifact;
8. for runtime mutation, compare-and-swap and append event(s);
9. for semantic mutation, validate exact predecessors and append successor;
10. append result, lineage, fidelity, and coverage receipts.

Tenant policy supplies finite numeric ceilings for objects per invocation, join fan-out, IR steps, proof bytes, wall time, and external calls. Their exact values are copied into the route receipt, so a later replay knows the operative bounds.

## 16. Falsification Plan

N05 is falsified as an implementation model if any of these tests succeeds in producing an accepted but invalid result:

1. **Effect-leak test:** generate every IR opcode under every effect class; falsify if `READ` or `VIEW_MATERIALIZATION` advances runtime or semantic revision, or runtime mutation changes semantics.
2. **Square property test:** generate typed relations and revision-contiguous events; falsify if accepted horizontal/vertical compositions violate endpoint closure, associativity, or the declared interchange check.
3. **Counterexample retention test:** insert a valid preservation claim and counterexample; falsify if either disappears or the result is reported as a single uncontested value.
4. **Plurality test:** generate claims that differ only in declared context dimensions; falsify if aggregation silently selects one or reports Conflict without a comparability projection.
5. **Status test:** inject missing data, inadequate proof, incompatible evidence, and unsupported opcode; falsify if their four envelopes become indistinguishable.
6. **Stale-write race:** concurrently mutate one target from the same revision; falsify if both commits succeed without an explicit serializable bundle.
7. **Successor targeting test:** attempt aliases, “latest,” wrong digests, cycles, and in-place edits; falsify if any is accepted.
8. **Persona fidelity test:** switch across permissions, locale, semantic pins, and unresolved Conflicts; falsify if privilege rises, a pin changes silently, or a Conflict vanishes.
9. **Unseen-Protocol corpus:** submit valid new descriptors, malformed descriptors, unknown opcodes, and excessive bounds; falsify if valid compiled descriptors cannot route reproducibly or rejected ones execute partially.
10. **Replay test:** replay fixed deterministic inputs; falsify on digest divergence. For declared nondeterminism, falsify if observation receipts and replay limits are absent.

Passing these tests would establish only the stated operational properties, not the universal adequacy of the ontology or witness policies.

## 17. Strongest Critique and Open Questions

The strongest critique is that witnessed squares may relocate rather than solve semantic disagreement. A square is trustworthy only insofar as its relation predicates, context projection, and witness policy are trustworthy; the double-category form can give weak ontology alignment an undeserved mathematical appearance. Identity events, lax witnesses, quarantine paths, and provenance records also impose substantial storage and operational cost. Protocols whose useful behavior depends on open-ended search or opaque learned judgment may fit the bounded IR only after a lossy adapter, while strict effect separation can make common workflows slower.

The following global questions remain **OPEN** and are not resolved by N05:

- **OPEN:** Who has authority to issue and revise witness policies across trust domains?
- **OPEN:** What minimum shared ontology is required before two Protocols’ relation predicates are comparable?
- **OPEN:** When should a context projection convert plurality into Conflict, and who approves that projection?
- **OPEN:** Which lax or oplax witnesses are strong enough to authorize runtime mutation rather than only a view?
- **OPEN:** How should external nondeterministic observations be audited when seeds or source snapshots are unavailable?
- **OPEN:** What performance threshold would make square construction too costly for interactive use?
- **OPEN:** Can a weakened interchange requirement preserve adequate auditability for partial, asynchronous transitions?

## 18. Unsupported Protocol Classes

The initial implementation deliberately returns `OUT_OF_SCOPE` for:

1. arbitrary native-code or self-modifying Protocols outside a metered adapter;
2. Protocols without immutable identity, revision, descriptor digest, or declared effects;
3. unbounded recursion, unbounded joins, open-ended agent loops, or continuous streams without checkpoints;
4. undeclared network, filesystem, device, or human side effects;
5. semantic mutations aimed at aliases, wildcards, ranges, or an implicit “latest” target;
6. retroactive history deletion or mutation of prior events, evidence, conflicts, or semantic revisions;
7. cross-object mutations lacking atomic-bundle or explicit saga/compensation semantics;
8. irreversible physical-actuation Protocols without an external authorization and consequence model;
9. opaque external or learned Protocols that provide neither versioned observations nor uncertainty/provenance receipts when their output is used as proof;
10. Protocols requiring hidden global state that cannot be pinned or receipted;
11. proof systems whose verifier, axioms, or resource bounds cannot be registered exactly;
12. cross-context projections with no typed mapping for proposition, units, time, permissions, and policy;
13. Persona switches that require privilege elevation or silent suppression of unresolved statuses;
14. higher-dimensional compositions beyond witnessed squares unless a future, separately validated extension supplies finite encodings and executable laws.

Unsupported Protocols may still be described or stored as opaque evidence when permitted, but they are not executed and their outputs do not authorize object, runtime, or semantic changes.
