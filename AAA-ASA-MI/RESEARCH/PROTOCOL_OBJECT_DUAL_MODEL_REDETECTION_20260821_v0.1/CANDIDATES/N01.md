This candidate is deliberately bounded. It specifies behavior only for registered types, evidence boundaries, adapters, and resource limits. Its local design choices do not settle the project-wide open questions about relation versus event primacy, the ontological status of Protocols, router separation, cross-Protocol invariants, the semantic-mutation boundary, or a universal conflict algebra.

## 1. Object Model

The Object Model is an immutable, typed, attributed, provenance-bearing hypergraph snapshot:

`ObjectSnapshot = <ModelRef, TypeCatalog, V, R, A, Prov, Constraints>`.

- `ModelRef = <namespace, name, version, content_digest>` is an exact target. A version label without a digest is not exact enough for execution.
- `V` contains typed vertices. Core kinds are `Entity`, `Agent`, `Artifact`, `Place`, `TimeExtent`, `Value`, `Concept`, `Role`, and `OpaqueTerm`. Domain extensions must name their catalog and version.
- `R` contains reified relation assertions. Binary edges are only arity-two relations; they receive no privileged storage semantics.
- `A` contains assertion records about vertices, relations, identities, types, and derived claims. Assertions are never silently overwritten.
- `Prov` is a provenance subgraph, not a free-text citation field.
- `Constraints` contains machine-checkable local well-formedness rules. A constraint violation is not automatically a false world claim; it is a validation result scoped to a catalog and snapshot.

A relation assertion has the minimum shape:

```text
RelationAssertion {
  id: RelationId,
  relation_type: TypeRef,
  participants: nonempty ordered multimap<RoleRef, VertexRef>,
  attributes: map<AttributeRef, TypedValue>,
  polarity: POSITIVE | NEGATIVE,
  validity: Interval | PartialOrderWindow | UNSPECIFIED,
  assertion_scope: ScopeRef,
  worldview_scope: set<WorldviewRef>,
  provenance: nonempty set<ProvenanceRef>,
  predecessor_claims: set<AssertionRef>
}
```

Participant role, ordinal, and multiplicity are data. Repeated participants and n-ary relations are legal if the relation type permits them. Attributes are typed values with declared units, precision, and lexical form when those distinctions matter. Missing values are absent fields, never invented null facts.

A provenance record includes `source_ref`, `source_kind`, acquisition time, claimed observation time, acquisition Protocol, transform step, parent provenance references, content digest when available, custody note, license/access label, and an explicitly scoped trust annotation. Trust annotations are inputs to Protocols, not global truth scores. Derived claims carry a derivation DAG down to source or declared axiom leaves. If provenance is unavailable, the claim remains quarantined and cannot enter a provenance-required view.

Identity is not ordinary string equality. `same-identity-as`, `possibly-same-as`, `alias-of`, and `distinct-from` are separate relation types. Conflicting identity evidence preserves candidate identities. No merge occurs merely because two labels, embeddings, or external identifiers match.

The model's coverage boundary is explicit: its type catalogs, admitted sources, access rights, spatial/temporal window, and snapshot digest. Silence outside that boundary has no negative meaning.

## 2. Protocol Model

`Protocol` is a first-class variable in every interaction, not a fixed rendering mode. This candidate operationally stores a Protocol as a versioned `ProtocolSpec` plus an executable adapter reference; that is a local engineering treatment, not a project-wide resolution of whether Protocols are objects, procedures, institutions, perspectives, or hybrids.

```text
ProtocolSpec {
  ref: <protocol_id, version, spec_digest>,
  declared_kind: observational | inferential | narrative | control |
                 negotiation | simulation | composite | opaque,
  commitments: set<TypedCommitment>,
  input_signature: set<TypePattern>,
  output_schema: SchemaRef,
  capabilities: set<Capability>,
  applicability_predicate: RuleRef,
  selector_rules: ordered set<RuleRef>,
  transform_rules: ordered set<RuleRef>,
  status_policy: StatusPolicyRef,
  conflict_policy: ConflictPolicyRef,
  persona_policy: PersonaPolicyRef,
  effect_permissions: set<EffectClass>,
  inverse_contract: NONE | PARTIAL | MULTIVALUED | DECLARED_LAWS,
  adapter: <runtime, artifact_digest, entrypoint>,
  resource_envelope: <time, memory, result_count, recursion_depth>,
  access_requirements: set<AccessLabel>,
  determinism_claim: deterministic | seeded | external_nondeterminism,
  provenance: nonempty set<ProvenanceRef>
}
```

The bound runtime value is `ProtocolInstance = <ProtocolSpecRef, parameter_bindings, adapter_digest, seed, runtime_namespace>`. Bindings cannot alter the spec's effect permissions or type commitments. Any such alteration requires another spec version.

The mandatory adapter surface is:

```text
introspect() -> CapabilityManifest
validate(ObjectSummary, RequestSchema, ContextSchema) -> ValidationReport
plan(ObjectSnapshotRef, Query, Context) -> TypedPlan
execute(ReadOnlyObjectSlice, TypedPlan, Context) -> RawView
explain(RawView) -> DerivationBundle
inverse_candidates(ViewItem) -> set<ObjectRefWithLoss>  // may be empty
```

An adapter does not gain support merely by implementing these method names. Its manifest, types, permissions, resource envelope, provenance behavior, and conformance probes must validate. An unseen Protocol begins as `opaque/untrusted`: it may be described and statically checked, but it is not executed or treated as semantically compatible until its declared capabilities pass the relevant gates. Lack of a compatible adapter produces `OUT_OF_SCOPE`, not an improvised mapping.

## 3. Object↔Protocol Interaction Contract

Every request carries both an exact Object target and an explicit Protocol binding or Protocol variable:

```text
InteractionRequest {
  target: ModelRef,
  protocol: ProtocolSpecRef | ProtocolVariable,
  operation: OperationRef,
  query: TypedQuery,
  context: Context,
  persona_scope: set<PersonaRef>,
  worldview_scope: set<WorldviewRef>,
  requested_effects: set<EffectIntent>,
  output_expectation: SchemaRef,
  proof_mode: bounded | exploratory | streaming,
  resource_override: Optional<NarrowerResourceEnvelope>
}
```

```text
InteractionResult {
  target: exact ModelRef,
  protocol_instance: exact ProtocolInstanceRef,
  cases: nonempty set<ViewCase> | empty-with-status,
  claim_statuses: map<ScopedClaim, StatusEnvelope>,
  provenance_slice: ProvenanceGraph,
  conflicts: set<ConflictRecord>,
  object_to_view_map: multimap<ObjectRef, ViewItemRef>,
  view_to_object_candidates: multimap<ViewItemRef, ObjectRefWithLoss>,
  execution_trace: TraceRef,
  effects: set<EffectReceipt>,
  omissions: set<OmissionReason>,
  limitations: set<Limitation>
}
```

Object→Protocol interaction exposes type incidence, relation patterns, provenance classes, event deltas, and access-safe statistics so that applicability can be tested without dumping the whole graph. Protocol→Object interaction selects and derives from an immutable object slice, requests explicitly typed effects, and returns references and derivation witnesses. Neither direction implies a total inverse.

The transaction is `resolve → bind → validate → plan → authorize → execute → verify → commit-allowed-effects`. Each stage emits a receipt. Validation failure stops later stages. A mixed request is decomposed into separate effect intents; a harmless read cannot smuggle a semantic write. A Protocol may return several inverse candidates or none, and every candidate includes a loss descriptor. A round-trip law is enforced only when the spec declares the law and supplies a conformance test.

## 4. Relation/Event Treatment

N01 is relation-first locally. Persistent claims are reified relations; an Event is a typed, time-scoped bundle of relation assertions plus optional transition and causal claims:

`Event = <event_id, participant_relations, time_claims, precondition_claims, outcome_claims, ordering_claims, provenance>`.

This does not reduce an Event to a timestamped binary edge. Duration, partial order, concurrency, roles, failed transitions, claimed causes, and uncertain boundaries remain explicit. State is derived from relation histories under a named Protocol. It is not destructively overwritten by the latest arrival.

Relation/event responsiveness is provided by an incidence index and an event-delta interface. A new external observation is normalized into a quarantined delta, provenance-checked, and matched against subscriptions by affected relation type, participant role, interval, and scope. Protocols can declare triggers over this delta. They may materialize a new view immediately; incorporating the observation into the frozen ObjectSnapshot requires the successor path in Section 10.

Late, duplicate, and out-of-order events retain source sequence identifiers and claimed times. Deduplication is an assertion with evidence, not byte-level deletion. When a total order is unsupported, the model stores a partial order. A Protocol needing a total order must return multiple admissible linearizations, use an explicit tie policy, or report `NOT_PROVEN`/`OUT_OF_SCOPE` as appropriate; it may not fabricate temporal certainty.

Event-primary Protocols remain usable: they can project the relation store into event streams and treat event identity as their operative unit. The resulting view is tagged as a projection. Thus this candidate's storage and update discipline favors relations, while relation versus event primacy remains open beyond N01.

## 5. Activation and Routing

N01 uses a separate `ActivationPlanner` for inspectability, but separation is a replaceable local choice. The planner has no authority to change claim status, resolve conflict, or rewrite a Protocol. Its output is a set of typed candidate plans with reasons.

Activation proceeds by hard gates before preferences:

- Exact target digest and Protocol spec digest resolve.
- Input type patterns unify with an access-safe object summary.
- Required capabilities, output schema, persona/worldview handling, and effect permissions match.
- Adapter runtime is available and its artifact digest matches.
- Resource and access requirements fit the request.
- Static validation and Protocol-specific conformance probes pass.

If the request names a Protocol, no other Protocol is silently substituted. If it binds a Protocol variable, the planner returns all eligible candidates unless the request supplies a named preference policy. Preferences form a partial order over declared properties such as evidence requirements, latency bound, or view schema. Incomparability produces multiple plans; internal registry order is never a semantic tiebreaker.

For an unseen Protocol, the planner validates a signed or otherwise provenance-bearing capability manifest, places its adapter in a restricted runtime, and runs read-only probes on synthetic fixtures. Passing probes establishes only the tested interface claims. A missing capability, unknown type rule, opaque effect, or unverifiable output mapping yields `OUT_OF_SCOPE` with a gate report. The system does not infer compatibility from a similar name or embedding.

Routing is recorded in the trace: candidate set, rejected gates, preference policy, selected plan or retained alternatives, manifest digest, and planner version. A future architecture could embed routing inside Protocols or Objects, so router separation remains globally open.

## 6. Coexistence and Protocol Switching

Multiple Protocol instances coexist by reading the same exact ObjectSnapshot through isolated runtime namespaces. Each receives the same immutable source slice when access rules permit, but may select different relation patterns, status policies, contexts, Personas, and output schemas. Their views remain tagged products; they are not merged into a supposed consensus object.

Parallel coexistence returns `set<ViewCase>` with a `DisagreementMap` that identifies common source references, different selections, incompatible derivations, distinct assumptions, and non-alignable fields. Sequential composition is permitted only through a registered connector whose input schema, output schema, effect classes, order, and loss contract validate. `P∘Q` and `Q∘P` are distinct composite Protocols unless a declared and tested commutation law holds.

A switch from `P@v1` to `Q@v3` is a fresh materialization from the same source snapshot whenever possible. It does not translate P's rendered output and relabel it as Q. The switch receipt contains:

```text
SwitchReceipt {
  source_target, from_protocol, to_protocol,
  shared_object_refs, dropped_object_refs, newly_selected_object_refs,
  status_correspondences, untranslatable_constructs,
  assumption_delta, context_delta, loss_witness
}
```

Semantic fidelity is never asserted merely because both runs completed. When no cross-Protocol alignment rule exists, the result is two validly scoped views plus `untranslatable` markers. Runtime activation state can change during a switch; the ObjectSnapshot, Protocol specs, and earlier view remain unchanged.

## 7. Conflict and Disagreement

Conflict is recorded, scoped, and non-explosive. A minimum `ConflictRecord` contains the claim pattern, positive supports, negative supports, identity assumptions, time/scope overlap, Protocol, Persona/worldview scope, incompatibility rule, and provenance subgraph. Assertions from different scopes are not contradictory until an explicit alignment rule makes them comparable.

N01 supplies a minimal paraconsistent carrier for Protocols that opt into it. For a scoped proposition, evidence support is `(s+, s-)`:

- `(1,0)` supports the proposition.
- `(0,1)` supports its negation.
- `(1,1)` yields `CONFLICT`.
- `(0,0)` yields `UNKNOWN`, unless a complete bounded proof obligation justifies `NOT_PROVEN`.

Negation swaps the components; evidence union takes componentwise maximum. These operations do not rank sources, collapse scopes, or settle modal, probabilistic, deontic, temporal, or defeasible conflict. Protocols may register another conflict policy, but the policy and its crosswalk must be explicit. Results under non-alignable policies coexist without algebraic combination.

Confidence, majority count, recency, source authority, and Persona preference may be exposed as attributes or used by a declared Protocol. None silently deletes opposing support. Adjudication creates a new, scoped adjudication assertion with provenance; it retains links to the claims it accepts, rejects, or suspends. Cross-Protocol disagreement is distinct from within-Protocol logical conflict and is returned as a `DisagreementMap`.

This carrier is an operational N01 default, not a universal conflict algebra. Whether one algebra can span all Protocol classes remains open.

## 8. Contextual Materialization

Materialization is a typed function:

`materialize(ObjectSnapshot, ProtocolInstance, TypedQuery, Context) -> set<ViewCase> + receipts`.

`Context` is closed and versioned for a request. It may contain snapshot time, temporal focus, location, locale, units, granularity, purpose, risk tier, access principal, Persona references, worldview references, evidence boundary, rendering constraints, randomness seed, and resource budget. Undeclared ambient process state is not context.

The materializer executes distinct stages: incidence selection, access filtering, scope alignment, derivation, status evaluation, conflict packaging, schema projection, ordering, and rendering. Each view item is one of `SOURCE_REF`, `DERIVED`, `ASSUMPTION`, `PLACEHOLDER`, or `OMISSION_MARKER`. Derived items contain rule and parent references. A placeholder can communicate `UNKNOWN`; it is not an invented object value.

A `ViewArtifact` records exact target and Protocol digests, normalized context digest, output schema, source references, derived items, status envelopes, conflict/disagreement records, omissions with reasons, execution trace, creation time, expiry policy, and inverse candidates. Cache keys include all semantics-relevant inputs. A hit with a different Persona, worldview, access principal, evidence boundary, seed, or Protocol digest is forbidden.

Context may alter selection, derivation allowed by the Protocol, units, wording, ordering, and disclosure. It cannot retroactively alter base assertions or hide a conflict without emitting an omission marker. Materialization is plural: two contexts can yield two validly scoped views without either becoming the canonical world view. Unselected content is not thereby false or nonexistent.

## 9. Runtime State Change and Effect Typing

Every observable effect is classified before execution. N01 uses exactly four top-level effect classes:

| Effect class | Permitted target | Semantic consequence | Typical examples |
|---|---|---|---|
| `READ` | Exact Object/Protocol snapshot | None; a pure read has no persistent effect | Resolve refs, scan incidence index, validate types |
| `VIEW_MATERIALIZATION` | Derived artifact namespace | Creates a tagged derivative, never source membership | View artifact, explanation bundle, export, view cache fill |
| `RUNTIME_STATE_MUTATION` | Ephemeral operational namespace | Changes execution state but not answers attributable to the frozen target | Cursor, lease, subscription checkpoint, active-Protocol pointer, cache eviction, telemetry |
| `MODEL_SEMANTIC_MUTATION` | Object claims, identities, catalogs, constraints, Protocol specs/rules, or any durable input that can change answers | Changes semantic content | Add/retract assertion, alter relation type, identity merge, change conflict rule, modify Protocol code or permission |

Audit logging is not smuggled into `READ`; if persistent logging occurs, it is a separately declared `RUNTIME_STATE_MUTATION`. An incoming stream may be held as an external, tagged runtime overlay for responsive views. If the overlay affects a result, that result names the overlay digest separately from the frozen target. Moving any overlay claim into the model is `MODEL_SEMANTIC_MUTATION`.

Each intent is `EffectIntent<class, exact_target, operation, preconditions, idempotency_key, expected_postcondition>`. Authorization is per intent. Mixed operations are split rather than labeled only with their most severe effect. The frozen target denies every direct `MODEL_SEMANTIC_MUTATION` and points to Section 10.

The boundary between operational and semantic state can be contested: for example, a learned cache or long-lived subscription may influence later answers. N01's test is behavioral—if a durable change can change a semantically attributed answer with all declared request inputs fixed, it is semantic. This is a local enforceable rule, while the general mutation boundary remains open.

## 10. Semantic Mutation and Successor Models

N01 never modifies a frozen exact target in place. Every attempted `MODEL_SEMANTIC_MUTATION` must become a `SUCCESSOR_MODEL_PROPOSAL` naming a new exact target and explicit lineage:

```text
SUCCESSOR_MODEL_PROPOSAL {
  proposal_id,
  parent_exact_target: <namespace, name, version, content_digest>,
  proposed_exact_target: <namespace, name, new_version, proposed_content_digest>,
  typed_change_set,
  change_rationale,
  source_and_author_provenance,
  affected_assertions_types_protocols,
  compatibility_claims,
  migration_and_loss_plan,
  invariant_reports,
  conformance_reports,
  unresolved_conflicts,
  state: PROPOSED | ACCEPTED_AS_SEPARATE_TARGET | REJECTED | WITHDRAWN
}
```

The proposed target must have a new identity and content digest; it cannot reuse the parent's exact reference. Lineage is recorded by `successor-of` and `derived-from` relations and must be acyclic. Validation says only that declared checks passed. Acceptance is a separate governed action and never rewrites the parent.

Corrections are modeled in the proposed target by new assertions such as `supersedes`, `retracts`, or `narrows-scope`; predecessor provenance remains reachable. A changed type catalog, inference rule, conflict policy, Persona/worldview spec, adapter artifact, or Protocol permission is likewise a successor change. If new event observations are to become persistent model content, their delta and provenance enter the proposal.

Construction is staged: apply the typed delta in an isolated candidate namespace, compute the proposed digest, run invariants and affected Protocol conformance tests, publish the proposal and reports, then await external acceptance. Failure leaves the parent untouched. A caller lacking proposal authority receives an effect denial and `OUT_OF_SCOPE` for the mutation operation, not a best-effort write.

## 11. Status and Plural Semantics

Status is an envelope, not a Boolean:

`StatusEnvelope = <status, claim, target, Protocol, context, Persona/worldview scope, evidence boundary, time, reasons, provenance>`.

The core statuses are intentionally non-total:

- `SUPPORTED`: admitted support satisfies the Protocol's declared rule and no stronger global conclusion is implied.
- `REFUTED`: admitted support satisfies the declared rule for the scoped negation.
- `UNKNOWN`: decisive support is absent and completeness of the search/evidence boundary is not established.
- `CONFLICT`: admitted positive and negative support coexist under an explicit comparability and incompatibility rule.
- `NOT_PROVEN`: a named proof obligation was evaluated to completion within a closed, declared boundary and no proof was obtained. It is not negation.
- `OUT_OF_SCOPE`: the claim or operation cannot be formed or evaluated under the Protocol signature, access boundary, type catalog, or permission set.
- `MULTIPLE_VALID_VIEWS`: at least two `ViewCase` outputs satisfy their declared constraints under distinct bindings, contexts, Persona/worldview scopes, or admissible choices, and no requested rule selects one.

`UNKNOWN`, `NOT_PROVEN`, and `OUT_OF_SCOPE` are never converted to false. `CONFLICT` is never converted to a scalar confidence without a declared lossy projection. `MULTIPLE_VALID_VIEWS` is a meta-status over view cases, not evidence that all view claims are mutually consistent.

Each `ViewCase` lists its assumptions, scope, derivation, and limitations. Plural cases may share source claims or disagree about selection and inference. There is no default convergence function. A caller can request a named comparison or decision Protocol, whose output remains another scoped view rather than retroactive agreement.

## 12. Personas and Worldviews

Personas and worldviews are explicit, versioned, plural inputs. They are related but not collapsed:

```text
PersonaSpec = <id, version, communicative_goals, lexical_preferences,
               salience_policy, risk_tolerance, disclosure_preferences,
               allowed_worldview_refs, provenance>
WorldviewSpec = <id, version, commitments, admitted_sources,
                 interpretive_rules, conflict_priorities, scope, provenance>
```

A Persona governs communication and salience; a worldview supplies scoped interpretive commitments. Either may be absent if a Protocol declares absence valid. No demographic label silently selects one, and a Persona is not an authority score. Access control, safety constraints, provenance obligations, and mutation permissions dominate Persona preferences.

Requests may bind one Persona/worldview pair, a set, or variables. Multiple bindings execute in isolated cases and return a `DisagreementMap`; minority or incomparable cases remain visible subject to access rules. The engine does not average commitments or choose the most populous case. Switching Persona or worldview rematerializes from source and emits a delta/loss receipt, just like Protocol switching.

If a requested Persona or worldview is unknown, the system asks for an exact reference or returns `OUT_OF_SCOPE`; it does not substitute a culturally presumed default. Updating either spec is semantic mutation and therefore requires a successor proposal. This formalization can itself encode stereotypes or freeze fluid identities; Section 17 treats that as a central risk.

## 13. Candidate-local Invariants

These invariants define N01's conformance boundary; they are not asserted as universal cross-Protocol laws.

- `I1 Exact-target immutability`: bytes and semantic records reachable from a frozen `ModelRef` do not change.
- `I2 Provenance closure`: every admitted source claim has provenance; every derived claim reaches source or declared axiom leaves through a finite derivation DAG.
- `I3 Effect exhaustivity`: every effect intent has exactly one of the four top-level classes before authorization.
- `I4 No hidden fallback`: a named Protocol is never replaced without an explicit new binding and receipt.
- `I5 View/source separation`: no view item acquires source-model membership through materialization or caching.
- `I6 Conflict preservation`: an admitted opposing support remains reachable from any result that summarizes its conflict set.
- `I7 Scope preservation`: target, Protocol, context, Persona/worldview, evidence boundary, and time accompany every status.
- `I8 Identity caution`: uncertain identity cannot collapse vertices; merges require a semantic successor and retained evidence.
- `I9 Switch accounting`: every Protocol or Persona/worldview switch emits selected, dropped, added, and untranslatable references plus a loss witness.
- `I10 Access non-amplification`: a Protocol, view, inverse map, trace, or disagreement report cannot expose a source beyond the request's access principal.
- `I11 Determinism disclosure`: equal declared inputs either reproduce the result or record the seed/external nondeterminism and return variant cases.
- `I12 Bounded claims`: a result names its admitted type, evidence, resource, and temporal bounds.
- `I13 Lineage`: every accepted successor names an exact parent, retains predecessor links, and cannot form a lineage cycle.
- `I14 Unsupported honesty`: failed compatibility is `OUT_OF_SCOPE` with gate reasons, never synthetic success.
- `I15 Composition explicitness`: Protocol composition order and connector digest are part of the composite identity.

Potential cross-Protocol invariants beyond access, provenance transport, exact targeting, and loss disclosure are left open. Even those four may be inexpressible for some Protocol classes; such a class is unsupported rather than coerced into compliance.

## 14. Failure Boundaries

Failures return a typed `FailureEnvelope<stage, code, exact inputs, partial outputs, effects_committed, rollback_state, retryability, status, evidence>`.

- Type mismatch, illegal arity, invalid role multiplicity, or dangling exact reference stops admission; raw input is quarantined with provenance.
- Missing required provenance stops a claim from entering provenance-required evaluation. The system may report its existence as quarantined metadata if access permits.
- Ambiguous identity preserves candidate bindings and may produce `MULTIPLE_VALID_VIEWS`; it never guesses a merge.
- Unknown or unverifiable Protocols stop at manifest/probe validation with `OUT_OF_SCOPE`.
- Adapter crashes, timeouts, memory exhaustion, recursion limits, and result caps are isolated to the Protocol runtime. Partial search yields `UNKNOWN` plus a termination reason, not `NOT_PROVEN`.
- Unauthorized effects are denied before execution. If an adapter attempts an undeclared effect, its run is terminated and its outputs are untrusted.
- Event duplicates, clock skew, and partial order remain explicit. No ingestion clock becomes event truth by default.
- External source unavailability yields `UNKNOWN` or a retrieval failure scoped to that source; cached evidence is labeled with its acquisition time.
- Nondeterministic output without a declared seed or external-nondeterminism contract fails verification.
- A malformed derivation DAG, provenance cycle where acyclicity is required, or missing parent invalidates the affected derived item.
- Cyclic Protocol composition without an explicit fixed-point contract is rejected.
- Failed inverse mapping returns no candidate plus a loss reason; it does not fabricate an object reference.
- Successor build or invariant failure leaves the proposal non-accepted and the parent unchanged.
- Cache key mismatch, stale access labels, or digest mismatch invalidates the cache entry without changing semantic content.
- Conflicting access and disclosure rules fail closed. Conflict details may be redacted, but the result must indicate that restricted material affected completeness when policy permits that disclosure.

Recovery is stage-specific. Retrying a `READ` is safe against the same digest; retrying materialization requires the same idempotency key; runtime recovery may advance a checkpoint; semantic recovery always creates or revises a successor proposal, never the frozen parent.

## 15. Executable Implementation Contact

A minimal implementation can use relational tables while retaining hypergraph semantics:

```sql
CREATE TABLE vertex (
  model_digest TEXT, vertex_id TEXT, type_ref TEXT, attrs_json TEXT,
  PRIMARY KEY (model_digest, vertex_id)
);
CREATE TABLE relation_assertion (
  model_digest TEXT, relation_id TEXT, relation_type TEXT, polarity TEXT,
  attrs_json TEXT, validity_json TEXT, scope_ref TEXT,
  PRIMARY KEY (model_digest, relation_id)
);
CREATE TABLE participant (
  model_digest TEXT, relation_id TEXT, role_ref TEXT, ordinal INTEGER,
  vertex_id TEXT,
  PRIMARY KEY (model_digest, relation_id, role_ref, ordinal)
);
CREATE TABLE provenance (
  model_digest TEXT, provenance_id TEXT, source_ref TEXT,
  acquisition_protocol TEXT, parent_json TEXT, payload_digest TEXT,
  attrs_json TEXT,
  PRIMARY KEY (model_digest, provenance_id)
);
CREATE TABLE assertion_provenance (
  model_digest TEXT, assertion_id TEXT, provenance_id TEXT,
  PRIMARY KEY (model_digest, assertion_id, provenance_id)
);
```

`model_digest` participates in every semantic primary key. Database permissions deny `UPDATE` and `DELETE` on frozen partitions. Candidate successor partitions are separate and become addressable only after digest calculation.

The execution kernel can be implemented behind the following Python-shaped boundary:

```python
from dataclasses import dataclass
from typing import Literal, Protocol, FrozenSet

Effect = Literal[
    "READ", "VIEW_MATERIALIZATION", "RUNTIME_STATE_MUTATION",
    "MODEL_SEMANTIC_MUTATION"
]
Status = Literal[
    "SUPPORTED", "REFUTED", "UNKNOWN", "CONFLICT", "NOT_PROVEN",
    "OUT_OF_SCOPE", "MULTIPLE_VALID_VIEWS"
]

@dataclass(frozen=True)
class ModelRef:
    namespace: str
    name: str
    version: str
    content_digest: str

@dataclass(frozen=True)
class EffectIntent:
    kind: Effect
    exact_target: str
    operation: str
    idempotency_key: str

@dataclass(frozen=True)
class Request:
    target: ModelRef
    protocol_digest: str
    query: object
    context: object
    effects: FrozenSet[EffectIntent]

class Adapter(Protocol):
    def validate(self, summary: object, request: Request) -> object: ...
    def plan(self, snapshot: ModelRef, query: object, context: object) -> object: ...
    def execute(self, readonly_slice: object, plan: object, context: object) -> object: ...
    def explain(self, raw_view: object) -> object: ...

def run(request: Request, adapter: Adapter, store, policy):
    snapshot = store.resolve_exact(request.target)       # READ
    if snapshot is None:
        return failure("RESOLVE", "UNKNOWN_TARGET", "OUT_OF_SCOPE")
    report = adapter.validate(snapshot.safe_summary(), request)
    if not report.ok:
        return failure("VALIDATE", report.codes, "OUT_OF_SCOPE")
    for intent in request.effects:
        if intent.kind == "MODEL_SEMANTIC_MUTATION":
            return successor_required(request.target, intent)
        policy.authorize_exact(intent, request, adapter)
    plan = adapter.plan(request.target, request.query, request.context)
    source_slice = store.readonly_slice(request.target, plan.read_set)
    raw = adapter.execute(source_slice, plan, request.context)
    derivation = adapter.explain(raw)
    verify_provenance_closure(raw, derivation, source_slice)
    verify_effect_receipts(request.effects)
    return package_cases(raw, derivation, request, plan)
```

The names `failure`, `successor_required`, and verification functions are required implementation seams, not permissive stubs: conformance tests must prove that no adapter can obtain a writable frozen-model handle. A reference engine should expose an append-only trace and property-test invariants I1–I15.

A four-case smoke fixture is mandatory: two provenance-distinct opposing claims return `CONFLICT`; an unseen manifest missing an inverse/loss contract is rejected for an inverse-required request; switching two valid Protocols retains distinct views and source refs; and a requested assertion write returns a `SUCCESSOR_MODEL_PROPOSAL` without changing the parent digest.

## 16. Falsification Plan

N01 is rejected or narrowed if any of these tests fails under the stated implementation boundary:

- `F1 Frozen-byte test`: after arbitrary allowed requests, every byte reachable from the parent semantic partition and its content digest is unchanged.
- `F2 Effect escape test`: a hostile adapter cannot write a model table, mutate a Protocol spec, or cause an undeclared persistent effect through logging, caching, callbacks, or inverse methods.
- `F3 Provenance property`: every output claim either maps to source claims with a finite derivation DAG or is labeled assumption/placeholder/omission. Random graph generation must find no orphan derived claim.
- `F4 Conflict retention`: adding admissible opposing evidence changes `(1,0)` to `(1,1)` and exposes both provenance branches; no unrelated proposition becomes derivable solely from the conflict.
- `F5 Scope separation`: identical lexical claims in non-aligned scopes do not become a conflict until a declared comparability rule is supplied.
- `F6 Event responsiveness`: for every subscribed relation-type/role pattern in a bounded fixture, an admitted external delta invalidates exactly the affected materialization keys and retains late/duplicate ordering metadata.
- `F7 Context isolation`: varying any semantics-relevant Context field cannot hit the prior cache key; irrelevant renderer-only fields can be shown, by declared schema, not to alter claim status.
- `F8 Switch-loss test`: Protocol switching never gains a source mapping absent from the source run, and every dropped or untranslatable construct appears in the receipt.
- `F9 Plurality test`: incomparable Protocol, Persona, worldview, or identity bindings return distinct cases without registry-order selection or averaging.
- `F10 Unknown honesty`: incomplete search produces `UNKNOWN`; only a completed declared proof boundary produces `NOT_PROVEN`; signature failure produces `OUT_OF_SCOPE`.
- `F11 Unseen-Protocol test`: a conforming novel manifest can pass only declared probes and execute read-only, while a name-similar incompatible manifest receives no fallback privileges.
- `F12 Successor lineage test`: accepted successors always have new exact targets, exact parents, acyclic lineage, retained predecessor links, and passing invariant receipts.
- `F13 Access test`: views, provenance slices, traces, conflicts, inverse candidates, and disagreement maps reveal no unauthorized source or side-channel count beyond policy.
- `F14 Reproduction test`: deterministic Protocols reproduce case digests for equal declared inputs; seeded Protocols reproduce under the same seed; external nondeterminism is visible in the result.

Performance claims require workload-specific thresholds and are not made here. If event latency, graph scale, or adapter isolation cannot meet a deployment's separately declared bounds, N01 is `OUT_OF_SCOPE` for that deployment rather than declared successful by architecture alone.

## 17. Strongest Self-Critique

The relation-first choice may be the wrong substrate for processual, performative, or constitutive phenomena. Decomposing an Event into relations can preserve typed roles and provenance yet still lose the fact that occurrence, sequence, and enactment are primary. An event-first or process-calculus model may be less distorting.

Making Protocols inspectable through `ProtocolSpec` risks domesticating social, tacit, embodied, negotiated, or adversarial Protocols into a capability vocabulary authored by the system. The `ActivationPlanner` is not neutral: its gates and type unification embed commitments even if it never resolves claims. Unseen Protocol support therefore covers only manifests that can enter this vocabulary; it is not open-ended understanding.

Successor-only semantic persistence provides strong auditability but is operationally expensive. High-rate observations can create a proliferation of snapshots or leave important data in tagged overlays. The behavioral mutation boundary is also contestable: learned indexes, caches, prompts, and resource scheduling may influence answers even when labeled runtime state.

The default two-component conflict carrier is too weak for graded probability, belief revision, non-monotonic exceptions, legal priority, deontic inconsistency, counterfactuals, and temporal change. Permitting Protocol-specific algebras preserves plurality but makes cross-Protocol comparison shallow. The candidate may end up returning carefully tagged parallel outputs instead of enabling meaningful translation.

Protocol switching can guarantee accounting and explicit loss only within registered mappings. It cannot guarantee semantic fidelity between unrelated Protocols. A loss witness may document distortion without preventing it, and a shared object reference may conceal different category boundaries.

Provenance adds accountability, not truth. Long derivation chains can be expensive, cyclic source ecosystems can defeat simple custody stories, and trust annotations can launder institutional bias. Personas/worldviews create similar risks: formalizing them can stereotype people, freeze fluid commitments, or privilege the author of the schema.

Exact digests do not by themselves make external dependencies reproducible. Hardware, remote services, clock behavior, undisclosed model weights, and nondeterministic runtimes can defeat replay. Hypergraph incidence joins and provenance closure may also be too costly at scale. If these limitations dominate, N01's clean invariants become documentation around an impractical or exclusionary core.

## 18. Unsupported Protocol Classes

The following classes are unsupported by the frozen N01 target unless a successor adds a typed, tested extension. The engine returns `OUT_OF_SCOPE` with missing capabilities and performs no substitute execution.

- Protocols without a machine-readable input/output signature, effect declaration, exact version/artifact reference, and minimum provenance contract. They may be stored as opaque descriptions only.
- Protocols demanding in-place mutation, deletion, history rewriting, self-modifying permissions, or reuse of the frozen target identity.
- Protocols whose code cannot be isolated from model storage or whose undeclared effects cannot be intercepted within the deployment boundary.
- Protocols requiring an infallible oracle, solution of undecidable problems, exhaustive search over an unbounded domain, or a universal closed-world guarantee.
- Protocols requiring hard real-time guarantees, specialized sensors, proprietary drivers, cryptographic keys, or remote services that the declared runtime does not possess.
- Protocols whose essential inputs are tacit, embodied, private, or institutionally enacted but have no admitted capture and consent contract.
- Protocols with semantic primitives absent from the registered type catalogs and no loss-declaring adapter—for example, unsupported continuous, quantum, higher-order, non-well-founded, or infinite-arity structures.
- Protocols that require probabilistic, modal, deontic, defeasible, legal-priority, or belief-revision conflict behavior but provide neither an executable policy nor a crosswalk to the result envelope.
- Protocols that require total event order where only partial-order evidence exists and reject multiple linearizations or explicit uncertainty.
- Protocols that erase provenance, opposing evidence, access scope, Persona/worldview scope, or switch loss while claiming a faithful semantic result. A visibly lossy presentation may still run as a view if it declares the omissions.
- Protocols that demand one canonical Persona, worldview, or consensus result without a named decision rule and retained dissent cases.
- Protocols whose output cannot be tied to source references, declared axioms, assumptions, or explicit placeholders at the granularity required by the requested operation.
- Protocols with cyclic composition and no bounded fixed-point semantics, or with nondeterminism that cannot be seeded or disclosed.
- Protocols whose access or disclosure behavior would leak restricted sources through values, counts, provenance, traces, conflicts, inverse mappings, timing, or error differences.
- Protocols requiring guaranteed semantics-preserving translation to an unrelated Protocol when no tested alignment law exists.

Unsupported today does not mean globally impossible. Admission requires an explicit new exact target, successor lineage, new capability/type commitments, executable conformance tests, failure boundaries, and a stated loss model; the frozen N01 proposal itself remains unchanged.
