Scope: N03 proposes a bounded implementation architecture, not a universal representation. It gives operational primacy to immutable events and process replay while retaining explicit object definitions, first-class Protocol definitions, contextual views, and plural interpretations. The globally open questions—relation versus event primacy, Protocol ontological status, router separation, cross-Protocol invariants, mutation boundaries, and conflict algebra—remain open outside this candidate; N03 makes local choices so that it can be implemented and falsified.

## 1. Object Model

An Object is not merely its latest state and not merely an untyped event stream. It has an explicit, versioned definition and a temporal runtime identity:

```text
ExactModelTarget = {model_id, semantic_version, content_digest}
ObjectRef        = {model_target, object_type_id, object_id}
ObjectDefinition = {
  object_type_id,
  field_schema,
  identity_rules,
  lifecycle_machine_id,
  relation_port_schema,
  invariant_ids,
  admissible_event_types
}
ObjectRuntime = {
  object_ref,
  stream_revision,
  lifecycle_state,
  field_projection,
  active_relation_projection,
  last_event_cut
}
```

`ObjectDefinition` belongs to the frozen semantic model. `ObjectRuntime` is a replayable projection at an explicit event cut. Object identity is stable only within its `ExactModelTarget`; cross-model identity requires an explicit lineage mapping and is never inferred from equal names.

Every object stream contains immutable `EventEnvelope` records with at least:

```text
{event_id, object_ref, stream_revision, event_type, payload_schema,
 payload, observed_at, effective_at, recorded_at, causation_id,
 correlation_id, actor_ref, persona_ref?, protocol_ref?, context_ref,
 evidence_refs[], integrity_digest}
```

The three times are distinct: `effective_at` is when the event claims to apply in the modeled world, `observed_at` is when an observer obtained it, and `recorded_at` is when the store accepted it. No timestamp is silently substituted for another. A current state is one permitted projection, not the Object's complete meaning.

Relations are explicit typed records, not anonymous foreign keys:

```text
RelationAssertion = {
  relation_type_id, subject_ref, object_ref,
  valid_interval, assertion_event_id, status,
  protocol_ref?, persona_ref?, context_ref, evidence_refs[]
}
```

Their provenance and temporal interval are mandatory. A relation projection may contain mutually incompatible assertions; storage does not force a single edge.

## 2. Protocol Model

A Protocol is a first-class, versioned semantic and executable model. It is neither a string tag nor unrestricted application code. N03 represents it with:

```text
ProtocolRef = {protocol_id, protocol_version, protocol_digest}
ProtocolDefinition = {
  protocol_ref,
  declared_protocol_classes[],
  descriptor_schema_version,
  applicability_predicate,
  accepted_object_types[], accepted_event_types[], accepted_relation_types[],
  required_context_schema,
  event_grammar,
  transition_rules,
  relation_rules,
  read_surfaces[], materializers[], command_types[],
  status_vocabulary_mapping,
  conflict_policy,
  persona_compatibility_predicate,
  capability_manifest,
  determinism_contract,
  resource_limits,
  proof_obligations[],
  implementation_artifact_digest
}
```

Protocol definitions are data plus a sandboxed implementation artifact. The data is inspectable and signed; the artifact must conform to the declared inputs, outputs, effects, and resource bounds. Protocol-local concepts remain in a Protocol namespace. The core does not pretend to understand every Protocol's internal ontology.

Heterogeneous or previously unseen Protocols can be admitted only through a minimal descriptor contract: stable identity and digest, typed envelopes, declared capabilities, context requirements, deterministic-or-recorded behavior, status mapping, and effect boundaries. Admission means the core can contain, route, replay, and expose the Protocol's results; it does not mean the core has semantically reduced those results to a universal vocabulary. If the descriptor is incomplete or its Protocol class is unsupported, the Protocol is quarantined and its applicability is reported as `OUT_OF_SCOPE`, not guessed.

## 3. Bidirectional Object↔Protocol Interaction

Interaction is mediated by immutable records and exact targets:

```text
Object -> Protocol:
  ObjectEvent | ObjectProjectionRef | RelationAssertionSet | ContextBundle

Protocol -> Object:
  ReadResult | ViewFragment | RuntimeCommandProposal |
  RelationAssertionProposal | EvidenceClaim | StatusClaim
```

An Object event can activate one or more Protocols. A Protocol can interpret that event, request an Object read at a declared cut, propose a new runtime command, or assert a contextual relation. A Protocol never writes an Object snapshot directly. Accepted commands are validated by the target Object's lifecycle machine and committed as new events in a transaction that also records the triggering `InteractionRecord`.

```text
InteractionRecord = {
  interaction_id, input_event_ids[], object_refs[], protocol_ref,
  exact_model_target, context_ref, persona_refs[],
  router_decision_id, output_claim_ids[], proposed_command_ids[],
  execution_digest, outcome_status
}
```

This provides bidirectionality without recursive hidden mutation. `causation_id`, depth, and deduplication key are required for Protocol-produced commands. Cycles are permitted only as finite, auditable process loops with a declared termination rule and budget. An exhausted budget produces a failure event; it does not truncate silently.

## 4. Relation/Event Responsiveness

N03 locally chooses event primacy for operational state: accepted changes enter as events, and state or relation views are replayed from them. This is a candidate choice, not a claim that relations are metaphysically secondary.

Relation changes are represented as `RelationAsserted`, `RelationRetracted`, `RelationQualified`, or `RelationDisputed` events. Conversely, relation projections are active inputs to transition guards. A new relation assertion can therefore enable, block, or compensate a process transition and can cause a typed follow-on event. Each reaction names the relation version and event cut it used.

Responsiveness is temporal rather than merely arrival-ordered. Per-stream revisions provide local order; causal links provide partial order across streams; watermarks define when a materializer regards an event window as provisionally closed. Late events never rewrite the log. They cause historical rematerialization, a correction projection, or a compensating event according to the active Protocol. Views expose whether their cut is `OPEN`, `WATERMARKED`, or `FINAL_BY_PROTOCOL`; the core itself does not declare world history finally complete.

Static or relation-first source systems may enter through adapters that emit provenance-preserving assertion events. If eventization would destroy relevant relational meaning, that adapter fails conformance and the source is unsupported rather than approximately coerced.

## 5. Protocol Routing

N03 uses a separate `ProtocolRouter` component. Its separation is an auditable design choice on an otherwise open global axis. The router performs eligibility and dispatch; it is forbidden to reinterpret Protocol results or alter Object semantics.

Routing inputs are `{exact_model_target, object/event/relation type IDs, protocol descriptors, context schema, persona refs, requested operation, capability policy}`. Routing output is an immutable `RoutingDecision`:

```text
{router_decision_id, input_digest, candidate_protocol_refs[],
 selected_protocol_refs[], rejected[{protocol_ref, reason_code}],
 fanout_policy, policy_version, decided_at}
```

Matching occurs in this order: descriptor validity, exact model compatibility, type compatibility, required context availability, Persona compatibility, capabilities, then the Protocol's pure applicability predicate. No heuristic ranking can convert incompatibility into compatibility.

Ambiguity defaults to explicit fan-out. Several eligible Protocols may run in isolated namespaces, and all selected refs remain visible. A context may request an explicit single-Protocol policy, but the discarded alternatives and the selection rule remain in the decision record. Unseen Protocols are registered without router code changes when they satisfy the descriptor contract. A new Protocol class requiring new effect types or routing semantics requires a successor model or router version; it is not dynamically smuggled through a generic payload.

## 6. Coexistence of Heterogeneous Protocols

Protocol outputs coexist in a `ProtocolResultSpace` keyed by `{ObjectRef, ProtocolRef, ContextRef, PersonaRef, event_cut}`. Shared Object identity permits comparison, but does not merge Protocol-local meanings.

Cross-Protocol exchange requires an explicit, versioned `BridgeDefinition` with source type, target type, transformation, loss declaration, proof obligations, and provenance. A bridge output is a new derived claim; it does not erase its source. Lossy bridges must label the lost dimensions and cannot be used for semantic mutation.

No convergence operator is mandatory. Coexistence can yield:

- independent compatible views;
- overlapping but non-equivalent views;
- contextual alternatives;
- explicit contradiction;
- absence of a valid bridge; or
- an unsupported comparison.

Cross-Protocol invariants are deliberately restricted to the small execution kernel: immutable identifiers and history, exact targeting, provenance, effect typing, replay requirements, isolation, and status preservation. Domain invariants remain Protocol- or Object-definition-specific. N03 does not assert that all Protocols share a substantive worldview.

## 7. Conflict Algebra

The storage unit for interpretation is an `EvidenceClaim`:

```text
{claim_id, proposition_key, value, polarity, protocol_ref,
 persona_ref?, context_ref, valid_interval, evidence_refs[],
 warrant_level, derivation_ref, status}
```

N03's conflict combination is a tagged set algebra, not last-writer-wins and not a total truth lattice:

1. Claims with different proposition keys, contexts, validity intervals, or declared semantic namespaces are retained as distinct views.
2. Equivalent values with compatible polarity may aggregate provenance, but source claims remain addressable.
3. Incompatible values or opposing polarities for the same normalized proposition, overlapping interval, context, and semantic namespace yield `CONFLICT({claim_ids})`.
4. No admissible claim yields `UNKNOWN`, unless the query itself is outside the evaluator's declared domain.
5. An attempted proof with insufficient warrant yields `NOT_PROVEN`; this is not equivalent to false or unknown.
6. An evaluator that declares no competence yields `OUT_OF_SCOPE`.
7. Different valid contextual or Persona-indexed conclusions yield `MULTIPLE_VALID_VIEWS({view_ids})`, not `CONFLICT`, unless a requested comparison supplies an explicit common frame in which they contradict.

Protocol-local conflict policies may rank, defer, or display claims within a materialized view, but they cannot delete underlying alternatives. A precedence result is labeled `SELECTED_UNDER_POLICY`, never promoted to context-free truth. If two conflict policies themselves disagree, their outputs remain separate Protocol results. N03 therefore defines operational conflict preservation while leaving the adequacy of any universal conflict algebra open.

## 8. Context-Sensitive View Materialization

A view is a derived artifact addressed by the complete key:

```text
MaterializationKey = {
  exact_model_target,
  ordered_object_refs[],
  protocol_refs[],
  context_digest,
  persona_refs[],
  event_cut,
  relation_cut,
  materializer_version,
  query_digest
}
```

`ContextBundle` is typed and immutable for a materialization. It may contain jurisdiction, task, time horizon, observer position, requested granularity, admissible evidence policy, locale, and explicit assumptions. Unspecified fields are marked absent; defaults are named and versioned, never ambient process variables.

Materialization is pure with respect to model and runtime state: it reads immutable events and definitions and returns `{view_id, key, claims, statuses, provenance_closure, assumptions, warnings, completeness}`. Caches are keyed by the full materialization key. A context or Persona change causes rematerialization, not patching of a prior view.

The result may contain multiple valid views and conflicts. It must distinguish “no event found at this cut” from “negative event found,” and “projection incomplete” from “Object absent.” A view lacking required context returns `UNKNOWN` or `OUT_OF_SCOPE` according to the relevant descriptor; it may not invent a default merely to produce a value.

## 9. Runtime Change and Typed Operations

Every request is classified before execution as exactly one of four operation classes:

| Operation class | May read events | May create a derived view | May append runtime events | May alter frozen semantics |
|---|---:|---:|---:|---:|
| `READ` | yes | no | no | no |
| `VIEW_MATERIALIZATION` | yes | yes | no | no |
| `RUNTIME_STATE_MUTATION` | yes | optional validation view | yes | no |
| `MODEL_SEMANTIC_MUTATION` | no direct execution | no | no | forbidden on a frozen model |

`READ` returns stored records or an existing projection at an exact cut. `VIEW_MATERIALIZATION` derives a new immutable view. `RUNTIME_STATE_MUTATION` submits a typed command against `{ObjectRef, expected_stream_revision, exact_model_target, ProtocolRef?, ContextRef, PersonaRef?, idempotency_key}`. It passes authorization, schema, lifecycle, invariant, Protocol capability, and conflict preconditions before one or more runtime events are appended.

Requests that mix classes are decomposed into explicit stages or rejected. A read cannot trigger a hidden write; materialization cannot “repair” runtime state; a runtime command cannot alter a field schema, transition rule, Protocol descriptor, status meaning, invariant, router semantic policy, or bridge definition. Those are semantic changes. Authorization changes to actual runtime actors may be events, but changing the authorization model is semantic.

## 10. Frozen Semantic Change and Successor Models

Once this proposal's semantic model is frozen, `MODEL_SEMANTIC_MUTATION` has no executable endpoint. The sole accepted representation of desired semantic change is:

```text
SUCCESSOR_MODEL_PROPOSAL = {
  proposal_id,
  predecessor_exact_target,
  successor_exact_target,
  lineage_edge_type,
  complete_successor_definition_digest,
  change_set,
  rationale,
  affected_object_protocol_bridge_ids[],
  compatibility_claims[],
  migration_plan,
  validation_evidence_refs[],
  proposer_ref,
  created_at
}
```

Both predecessor and successor are exact targets `{model_id, semantic_version, content_digest}`. A name, “latest,” or version range is not an exact target. The successor receives a new semantic version and digest; incompatible identity semantics require a new `model_id`. Lineage is explicit, directed, and acyclic.

Submitting a proposal changes neither model. Validation, acceptance, activation, and migration are separate recorded governance events. Activation never edits predecessor events. Migration replays or translates into successor-addressed streams using a versioned mapper and emits provenance links to every source record. Failed or lossy translations remain reported; they are not silently defaulted. Historical reads continue targeting the predecessor. This preserves a frozen model while allowing an inspectable successor lineage.

## 11. Status and Plural Semantics

N03 reserves and preserves these non-interchangeable statuses:

| Status | Meaning | Forbidden inference |
|---|---|---|
| `UNKNOWN` | Relevant question, but no admissible determination is available at the stated cut/context | false, absent, or impossible |
| `CONFLICT` | Incompatible admissible claims exist in a declared comparison frame | either side wins |
| `NOT_PROVEN` | A proof/warrant was required and attempted or evaluated, but the threshold was not met | disproven |
| `OUT_OF_SCOPE` | The selected Object/Protocol/evaluator declares no competence for the question | unknown within scope |
| `MULTIPLE_VALID_VIEWS` | More than one contextual or worldview-indexed result is valid without a required common-frame contradiction | mergeable consensus |

Statuses are values with provenance, evaluator, context, and event cut—not nullable fields. A Protocol may have richer local statuses, but its descriptor must state whether and how each maps to the reserved set. Non-lossless mappings retain the local status alongside `OUT_OF_SCOPE` for the common status surface.

Plurality is structural: a query result is a set of view records, not a scalar plus footnote. APIs may request a display selection, but must return the selection policy and handles to unselected views. No aggregation function is allowed to turn plurality into convergence unless the query explicitly names that function and frame.

## 12. Personas and Worldviews

A `Persona` is a first-class interpretive profile, distinct from authentication identity:

```text
PersonaRef = {persona_id, persona_version, persona_digest}
PersonaDefinition = {
  worldview_assumptions[], admissible_evidence_policy,
  salience_policy, protocol_preferences[], conflict_display_policy,
  prohibited_inferences[], locale?, disclosure_policy
}
```

Personas may share observations while differing on admissible evidence, relevant relations, preferred Protocols, or conclusions. Their claims are indexed by `PersonaRef`. N03 never requires Personas to negotiate a common view.

Persona switching creates a new materialization key and replays from the same declared event cut. It does not translate the previous Persona's conclusions into the next Persona's vocabulary, mutate prior claims, or carry over an implicit conflict resolution. The returned transition receipt contains `{from_persona_ref, to_persona_ref, unchanged_event_cut, changed_context_fields, new_view_ids}`. If exact replay is impossible because the target Persona or Protocol artifact is unavailable, switching fails visibly; it does not approximate.

Cross-Persona comparison is itself a Protocol operation with an explicit frame. Without such a frame, divergent outputs are `MULTIPLE_VALID_VIEWS`. Authentication and permissions may restrict which evidence a Persona can see, but access filtering is disclosed in `completeness`; it cannot masquerade as lack of evidence.

## 13. Invariants

The implementation must continuously enforce:

1. **Append-only history:** accepted events are immutable; corrections are additional events.
2. **Exact targeting:** every Object, command, Protocol run, view, bridge, and successor proposal names exact model and artifact digests.
3. **Deterministic replay:** equal inputs, artifacts, context, Persona, and cut produce equal output digests; declared nondeterministic observations must be captured as input events.
4. **Bitemporal integrity:** effective, observed, and recorded times remain distinguishable; projection APIs declare which they use.
5. **Causal auditability:** derived outputs close over their triggering events, rules, Protocol, Persona, and context.
6. **No semantic writes to frozen targets:** semantic change can exist only as an inert successor proposal until separately accepted.
7. **Effect confinement:** Protocol code can emit only capabilities declared in its manifest; no direct store or network mutation.
8. **Projection purity:** materializers append no runtime events and read no undeclared ambient state.
9. **Plurality preservation:** conflicts, unknowns, and unselected valid views remain addressable after selection or bridging.
10. **Namespace isolation:** Protocol-local terms do not collide by label alone.
11. **Idempotent command handling:** duplicate idempotency keys against the same exact target cannot create duplicate effects.
12. **Revision safety:** runtime commands fail on an unexpected stream revision unless their declared commutativity rule validates rebasing.
13. **Lineage acyclicity:** successor and translation graphs contain no ancestry cycles.
14. **Finite reaction:** each Protocol reaction declares depth, time, memory, and event-emission limits.
15. **Unknown safety:** missing context, missing mappings, or missing evidence cannot become a positive or negative fact through defaults.

Cross-Protocol domain invariants are not assumed. They become enforceable only when a named Bridge or Object definition declares their shared frame and validation procedure.

## 14. Failure Boundaries

N03 fails closed at semantic and effect boundaries, but preserves partial evidence:

- **Unknown schema or Protocol class:** quarantine the envelope; return `OUT_OF_SCOPE` with the unsupported descriptor and no execution.
- **Digest or signature mismatch:** reject execution and record an integrity failure outside the affected Object stream.
- **Late or causally reordered event:** retain it, invalidate affected caches, and rematerialize or compensate under the active Protocol.
- **Projection divergence:** stop serving the suspect projection, replay independently, and expose `UNKNOWN` for derived fields until digest agreement.
- **Missing context:** return `UNKNOWN` or `OUT_OF_SCOPE`; do not select ambient defaults.
- **Protocol timeout/resource exhaustion:** terminate the sandbox, append no proposed runtime effects, and retain a failed `InteractionRecord`.
- **Nondeterministic undeclared behavior:** fail conformance and quarantine that Protocol version.
- **Reaction loop:** enforce the declared budget and emit `REACTION_BUDGET_EXHAUSTED`.
- **Concurrent runtime mutation:** reject on revision mismatch or apply only a declared commutative reducer.
- **Bridge loss not declared:** reject the bridge output.
- **Conflicting claims:** preserve the set and apply only a requested, named view policy.
- **Successor migration failure:** leave predecessor untouched, mark successor object mapping incomplete, and expose source/target lineage.

The transaction boundary is the append of validated events for one command plus its command receipt/outbox records. Atomic multi-object truth is not promised. Cross-object processes use sagas with compensating events and can expose an intermediate `IN_PROGRESS` or failure state.

## 15. Implementation Contact

A minimal deployable implementation consists of:

1. an append-only event store partitioned by `ObjectRef`, with optimistic stream revisions;
2. a model registry storing content-addressed Object, Protocol, Persona, Bridge, router-policy, and successor definitions;
3. a schema registry for envelopes and payloads;
4. the separate stateless `ProtocolRouter` that emits durable routing decisions;
5. sandboxed Protocol workers, preferably WASM or equally capability-restricted processes;
6. deterministic reducers and temporal relation projectors;
7. a materialization service with full-key caches and provenance closure;
8. a command gateway enforcing operation type, authorization, revision, invariants, and outbox delivery;
9. a lineage/migration service that cannot mutate predecessor streams; and
10. a conformance harness for replay, isolation, budget, and status-preservation tests.

Concrete tables or logs include `model_artifacts`, `object_events`, `routing_decisions`, `interaction_records`, `evidence_claims`, `view_manifests`, `command_receipts`, `successor_proposals`, and `lineage_edges`. Payload blobs are content-addressed; indexes are disposable projections.

Illustrative API boundaries are:

```text
GET  /models/{model_id}/{version}/{digest}/objects/{type}/{id}/events?cut=...
POST /views:materialize             # VIEW_MATERIALIZATION
POST /commands:submit               # RUNTIME_STATE_MUTATION
POST /protocols:conformance-check   # no model activation
POST /successor-model-proposals     # inert semantic proposal only
GET  /views/{view_id}/provenance
```

The command gateway writes events and an outbox row in one database transaction; workers consume the outbox at least once and deduplicate by interaction or command key. Projection checkpoints include input cut, artifact digests, and output digest. External calls by a Protocol must be requested as typed effects; their responses return as observation events before deterministic continuation. This is implementation contact, not a mandate for a specific database or queue.

## 16. Falsification Criteria

N03 is falsified as an adequate candidate for its stated scope if any conforming implementation permits one of the following:

1. replay of identical events, exact artifacts, context, Persona, and cut yields different output digests without a recorded nondeterministic input;
2. a `READ` or `VIEW_MATERIALIZATION` changes runtime state;
3. a runtime command changes a frozen schema, transition, status meaning, routing semantics, or Protocol definition;
4. a semantic change becomes active without a `SUCCESSOR_MODEL_PROPOSAL`, a new exact target, and traceable lineage;
5. switching Personas reuses or rewrites a conclusion without rematerialization and a transition receipt;
6. a conflict, `UNKNOWN`, `NOT_PROVEN`, `OUT_OF_SCOPE`, or unselected valid view is collapsed to a Boolean or deleted without an explicit view policy visible in the result;
7. two contexts that differ in a meaning-relevant field collide in the materialization cache;
8. an unseen Protocol satisfying the declared supported descriptor and class cannot be registered without core code modification;
9. an unsupported Protocol executes effects merely because its payload fits a generic envelope;
10. a late event overwrites history or produces an unmarked historical change;
11. Protocol code performs an undeclared network, store, or semantic effect;
12. a bridge loses meaning without a machine-visible loss declaration;
13. lineage admits a cycle or a successor silently replaces its predecessor for historical reads; or
14. a result cannot enumerate the events, rules, Protocol, context, and Persona that generated it.

Passing these tests does not prove semantic adequacy for every domain. Domain-specific validation must additionally test its Object lifecycles, relation rules, Protocol semantics, Personas, and evidence policies.

## 17. Strongest Self-Critique

N03's main weakness is that event primacy is an implementation bias with semantic consequences. Rich static structures, mutually constitutive relations, continuous processes, or retroactive reinterpretations may be awkwardly fragmented into events. Although relation assertions can drive transitions, the event log still owns operational history, so a genuinely relation-first worldview may see this as distortion.

The “minimal” Protocol descriptor is itself a meta-Protocol. It constrains heterogeneity to what N03 can envelope, sandbox, replay, and status-map. Thus support for unseen Protocols is extensibility within a declared class, not openness to arbitrary semantics. The separate router improves auditability but can become a policy bottleneck and may encode applicability assumptions despite its intended semantic thinness.

Deterministic replay requires external observations and nondeterministic choices to be captured, which increases latency and storage and can misrepresent interactive human judgment. Full provenance closure and context-complete cache keys may be expensive. Eventual cross-object sagas expose intermediate states and cannot guarantee universal atomicity. Finally, preserving every conflict and plural view avoids false convergence but can produce unusable result sets unless view policies are carefully governed; those policies reintroduce power and bias at the presentation layer.

These are structural limitations, not engineering tasks that N03 claims to have solved.

## 18. Unsupported Protocol Classes

N03 explicitly does not support, without a future successor model and new exact target:

- Protocols that require in-place self-modification of frozen semantic rules;
- Protocols that refuse stable identity, version, digest, typed input/output envelopes, or provenance;
- Protocols whose correctness depends on undeclared ambient state or unrecorded nondeterminism;
- Protocols requiring unrestricted direct database, network, filesystem, or actuator access from interpretation code;
- Protocols whose effects cannot be separated into proposals, validated commands, and recorded observations;
- Protocols demanding destructive rewrite of historical events or erasure of conflicting evidence as a semantic operation;
- Protocols with unbounded recursive reactions, non-terminating meta-interpretation, or no enforceable resource contract;
- continuous analog or embodied processes for which event sampling cannot preserve the fidelity required by the Protocol;
- relation-first systems whose semantics cannot survive provenance-preserving assertion-event adaptation;
- secret or opaque decision procedures when their declared obligations require inspectable derivation or replay;
- global transactions across arbitrary Objects, models, or external systems when compensating sagas are semantically insufficient;
- Protocols that require all Personas or worldviews to converge to one canonical result;
- Protocols whose truth/status vocabulary cannot preserve at least the distinctions among `UNKNOWN`, `CONFLICT`, `NOT_PROVEN`, `OUT_OF_SCOPE`, and plural valid views on the common surface; and
- Protocol classes requiring a new effect, conflict, identity, time, or routing semantics absent from the frozen kernel.

Such cases are reported as `OUT_OF_SCOPE` with the failed capability or conformance obligation. They are not coerced into a nearby supported class. A later design may address them only through a `SUCCESSOR_MODEL_PROPOSAL` with a new exact target and explicit lineage.
