## 1. Candidate thesis

N10 models an object and its protocol as two distinct, versioned state carriers coupled inside a guarded hybrid dynamical system. A continuous viability/control field may rank or propose locally safe evolution, while a discrete symbolic rail is the only component allowed to authorize an effect. The rail checks authority, provenance, scope, and lineage using explicit predicates; a high continuous score can never substitute for a missing symbolic authorization.

The claim is deliberately bounded: this construction is useful only where a deployment can declare finite protocol interfaces, typed observables, trust roots, and an auditable fragment of guard logic. It does not claim universal protocol translation, universal semantic equivalence, or decidability for arbitrary hybrid systems.

## 2. Scope, boundary, and non-goals

The unit of analysis is a deployment envelope

\[
D=(\mathcal O,\mathcal P,\mathcal A,\mathcal C,\mathcal T,\Delta),
\]

where \(\mathcal O\) is the admitted object vocabulary, \(\mathcal P\) the registered protocol descriptions, \(\mathcal A\) the authority model, \(\mathcal C\) the context/view vocabulary, \(\mathcal T\) the trusted provenance roots, and \(\Delta\) the declared numerical and temporal tolerances. Claims outside this envelope receive `OUT_OF_SCOPE`; they are not coerced into a result.

N10 addresses protocol-aware observation, bounded runtime adaptation, explicit semantic revision, protocol switching, and exact successor lineage. It does not solve trust-root selection, social legitimacy, ontology alignment for arbitrary unseen meanings, distributed consensus under unconstrained faults, or exact reachability in unrestricted continuous dynamics.

## 3. Explicit Object Model

An object revision is

\[
O_i=(\ell_O,r_i,\tau_i,A_i,R_i,K_i,I_i),
\]

with stable lineage identifier \(\ell_O\), immutable revision identifier \(r_i\), declared type/schema \(\tau_i\), attributed assertions \(A_i\), typed relations \(R_i\), admissible operations \(K_i\), and object invariants \(I_i\). Each assertion is a tuple

\[
a=(subject,predicate,value,context,validity,provenance,status).
\]

Object identity is not inferred from similarity. `lineage_id` says which history is being followed; `revision_id` identifies exact immutable semantics; an optional `runtime_instance_id` identifies a live execution. Relations may point to exact revisions or explicitly to a lineage policy such as “latest approved”; the two reference kinds cannot be silently interchanged.

Object state is separated into semantic state \(s_O\), which changes only by `SEMANTIC_MUTATION`, and runtime state \(x_O\), which may change by authorized `RUNTIME_MUTATION`. Observations and views never rewrite either state.

## 4. First-class variable Protocol Model

A protocol is itself a versioned object rather than a fixed interpreter:

\[
P_j=(\ell_P,p_j,Q,X,U,\Sigma,F,G,Reset,Obs,Views,Auth,Inv,Adapters).
\]

Here \(Q\) is the finite set of discrete modes; \(X\) is the declared continuous state space; \(U\) is the control/input space; \(\Sigma\) is the typed event alphabet; \(F_q\) is a mode-local vector field or differential inclusion; \(G\) contains symbolic transition guards; `Reset` contains discrete reset maps; `Obs` declares observables; `Views` declares contextual projections; `Auth` declares capability requirements; `Inv` declares mode and protocol invariants; and `Adapters` names versioned interoperability manifests.

Protocol variables are addressable, inspectable, and revisioned. Runtime-selectable parameters occupy a declared set \(\theta_R\); meaning-bearing parameters occupy \(\theta_S\). Changing \(\theta_R\) is not permitted to change schemas, guard meanings, authority requirements, status semantics, or observation meanings. A change to any of those belongs to \(\theta_S\), is a `SEMANTIC_MUTATION`, and creates a new exact protocol revision \(p_{j+1}\).

## 5. Coupled hybrid state and bidirectional interaction

The live system state is

\[
H_t=(r_i,p_j,q_t,x_t,c_t,\rho_t,L_t),
\]

where \(r_i\) and \(p_j\) select exact object and protocol revisions, \(q_t\) is the discrete mode, \(x_t\in X\) is continuous runtime state, \(c_t\) is context, \(\rho_t\) is the active Persona assignment, and \(L_t\) is the committed event-log position.

Interaction is genuinely bidirectional but typed:

- **Object to protocol:** object assertions, relations, invariants, and runtime observations parameterize \(F_q\), enable or disable guards, and constrain the viability set.
- **Protocol to object:** an authorized transition may observe the object, create a view, mutate declared runtime fields, or propose a semantic successor.
- **Protocol to protocol:** an authorized meta-transition may select a new protocol revision or adapter.
- **Object to protocol revision:** a newly encountered invariant may open a revision proposal, but it cannot edit the active protocol in place.

During dwell in mode \(q\), \(\dot x\in F_q(x,u;O_i,P_j,c)\). On event \(e\), a transition occurs only when its typed guard approves; then `Reset` updates runtime state and the authorized object/protocol effect is appended atomically to the log. If multiple guards approve without a declared priority or composition rule, the verdict is `CONFLICT` and no mutation occurs.

## 6. Viability/control field

For a declared horizon \(T\), context \(c\), and active revisions, N10 uses a constraint set \(K_{i,j,c}\subseteq X\) and a bounded viability estimate

\[
\widehat{V}_{i,j,c,T}=\{x\in K_{i,j,c}:\exists u(\cdot)\ \text{such that the certified approximation remains in }K\text{ on }[0,T]\}.
\]

A control field \(\kappa(q,x,O_i,P_j,c)\) can rank candidate inputs by safety margin, evidence coverage, cost, or reversibility. Its output is only a proposal ticket containing the solver version, assumptions, horizon, approximation direction, tolerance, and input hashes.

Exact viability is not asserted. Implementations must label estimates as certified inner sets, certified outer sets, or uncertified heuristics. Only membership in a certified inner set may satisfy a guard premise that explicitly asks for “certified viable”; outer-set membership or a heuristic score yields `NOT_PROVEN` for that premise.

## 7. Symbolic authority and provenance guard rail

Each event or assertion carries a provenance envelope

\[
\pi=(issuer,key,source,contentHash,issuedAt,validDuring,scope,delegationChain,derivation).
\]

A mutation guard evaluates typed premises over immutable inputs and returns one of `APPROVE`, `DENY`, `DEFER`, or `CONFLICT`. At minimum it checks signature/integrity, trust-root reachability, unexpired and non-revoked capability, operation kind, target identity, field scope, context, protocol revision, provenance of derived premises, and any declared separation-of-duty rule.

`APPROVE` alone can commit a mutation. `UNKNOWN`, `NOT_PROVEN`, `OUT_OF_SCOPE`, an unresolved provenance fork, or an unavailable revocation check maps to `DEFER` or `DENY` according to a declared fail policy; none maps to approval. Continuous confidence, utility, proximity, or viability margin is never authority. A derived assertion can carry no greater authority than the intersection of the scopes of its premises unless a separately authorized endorsement explicitly grants it.

The guard language must be a named, versioned, auditable fragment (for example, stratified Datalog plus a bounded arithmetic theory). An adapter containing arbitrary executable guard code is not guard-equivalent and is `OUT_OF_SCOPE` until separately sandboxed and authorized.

## 8. Honest continuous–discrete translation contract

The two layers are connected by partial, evidence-producing maps rather than claimed inverses:

- `Lift`: a supported symbolic predicate plus provenance becomes a continuous constraint, parameter, or initial-set restriction.
- `Witness`: a continuous trace becomes a signed evidence ticket with sampling regime, error bound, model version, and applicable predicate template.
- `Judge`: a symbolic proof policy consumes evidence tickets and returns a situated status.

`Witness(x)` is not itself a proposition and never grants authority. `Judge(Witness(x))` can establish only predicates whose observation contract and error budget are registered. Unsupported predicates return `OUT_OF_SCOPE`; inadequate evidence returns `NOT_PROVEN`.

No round-trip equality is promised. Symbolic → continuous → symbolic must be provenance-non-amplifying and may lose distinctions; continuous → symbolic → continuous may widen a set or quantize a value. Every crossing records `translation_debt` containing omitted fields, approximation direction, tolerance, and untranslatable residues. A transition whose guard depends on an unresolved residue cannot commit.

## 9. R/E responsiveness

N10 treats R/E as two declared stimulus lanes so the term remains testable rather than rhetorical:

- **R-lane (request responsiveness):** a typed request from a Persona or system actor is acknowledged, classified, authorized, and either answered or given a terminal situated status within a declared deadline \(\delta_R\).
- **E-lane (environment responsiveness):** a registered environmental observation is sampled, provenance-checked, incorporated into the viability estimate, and either acted on or explicitly deferred within \(\delta_E\).

Both lanes expose timestamps for receipt, snapshot selection, decision, and commit, plus the protocol revision used. Priority and overload policy are protocol fields, not hidden scheduler behavior. If the governing evaluation uses different meanings for R/E, those meanings require an explicit binding; absent that binding, N10 makes no score claim.

Responsiveness never weakens authority checks. A missed deadline produces a timeout event and `NOT_PROVEN` or a declared safe fallback; it does not authorize a rushed write. Environmental events arriving between decision and commit trigger revalidation when they affect a guard dependency.

## 10. Heterogeneous and unseen Protocol support

A heterogeneous protocol is admitted through a versioned adapter manifest declaring source revision, target revision, typed ports, event mapping, status mapping, observable mapping, authority mapping, loss profile, and tests. Composition is permitted only across compatible types and authority scopes. Information lost in mediation is retained as a residue; incompatible claims remain plural or become `CONFLICT`.

An unseen protocol can always be stored as an opaque protocol object with exact bytes/hash, provenance, identity, and lineage. It can be read and transported without being semantically executed. It gains bounded participation only after structural validation and one of:

- a verified adapter to a registered interface;
- a conservative capability declaration accepted by policy; or
- an isolated observation-only mode.

Missing semantics yield `OUT_OF_SCOPE`; missing proof for declared behavior yields `NOT_PROVEN`. N10 does not infer an unseen protocol’s authority rules from syntax, embeddings, similarity, or examples, and does not promise automatic full-fidelity adaptation.

## 11. Contextual, plural, and epistemic views

A view is a pure, versioned projection

\[
V_k=Project(O_i,P_j,c,\rho,policy_k,L_t),
\]

identified by the exact source revisions, log position, context, Persona, projection policy, and projection-code hash. It cannot mutate its source. Two contextual views may legitimately disagree because their scopes, times, authorities, or proof policies differ.

Atomic judgments use at least these distinct statuses:

| Status | Meaning |
|---|---|
| `UNKNOWN` | No admissible value or claim is available in the selected context. |
| `NOT_PROVEN` | A claim was posed, but the applicable proof policy is not satisfied. |
| `CONFLICT` | Two or more admissible, applicable claims are mutually incompatible and no authorized precedence rule resolves them. |
| `OUT_OF_SCOPE` | The active protocol/view does not define how to state or decide the claim. |
| `PROVEN(value)` | The named proof policy is satisfied for this value and scope. |

Plural results are first-class sets of situated judgments, not an error to be flattened. Aggregation must retain each source status and provenance. In particular, `UNKNOWN`, `NOT_PROVEN`, `CONFLICT`, and `OUT_OF_SCOPE` are neither false nor interchangeable.

## 12. Multi-Persona semantics

A Persona is a versioned policy lens

\[
\rho=(personaId,principalBinding,roles,contextScope,viewPolicy,capabilities,obligations,validity).
\]

It is not synonymous with a human identity or an authority grant. One principal may hold several Personas, and one Persona template may be instantiated by several principals. Capabilities are checked at the specific principal–Persona–context–operation intersection.

Concurrent Personas receive separate contextual views and may submit competing proposals. Their assertions remain attributable. A declared arbitration protocol may resolve proposals; otherwise incompatible admissible proposals produce `CONFLICT`. Persona switching changes the active lens and capability set but does not rewrite object facts, protocol semantics, prior provenance, or log history. Self-asserted Persona labels convey no authority without a valid binding.

## 13. Operation classes and effect discipline

Every endpoint and event declares exactly one primary effect class:

| Operation | Allowed effect | Identity/lineage consequence |
|---|---|---|
| `READ` | Retrieve immutable raw records or exact snapshots. | No new object/protocol revision; access may be audited. |
| `VIEW` | Compute/cache a contextual projection. | New view ID only; no source mutation. |
| `RUNTIME_MUTATION` | Change declared runtime fields, active mode, or \(\theta_R\). | Same semantic revision; new event-log position and runtime-state hash. |
| `SEMANTIC_MUTATION` | Change meaning, schema, invariant, guard, status policy, adapter semantics, or \(\theta_S\). | New immutable object or protocol revision with explicit lineage edge. |

A compound request is decomposed into separately guarded effects and commits atomically only if the protocol declares such a transaction. `READ` and `VIEW` handlers are structurally denied write capabilities. Reclassifying a semantic change as runtime tuning is an invariant violation, not an implementation convenience.

## 14. Switching fidelity

A switch from \(P_a\) to \(P_b\) requires a switch manifest

\[
M_{a\to b}=(Map_Q,Map_X,Map_\Sigma,Map_Status,Y,\epsilon,H,Residue,Rollback),
\]

where \(Y\) is the finite declared observable set, \(\epsilon\) its typed tolerance vector, and \(H\) the comparison horizon. Before commit, N10 records a source checkpoint, maps state, evaluates target invariants and authority, and produces a fidelity certificate or a bounded failure report.

Fidelity means only that, for the declared test domain and horizon, paired observable traces satisfy \(d_Y(y_a,y_b)\leq\epsilon\), while statuses, provenance references, and required authority are preserved exactly unless the manifest declares a visible loss. It is not global behavioral or semantic equivalence. Unmapped state is retained as residue. Loss affecting a guard dependency blocks switching; tolerated display-only loss may proceed if explicitly authorized.

Switches are event-atomic. A failed target initialization leaves the source checkpoint active. Zeno/chattering protection requires minimum dwell time, a finite switch budget, or a proved ranking function.

## 15. Exact successor identity and lineage

Semantic successors are immutable records in a lineage DAG. The canonical derivation key is

\[
d=Hash(parentRevisionIds,eventId,transformId,transformVersion,inputHashes,authorizedPatch).
\]

The committed successor receives a new exact `revision_id`, retains the relevant stable `lineage_id`, and stores all parent revision IDs, \(d\), the authorizing guard decision, provenance envelopes, and the commit log position. Replaying the same canonical derivation is idempotent; a different derivation cannot reuse the revision ID.

“Successor” never means “most similar” or merely “latest.” `successor(parent,eventId,transformVersion)` returns one exact revision or a typed absence. Branching yields several named successors and makes unqualified `next` return `CONFLICT`. Merging creates a new revision with every parent named. A protocol switch that changes semantics creates a protocol successor; a runtime-only switch records a new runtime-state hash but does not pretend that a new semantic revision exists.

## 16. Reference implementation shape

A minimal implementation has six separable components: (1) an append-only, hash-chained event and provenance store; (2) immutable object/protocol revision stores plus a lineage index; (3) a restricted symbolic guard engine; (4) a hybrid runtime and viability estimator; (5) an adapter registry and switch coordinator; and (6) a pure contextual-view engine.

The mutation path is:

1. Normalize a request/environment envelope without discarding its raw bytes.
2. Resolve exact object, protocol, context, Persona, and log-position references.
3. Validate types, provenance, capability, freshness, and scope.
4. Ask the viability layer for a labeled proposal ticket when required.
5. Evaluate the symbolic guard over the immutable snapshot and ticket.
6. Revalidate changed dependencies, then atomically append the decision and effect.
7. Materialize runtime state or a new semantic revision; derive views asynchronously from the committed log.

Deterministic guard replay uses pinned code/data versions. Numerical solvers record platform, tolerances, seed where relevant, and approximation class. Production hardening additionally needs authenticated storage, revocation distribution, clock policy, privacy controls, crash recovery, and model-checking or runtime monitors for critical invariants.

## 17. Invariants, failures, falsification, and unsupported claims

**Required invariants.** No mutation without symbolic approval; no authority gained through numerical confidence or derivation; no semantic change without a new revision; no view-to-source write path; no loss of provenance/status during aggregation; no unrecorded continuous–discrete crossing; exact parentage for every successor; no protocol switch with unresolved guard-relevant residue; and deterministic guard replay for a pinned snapshot.

**Expected failure modes.** Stale or revoked provenance, ambiguous principal binding, clock skew, adapter type mismatch, solver unsoundness, outer-set misuse, event races, log/store partition, guard-rule conflict, continuous-state drift, Zeno switching, view cache staleness, lineage forks, and state explosion. The safe response is explicit denial/defer/conflict, quarantine, rollback to the recorded checkpoint where valid, or operator escalation—not fabricated certainty.

**Falsification tests.** N10 is falsified for a deployment if any of the following occurs: an unauthorized high-score proposal commits; `VIEW` changes source state; `UNKNOWN` is treated as false; two conflicting situated claims are silently collapsed; an unseen protocol executes semantic effects without an admitted contract; a switch exceeds declared observable tolerance without a visible failure; a semantic mutation retains the old exact revision ID; the same successor query resolves nondeterministically; or a guard cannot be replayed from its recorded inputs.

**Unsupported claims.** N10 does not establish global safety, correctness of sensors, legitimacy of authorities, full equivalence of protocols, total support for unseen protocols, exact high-dimensional viability, termination of arbitrary hybrid executions, Byzantine consensus, or lossless ontology translation. Results are conditional on the declared envelope, trusted roots, observation contracts, solver certificates, and guard fragment.
