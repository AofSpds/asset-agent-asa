## 1. Candidate thesis

N06 models a domain as a **causal-incidence bundle** rather than as objects with relations and events attached afterward. Objects, structural relations, and event occurrences are separately addressable, but their admissible meanings are co-constituted:

- an event may create, terminate, qualify, or expose an incidence;
- an incidence may enable, inhibit, require, or contextualize an event;
- an object is recognized through stable identity plus its incident relations and causal history;
- a Protocol supplies the rules under which those structures are read, materialized, and, when authorized, changed.

The executable kernel is deliberately bounded: finite or finitely presented prime/causal event structures, typed finite-arity incidence relations, versioned Protocol definitions, and explicit counterfactual branches. N06 makes no claim that every possible Protocol or ontology can be represented.

## 2. Scope, commitments, and non-claims

N06 commits to all of the following within its support envelope:

1. An explicit Object Model and an explicit, first-class Protocol Model.
2. A Protocol is a runtime value pinned to an identifier and version, not a hard-coded evaluator mode.
3. Relations and event occurrences are first-class nodes with provenance and typed incidence.
4. Alternative futures are explicit branches, not overwritten intermediate states.
5. Materialization is contextual, reproducible from its declared inputs, and non-authoritative.
6. Object-to-Protocol conditioning and Protocol-to-Object enactment are both represented and traced.
7. Uncertainty, contradiction, proof failure, scope failure, and compatible plurality remain distinguishable.
8. Persona plurality and switching are modeled without presuming that one Persona is canonical.

N06 does **not** claim universal expressivity, automatic semantic translation, complete counterfactual discovery, global consistency across arbitrary Protocols, or safe execution of opaque effects. It does not infer authority from technical representability. A Protocol may be validly stored yet unsupported for evaluation or mutation.

## 3. Core vocabulary and semantic boundary

The kernel uses the following addressable entities:

- `Object`: a persistently identified domain participant or referent.
- `Relation`: a typed, role-labelled structural relation with two or more incidences.
- `Event`: a typed occurrence with causes, conflicts, observations, and effects.
- `Configuration`: a causally closed, conflict-free set of events representing one reachable history.
- `Branch`: an identified counterfactual extension from a shared configuration.
- `Protocol`: a versioned value defining admissibility, interpretation, observation, materialization, and effect rules.
- `Context`: the explicit parameters under which a Protocol is evaluated.
- `Persona`: a scoped policy/viewpoint bundle associated with a Person or other eligible Object.
- `Claim`: a proposition plus evidence, provenance, and epistemic result.
- `Materialization`: a derived view for a precise `(Protocol, Context, Configuration, Persona-set, target)` tuple.

“Object” and “Protocol” are roles in the architecture, not an absolute metaphysical partition. A Protocol definition is stored as an Object for provenance and lifecycle purposes, but it is accepted as an executable Protocol only after Protocol validation. Conversely, a Protocol may describe Object kinds without becoming one of their instances. The two roles therefore interact without being collapsed.

## 4. Explicit Object Model

An Object revision has this minimum shape:

```text
ObjectRevision {
  object_id: ObjectId,             // stable logical identity
  revision_id: RevisionId,         // immutable content-addressed revision
  kind: QualifiedType,
  schema_ref: ExactProtocolRef?,   // if its structure is Protocol-governed
  facets: Map<FacetName, Value>,
  claims: Set<ClaimRef>,
  created_by: EventId,
  predecessors: Set<RevisionId>,
  branch_id: BranchId,
  provenance: ProvenanceRef
}
```

Identity and state are separated. `object_id` survives an ordinary revision; `revision_id` never changes. A fork may preserve `object_id` only when the governing Protocol declares branch-relative identity. Otherwise it creates a new `object_id` with an explicit derivation edge. A merge never erases its parent revisions.

Object state is not a single mutable property bag. It is reconstructed from an accepted configuration, object revisions, incident relations, and claims under a pinned Protocol. Facets may be absent, multiply asserted, or disputed. Absence is not automatically false. Protocol-independent storage retains the original typed value and source even when the current Protocol cannot interpret it.

Personhood is not required for Objecthood. When an Object is a `Person`, it may own zero, one, or several Personas; none is automatically the “real” representation. Group, composite, delegated, and institutional participants remain distinct Object kinds rather than synthetic Persons.

## 5. First-class variable Protocol Model

A Protocol is an immutable, versioned value:

```text
ProtocolDefinition {
  protocol_id: ProtocolId,
  version: SemVerOrDigest,
  object_signatures: Set<ObjectSignature>,
  relation_signatures: Set<RelationSignature>,
  event_signatures: Set<EventSignature>,
  causal_rules: Set<CausalRule>,
  conflict_rules: Set<ConflictRule>,
  incidence_rules: Set<IncidenceRule>,
  admissibility_rules: Set<Predicate>,
  observation_rules: Set<ObservationRule>,
  materializers: Map<ViewType, Materializer>,
  effect_permissions: CapabilityPolicy,
  successor_rules: Set<SuccessorRule>,
  persona_policy: PersonaPolicy,
  bridge_requirements: Set<BridgeRequirement>,
  proof_profile: ProofProfile,
  support_envelope: SupportEnvelope
}
```

Every public evaluator receives an `ExactProtocolRef = (protocol_id, version-or-digest)` argument. No “current Protocol” singleton is semantically significant. A deployment default may fill an omitted UI field, but the resulting call record must contain the resolved exact reference.

Protocol definitions may themselves vary by object kind, context predicate, branch, or Persona, but variation is data: a selection rule returns one or more exact Protocol references with an epistemic result. It cannot silently replace the Protocol during evaluation. A Protocol upgrade creates a new version and an explicit migration or coexistence event; it never retroactively changes prior traces.

## 6. Relation–event co-constitutive kernel

For a pinned Protocol `P`, a branch history is represented by a prime event structure:

```text
PES(P) = (E, <=, #, label)
```

where `E` is the set of event occurrences, `<=` is a partial causal order, `#` is symmetric, irreflexive, and hereditary conflict, and `label` assigns an event signature. A valid configuration `K` is downward closed under `<=` and conflict-free under `#`.

Structural relations form a typed incidence hypergraph:

```text
RelationOccurrence {
  relation_id: RelationId,
  relation_type: QualifiedType,
  incidences: ordered Map<RoleName, NonEmptySet<EntityRef>>,
  valid_from: EventId,
  valid_until: EventId?,
  qualifiers: Map<Name, Value>,
  branch_id: BranchId,
  provenance: ProvenanceRef
}

EntityRef := ObjectRevisionRef | EventRef | RelationRef
```

Relation-to-relation incidence is stratified: a relation may cite only a lower stratum or an explicitly Protocol-approved same-stratum acyclic dependency. This keeps validation and materialization finite within the support envelope.

The coupling is explicit in two rule forms:

```text
EventEffect:   EventPattern -> Create | End | Qualify | Rebind RelationOccurrence
EventGuard:    IncidencePattern + ConfigurationPredicate -> Enable | Inhibit | Require EventPattern
```

An event that changes a relation and the relation that enables that event are not reduced to annotations on one another. Both receive identifiers, provenance, and validation. Any apparent causal cycle must be expanded into distinct proposal, authorization, and commitment events or be rejected as unsupported.

## 7. Counterfactual branches and causal evaluation

A branch is an explicit record:

```text
Branch {
  branch_id: BranchId,
  parent_configuration: ConfigurationDigest,
  divergence_event_set: Set<EventId>,
  assumed_claims: Set<ClaimRef>,
  generator: ProtocolRuleRef | HumanAssertionRef,
  status: OBSERVED | PROPOSED | COUNTERFACTUAL,
  provenance: ProvenanceRef
}
```

Branches with a common prefix remain distinct. Mutually exclusive alternatives are represented by `#`; compatible alternative extensions may both be valid and are reported as multiple-valid rather than as conflict. Counterfactual events cannot be committed to observed history merely because a materializer displayed them.

`evaluate_counterfactual(P, C, K, intervention)` constructs only branches licensed by `P.support_envelope`. It records the intervention, held-fixed assumptions, generated events, stopped rules, and proof budget. If branch enumeration is truncated, the result is `NOT_PROVEN` with a truncation receipt, never “no other branch exists.” If the intervention has no defined semantics under `P`, the result is `OUT_OF_SCOPE`.

## 8. Contextual materialization

Materialization has the pure semantic signature:

```text
materialize(
  protocol: ExactProtocolRef,
  context: Context,
  configuration: ConfigurationDigest,
  personas: OrderedSet<PersonaRef>,
  target: ExactEntityRef,
  view_type: ViewType
) -> EpistemicResult<MaterializedView>
```

`Context` minimally carries effective time, jurisdiction or normative domain if relevant, purpose, locale, observer/capability set, accepted evidence boundary, proof budget, and branch policy. A Protocol may require more named fields. Missing required context yields `UNKNOWN`; a context dimension whose semantics the evaluator cannot implement yields `OUT_OF_SCOPE`.

Every view includes its complete cache key, exact source revisions, Protocol version, configuration digest, active Personas, excluded branches, evidence cutoff, and materializer version. A cached view is valid only for that complete key. Materialization may populate a disposable cache but cannot change domain Objects, relations, causal history, Protocol semantics, or successor lineage.

Context may legitimately produce different views of the same Object. Such variance is retained as contextual variance. It is not normalized away unless the Protocol proves equivalence for the relevant observation surface.

## 9. Bidirectional Object–Protocol interaction

Interaction is a two-way, traced loop with different authorities on each edge:

1. **Object → Protocol (conditioning).** Exact Object revisions, incident relations, accepted configuration, Context, and Persona set are supplied as facts or claims. They can select applicable rules, instantiate roles, satisfy guards, or expose ambiguity. They do not rewrite the Protocol definition.
2. **Protocol → Object (enactment).** The Protocol evaluates rules and emits observations, materializations, proposed events, or capability-checked mutation plans. Only a committed event may change persistent Object/relation state.
3. **Feedback.** Newly committed events create new revisions or incidences; a later evaluation sees them through a new configuration digest. The original trace remains immutable.

The contract is:

```text
condition(P@v, K, O, R, C, Personas) -> EvaluationFrame
evaluate(EvaluationFrame)            -> Findings + ProposedEvents + Proofs
authorize(ProposedEvent, ActorCaps)   -> AuthorizedPlan | Denial
commit(AuthorizedPlan, ExpectedK)     -> NewK + MutationReceipt
```

There is no direct `Protocol.setObjectState`. Optimistic comparison against `ExpectedK` prevents a plan evaluated on one history from silently committing to another. Re-evaluation is required after a mismatch.

Bounded round-trip obligations are tested only on declared observation surfaces. A read followed by a materialization has no semantic effect. A supported Persona switch followed by its declared inverse must preserve the intersection of explicitly marked invariant observations; N06 does not require total or lossless round trips across arbitrary Protocols.

## 10. Honest epistemic results and multiple-valid outcomes

All queries, rule evaluations, translations, and materializations return:

```text
EpistemicResult<T> {
  status: KNOWN | UNKNOWN | CONFLICT | NOT_PROVEN | OUT_OF_SCOPE,
  valid_values: Set<T>,
  cardinality: NONE | SINGLE | MULTIPLE_VALID,
  evidence: Set<EvidenceRef>,
  objections: Set<EvidenceRef>,
  proof_or_receipt: ProofRef | ReceiptRef?,
  explanation: StructuredReason
}
```

The statuses have non-interchangeable meanings:

- `UNKNOWN`: required information is absent or unavailable at the accepted evidence boundary.
- `CONFLICT`: supported claims or branch commitments are jointly incompatible under the pinned Protocol.
- `NOT_PROVEN`: the requested conclusion does not follow from the available trace, rules, or bounded proof search; it may still be true.
- `OUT_OF_SCOPE`: the Protocol or evaluator declares no supported semantics for the request.
- `KNOWN`: the supplied proof profile establishes the returned value or values.
- `MULTIPLE_VALID`: a cardinality, not a failure status; two or more compatible results remain admissible.

`CONFLICT` cannot be produced merely because there are several values. `UNKNOWN` cannot be coerced to false or an empty collection. `NOT_PROVEN` cannot be marketed as disproof. `OUT_OF_SCOPE` cannot be repaired by choosing a default. An aggregation must retain the strongest relevant non-success receipt and the provenance of every returned value.

## 11. Plurality, multi-Persona participation, and switching fidelity

A Persona is a first-class, versioned policy/viewpoint object:

```text
Persona {
  persona_id: PersonaId,
  owner_ref: ObjectId,
  protocol_bindings: Set<ExactProtocolRef>,
  visible_facets: Set<FacetSelector>,
  interpretation_rules: Set<RuleRef>,
  authority_caps: CapabilitySet,
  commitments: Set<ClaimRef>,
  provenance: ProvenanceRef
}
```

An evaluation may activate an ordered set of Personas. The Protocol must declare whether their outputs are unioned, intersected, kept side-by-side, negotiated, or rejected as an unsupported composition. Side-by-side is the safe default because it preserves plurality. A collective Persona does not erase the participating Personas or inherit their authority without an explicit delegation relation.

A Persona switch is an event, not a UI-only flag:

```text
SwitchEvent {
  from: OrderedSet<PersonaRef>,
  to: OrderedSet<PersonaRef>,
  exact_target: ExactEntityRef,
  source_protocol: ExactProtocolRef,
  target_protocol: ExactProtocolRef,
  source_configuration: ConfigurationDigest,
  mapping: SwitchMapRef,
  fidelity_receipt: FidelityReceipt
}
```

The fidelity receipt lists preserved observations, translated observations, intentionally hidden observations, unmapped claims, authority changes, and introduced defaults. Unmapped information remains `UNKNOWN` or `OUT_OF_SCOPE`; it is not dropped silently. Incompatible commitments remain `CONFLICT`. Several faithful target renderings may be returned as `MULTIPLE_VALID`. A switch is refused when a required invariant observation or authority boundary cannot be preserved.

## 12. Typed operation and effect discipline

Every operation is assigned exactly one primary effect class and may declare narrower subeffects:

| Effect class | Permitted consequence | Forbidden consequence |
|---|---|---|
| `READ` | Fetch immutable records, proofs, receipts, or configuration metadata | Cache population, session change, domain mutation, Protocol change |
| `VIEW_MATERIALIZATION` | Compute a derived view and optionally write only a disposable cache entry keyed by all semantic inputs | Change Object/relation truth, commit events, change Protocol semantics |
| `RUNTIME_STATE_MUTATION` | Change ephemeral evaluator/session state such as cursor, open branch, local cache, or active UI Persona | Alter persistent domain history or the meaning of Protocol rules |
| `MODEL_SEMANTIC_MUTATION` | Through authorization and committed events, create revisions, incidences, Protocol versions, migrations, or lineage | Silent in-place rewrite, unreceipted side effect, mutation under an unpinned Protocol |

An API endpoint cannot relabel a semantic mutation as materialization because it is convenient to implement. Mixed requests are decomposed into separately receipted steps. `MODEL_SEMANTIC_MUTATION` requires an exact Protocol reference, expected configuration digest, actor/capability evidence, proposed effect set, authorization decision, and atomic commit receipt. External effects require idempotency keys and an external acknowledgement linked to the causal event.

## 13. Successors, exact targets, and lineage

All successor-producing operations use:

```text
SuccessorSpec {
  exact_target: EntityId + RevisionOrVersion,
  predecessor_refs: NonEmptySet<ExactEntityRef>,
  source_configuration: ConfigurationDigest,
  destination_branch: BranchId,
  governing_protocol: ExactProtocolRef,
  transformation: RuleRef | ExactPatchDigest,
  identity_mode: REVISION | FORK | DERIVATION | MERGE,
  requested_by: ActorRef,
  idempotency_key: String
}
```

“Advance this,” “use the latest,” or a display label is not an exact target. Name resolution, if offered, is a separate `READ` that returns candidate exact references and may return `MULTIPLE_VALID` or `CONFLICT`. The mutation call accepts only the selected exact reference.

The committed successor records all predecessor revisions, causal commit event, branch, transformation digest, Protocol version, authorization receipt, and provenance. A revision has one logical identity and at least one predecessor; a fork names its divergence point; a derivation receives a new logical identity; a merge lists every parent and preserves unresolved conflicts. Deleting or compacting payloads may not delete the minimal lineage receipt.

## 14. Heterogeneous and previously unseen Protocols

N06 supports heterogeneity through a small Protocol Intermediate Representation (PIR), declared adapters, and bridges. On ingest, an unseen Protocol is processed in four stages:

1. Parse its manifest and exact version without executing extension code.
2. Validate signatures, rule safety, effect declarations, proof profile, and support envelope.
3. Map supported constructs into PIR; retain unmapped constructs verbatim with stable identifiers.
4. Return a capability report per operation: `SUPPORTED`, `PARTIAL`, or `OUT_OF_SCOPE` with reasons.

`PARTIAL` never authorizes semantic mutation. It may permit reads or materializations whose dependencies are wholly within the mapped subset, and the view must enumerate excluded constructs. Unknown event or relation kinds remain opaque first-class records; they are not guessed into the nearest known kind.

Two Protocols interact only through a versioned bridge specifying type correspondences, observation translations, authority boundaries, causal/event mapping, conflict preservation, and loss accounting. If multiple bridges apply, selection returns `MULTIPLE_VALID` unless Context or an explicit choice selects one. If bridges disagree, the result is `CONFLICT`. If no bridge covers the requested operation, it is `OUT_OF_SCOPE`.

## 15. Implementation contact and bounded executable slice

A reference implementation can use an append-only event/lineage store plus indexed incidence tables:

```text
objects(object_id, revision_id, kind, payload_digest, branch_id, created_event)
relations(relation_id, type, valid_from_event, valid_until_event, branch_id)
incidences(relation_id, role, entity_kind, exact_entity_ref, stratum)
events(event_id, type, protocol_ref, branch_id, payload_digest, status)
causes(effect_event_id, cause_event_id)
conflicts(left_event_id, right_event_id, protocol_ref)
branches(branch_id, parent_configuration_digest, status, provenance_ref)
protocols(protocol_id, version_digest, pir_digest, support_envelope_digest)
claims(claim_id, proposition_digest, epistemic_status, evidence_digest)
lineage(successor_ref, predecessor_ref, commit_event_id, transform_digest)
receipts(receipt_id, effect_class, inputs_digest, outputs_digest, proof_digest)
```

The minimal service boundary is:

```text
read_exact(ref) -> Record
validate_protocol(definition) -> CapabilityReport
materialize(request) -> EpistemicResult<View>
evaluate(request) -> Findings + ProposedEvents
switch_personas(request) -> EpistemicResult<View> + FidelityReceipt
plan_successor(spec) -> ProposedEvent
authorize(plan, capabilities) -> AuthorizedPlan | Denial
commit(plan, expected_configuration) -> CommitReceipt
trace(entity_or_receipt) -> CausalLineage
```

Validation checks causal acyclicity, conflict heredity, configuration closure, incidence typing/stratification, exact reference resolution, rule determinism where claimed, and effect-class constraints before enabling mutation. The first executable slice is intentionally limited to finite configurations, finite-arity relations, deterministic materializers, explicit bounded branch generation, and local atomic commits. A persistent queue/outbox mediates external effects so storage commit and delivery acknowledgement are separately visible.

## 16. Invariants and acceptance properties

The implementation must continuously enforce:

1. **Causal closure:** every committed configuration contains the causes of each included event.
2. **Conflict exclusion:** no committed configuration contains events related by `#`.
3. **Conflict heredity:** a descendant of an event conflicts with every event that conflicts with its ancestor, unless the Protocol explicitly models reconciliation as new events rather than removing history.
4. **Incidence integrity:** every incidence resolves to an exact entity revision/version and satisfies its role signature and stratum rule.
5. **Co-constitution traceability:** every structural relation change names its event; every event guard depending on structure names the matched incidence set.
6. **Protocol pinning:** every evaluation, view, switch, and mutation receipt names one exact Protocol version per role.
7. **Effect separation:** reads and view materializations cannot produce model-semantic changes.
8. **Epistemic honesty:** unknown, conflict, not-proven, out-of-scope, and multiple-valid outcomes are not collapsed.
9. **Branch separation:** counterfactual, proposed, and observed events cannot be confused by projection or cache reuse.
10. **Persona fidelity:** switching records loss, conflict, authority change, and all preserved invariant observations.
11. **Target exactness:** every successor commit names exact target and predecessor references.
12. **Lineage permanence:** a semantic successor is unreachable without a durable lineage and authorization receipt.
13. **No view-as-truth:** a materialized view cannot become authoritative without a separately authorized semantic event.
14. **Idempotent commit:** repetition with one idempotency key yields the original receipt or an explicit conflict, never a second silent mutation.

Property tests generate small event structures and incidence graphs; mutation tests attempt effect smuggling; differential tests compare materialization from the event log with materialization from indexes; switch tests verify declared observable intersections; and recovery tests replay every commit from receipts.

## 17. Failure modes, falsification, and unsupported Protocols

Expected failure modes and required responses include:

| Failure | Required response |
|---|---|
| Missing Object/context evidence | `UNKNOWN` plus missing-field paths |
| Incompatible supported claims or branches | `CONFLICT` plus minimal conflicting evidence when computable |
| Exhausted branch/proof budget | `NOT_PROVEN` plus budget and truncation receipt |
| Unsupported rule, effect, or translation | `OUT_OF_SCOPE`; no guessed fallback |
| Several compatible results or bridges | `MULTIPLE_VALID` with every retained option |
| Stale configuration at commit | Reject, return current digest, require re-evaluation |
| Dangling or ill-typed incidence | Quarantine record; prohibit dependent mutation |
| Causal cycle in a prime-event claim | Reject or require explicit phase expansion |
| Branch explosion | Bounded frontier, deterministic cutoff receipt, `NOT_PROVEN` |
| Persona mapping loss | Expose loss in fidelity receipt or refuse required-fidelity switch |
| Protocol upgrade without migration | Coexist by version; never reinterpret old traces silently |
| External effect timeout | Preserve pending/outbox event; report delivery as `UNKNOWN`, not success |

N06 is falsified as a candidate for this task if any conforming implementation:

- must reduce either relations or events to unaddressable metadata to express the core examples;
- can mutate semantic state through `READ`, `VIEW_MATERIALIZATION`, or `RUNTIME_STATE_MUTATION`;
- silently assigns semantics to an unmapped unseen Protocol construct;
- conflates compatible plurality with contradiction;
- loses a required invariant observation during a purportedly faithful switch;
- produces a successor without exact target, predecessor set, branch, and governing Protocol version;
- cannot replay a committed lineage from durable receipts; or
- reports exhaustive counterfactual certainty after a bounded/truncated search.

Unsupported without an explicit extension include dense or truly continuous-time causality, unbounded higher-order incidence, non-well-founded self-referential relations, probabilistic/quantum semantics requiring amplitudes rather than explicit branches, arbitrary self-modifying executable Protocol code, irreversible opaque side effects without receipts, and Protocols whose correctness depends on a global oracle. These are honest `OUT_OF_SCOPE` results, not evidence that the underlying domain is invalid.

## 18. Global open questions and frozen disposition

The following global questions are deliberately preserved as open; N06 does not settle them by definition:

1. What criterion fixes the boundary between an Object rule and a Protocol rule when both can be represented as data?
2. Who has authority to register, validate, deprecate, or bridge a Protocol, especially one first encountered at runtime?
3. Which Context dimensions are mandatory globally, and which can only be known Protocol-locally?
4. What identity must persist across revision, fork, derivation, merge, and cross-Protocol translation?
5. What proof standard should each deployment attach to `KNOWN`, and when should resource exhaustion become `NOT_PROVEN` rather than `UNKNOWN`?
6. How should incompatible but legitimate Protocols coexist when no neutral bridge or adjudicator exists?
7. Which observations must a Persona switch preserve, and who is authorized to define or waive the fidelity threshold?
8. Can bridge composition be made associative on any useful bounded subset, and how should accumulated translation loss be measured?
9. What are acceptable complexity bounds for counterfactual branch generation and minimal-conflict explanation?
10. How are privacy, deletion rights, audit retention, and durable lineage reconciled without fabricating continuity?
11. When may a materialized result be promoted to an authoritative claim, and which event records that promotion?
12. How should distributed commits and external acknowledgements alter causal order when clocks, delivery, or authority disagree?

This document is a frozen, non-normative, unvalidated proposal. Changes require a new candidate revision and digest receipt; this artifact itself must not be treated as an adopted standard, reference answer, or validated implementation design.
