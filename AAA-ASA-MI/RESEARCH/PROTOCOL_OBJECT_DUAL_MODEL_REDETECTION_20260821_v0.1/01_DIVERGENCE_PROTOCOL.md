## Isolation contract

Each N01–N12 proposal is produced in a fresh worker context. Every worker receives only:

- the 16-row corrected requirement matrix and its explicit OPEN set;
- the general AAA research purpose;
- its assigned diversity seed;
- the mandatory 18-section candidate schema;
- permission to use general prior art as inspiration, never as AAA performance proof;
- an explicit prohibition on reading any other new candidate, C01–C08 architecture, candidate/evaluator ranking, D1 result, proxy prediction, current Owner D1 answer, or winner/champion statement.

Workers write only their assigned candidate file. No candidate worker participates in cross-candidate synthesis. The shared filesystem does not confer read authorization; workers are told not to enumerate or inspect it beyond their assigned output path.

## Mandatory candidate schema

Every frozen proposal must specify exactly and concretely:

1. Object Model
2. Protocol Model
3. Object↔Protocol interaction contract
4. Relation/Event treatment
5. Protocol activation/routing
6. Multiple Protocol coexistence
7. Conflicting Protocol behavior
8. Contextual view/materialization
9. Runtime state change
10. Semantic mutation/successor boundary
11. UNKNOWN/CONFLICT/multiple-valid-views semantics
12. Multiple Persona/worldview support
13. Invariants
14. Failure boundaries
15. Executable implementation contact
16. Falsification/abandonment conditions
17. Strongest self-critique
18. Protocols unsupported without distortion

Each proposal must also declare its non-trivial constraints, protocol request classes (`READ`, `MATERIALIZE`, `MUTATE_RUNTIME`, `MUTATE_SEMANTICS`), and result status algebra.

## Freeze sequence

1. Candidate architecture drafts are completed without access to any protocol battery.
2. Each file receives an exact byte identity and SHA-256 in the receipts layer; that identity is `CANDIDATE_ARCHITECTURE_FREEZE`.
3. The OPEN development battery is disclosed only after all twelve architecture freezes.
4. Open-battery responses are evaluation records against frozen candidates; candidate text is not repaired.
5. The held-out battery content remains unavailable to candidate generation and development-response work until those responses are frozen.
6. Held-out execution uses the same frozen candidate identities. Failure may generate a separately labeled successor hypothesis, never an in-place candidate edit.

## Convergence and leakage checks

- Candidate files are compared for seed compliance, primitive overlap, routing homogeneity, and shared unsupported regions.
- Similar vocabulary alone is not convergence; shared hidden ontology or identical failure behavior is.
- Any candidate that depends on unseen peer content is `ISOLATION_FAIL` and excluded rather than repaired.
- Held-out content appearing in a candidate or open response before unseal is `SEAL_FAIL`.
- No D1-derived content is permitted at any phase.

## Evaluation discipline

No scalar aggregate and no forced winner are produced. M1–M18 remain separate ordinal evidence surfaces (`STRONG`, `MIXED`, `WEAK`, `FAIL`, `NOT_PROVEN`) with four explicit risks. `NO ADEQUATE MODEL` remains valid.
